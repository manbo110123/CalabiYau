# 阶段 16：服务器权威碰撞与 3C 碰撞基础

状态：**16.0--16.3 已完成；当前 Tank 静态碰撞与战斗空间查询阶段已收口；16.4--16.5 尚未开启。** 用户于 2026-08-22 完成 revision 3 的双客户端与 100--200 ms 弱网移动碰撞验收，并于 2026-08-29 在 Unity 2022.3.62f3c1 下完成 revision 4 的射击遮挡、出生/重生和弱网人工验收。人物 Capsule、斜坡、台阶与骨骼 HitBox 仍属于后续 3C 阶段。

## 一、为什么重新规划碰撞阶段

阶段开始前，项目的 Tank、场景地面和部分方块已经带 Unity `Collider`，但联网模式下为了避免客户端物理与服务器权威位置互相争夺，客户端预测会主动忽略本地物理碰撞；当时独立 .NET 服务器也不知道 Unity Scene 中有哪些墙体，只按输入直接推进玩家 X/Z 坐标。16.2 已用共享、版本化的纯 C# 二维清单补上静态移动碰撞，但服务器仍不会直接读取 Unity Scene 或运行 Unity Physics。

因此当前问题不是“缺一个 BoxCollider”，而是缺少一条完整的数据与规则链路：

```text
同一份地图碰撞数据
-> 服务端固定 Tick 计算合法移动与射击遮挡
-> 客户端用相同规则做本地预测和未确认输入重放
-> 权威快照只修正剩余误差
-> Unity 模型与调试图形显示同一个碰撞结果
```

只打开客户端 Rigidbody 碰撞会造成“本地撞墙停住、服务器继续穿墙、权威快照再次把玩家拉过去”；这不是完整碰撞，不能作为本阶段方案。

## 二、阶段目标与明确边界

本阶段的总体目标不是编写完整物理引擎，而是建立一套适合本项目的、可测试的**玩法碰撞核心**：先完整解决当前 Tank 的静态地图移动与射击遮挡，再为以后人物 3C 的胶囊移动、斜坡、台阶和骨骼 HitBox 留下可复用基础。

### 现在完成：Tank 与静态地图闭环

- 世界边界、静态墙体和掩体由服务器拥有。
- Tank 旋转后使用二维 OBB 或经过明确取舍的简化形状参与移动碰撞。
- 支持正面阻挡、斜向滑墙、墙角稳定和有限防穿透。
- 客户端即时预测与服务器 Tick 使用同一碰撞语义。
- 未确认输入重放同样经过碰撞，不能只修正常规直线移动。
- 服务端射线先比较墙体与玩家的命中距离，墙更近时阻挡命中。
- 出生点和重生点经过占用检查，不能落在静态障碍内部。
- 提供服务端自动测试、Unity 调试可视化和双客户端弱网验收。

### 3C 出现后再完成：人物角色碰撞

- Capsule 角色移动。
- 地面探测、贴地、斜坡法线和最大可行走坡度。
- 过陡斜坡阻挡或滑落。
- 台阶高度、上台阶与下坡吸附。
- 跳跃、下落和冲刺 Sweep。
- LogicRoot 立即应用权威碰撞，VisualRoot 平滑跟随。

这些功能需要真实角色 Motor、相机和实际斜坡场景才能判断手感；当前可以先设计数据接口，但不提前声称完成。

### 模型与动画稳定后再完成：战斗 HitBox

- 头部 Sphere、躯干 Capsule/OBB、四肢 Capsule 等简化 HitBox Rig。
- 枪械 Raycast、近战 OBB/Sweep、范围技能 Sphere/Capsule 查询。
- 动画骨骼只驱动表现层 HitBox 姿态，不直接决定角色移动碰撞。
- 若服务端需要分部位延迟补偿，再保存有限历史 HitBox 姿态。

### 本阶段不做

- 刚体角动量、摩擦冲量求解、多物体堆叠、关节、布料或软体。
- 任意动态 MeshCollider 的完整模拟。
- 可推动箱子、移动门和动态平台的权威复制；它们属于动态实体模拟阶段。
- 玩家之间的物理推挤。第一版明确将 Player-Player 阻挡关闭，避免远端延迟位置干扰本地手感；若玩法需要，再单独设计服务端推挤规则。
- 为了碰撞迁移到 Unity Headless Server、第三方物理库、ECS 或复杂框架。

## 三、需要真正理解的碰撞概念

| 概念 | 解决的问题 | 本项目的第一落点 |
| --- | --- | --- |
| AABB | 用与世界坐标轴对齐的盒子快速排除不可能碰撞的对象 | 粗检测、无旋转墙体、空间范围 |
| OBB | 表示会随物体旋转的盒子 | Tank 足迹、旋转掩体、未来武器和躯干 |
| SAT 分离轴定理 | 判断两个凸形状是否重叠，并寻找最小穿透方向 | 二维 OBB 与 OBB 精确检测 |
| Circle / Sphere | 旋转不改变形状的简单碰撞体 | 范围技能、粗略角色检测、爆炸范围 |
| Capsule | 没有尖角、适合稳定角色移动 | 未来人物移动和四肢 HitBox |
| Ray / Segment | 查询一个方向上最先碰到什么 | hitscan、视线、地面探测 |
| Sweep / Cast | 查询一个形状从起点移动到终点途中是否命中 | 防高速穿墙、冲刺、胶囊移动 |
| Plane / Triangle | 表示地面、斜坡和网格表面 | 未来地面法线和坡度判断 |
| Broad Phase | 便宜地筛掉不可能碰撞的对象 | 第一版线性遍历 AABB；规模变大后再考虑网格/BVH |
| Narrow Phase | 对候选对象做精确形状检测 | SAT、Circle/OBB、Ray/OBB 等 |
| Collision Response | 决定碰撞后停止、滑动还是触发事件 | Tank 沿墙滑动；人物沿坡面移动 |

`AABB`、`OBB` 和 `SAT` 只负责碰撞检测的一部分。完整移动还需要位移积分、碰撞法线、穿透修正、滑动、容差和防穿透策略。

## 四、推荐架构

以下是逻辑职责，不要求第一步就拆出大量文件；每个模块只有在产生真实代码和测试时才建立。

```text
CollisionCore（纯 C# 数学）
├─ 形状：AABB、OBB、Circle、Ray；后续 Capsule、Plane、Triangle
├─ 查询：Overlap、Raycast、Sweep
└─ 结果：Point、Normal、Depth、Distance/TimeOfImpact

WorldCollision（地图空间）
├─ 地图边界与静态碰撞体
├─ Layer / Mask
├─ 粗检测与候选收集
└─ Move、Raycast、Overlap 等玩法查询

GameWorld（权威规则）
├─ 固定 Tick 移动调用 WorldCollision
├─ 出生/重生占用检查
└─ 射击先检查静态遮挡，再检查玩家

Unity Adapter（客户端）
├─ 本地预测与输入重放使用同一碰撞语义
├─ Gizmo 显示权威碰撞形状、法线和射线
└─ LogicRoot 使用碰撞结果，VisualRoot 只负责平滑表现
```

### 纯碰撞核心的约束

- 不依赖 `UnityEngine.Vector3`、`Rigidbody`、`Collider`、GameObject、UDP 或 JSON。
- API 接收值类型数据并返回明确结果，不在查询函数里偷偷修改场景对象。
- 浮点比较集中使用统一 `epsilon` 或 `skinWidth`，避免每个函数各写魔法值。
- 客户端和服务器应复用同一份纯 C# 源码或同一程序集；如果 Unity 兼容性阻碍共享，才退回“两端镜像实现 + 共同测试向量”，不能无说明地复制两套公式。
- 本项目不是严格确定性帧同步；共享碰撞规则的目标是减少预测分叉，不宣称不同运行时浮点结果逐位一致。

### 碰撞查询统一返回值

建议逐步形成类似语义的结果结构：

```text
CollisionHit
- Hit：是否命中
- Point：接触点
- Normal：从障碍指向可移动区域的法线
- PenetrationDepth：已重叠时的最小推出距离
- Distance / TimeOfImpact：射线或 Sweep 首次命中距离/时刻
- ColliderId：命中的地图碰撞体
- Layer：碰撞类别
```

第一小步只保留实际用到的字段，后续按测试需求增加，不为了结构完整一次性制造空字段。

## 五、地图碰撞数据：必须只有一个权威来源

Unity Scene 不能成为独立 .NET 服务器唯一能理解的地图格式。阶段 16 应建立一份简单、版本化的碰撞清单，例如：

```text
CollisionMap
- mapId
- collisionRevision
- worldBounds
- staticColliders[]
  - colliderId
  - shapeType
  - center
  - halfExtents / radius
  - yaw
  - layer
- spawnPoints[]
```

推荐演进：

1. 第一版手工维护少量训练场碰撞数据，并用 Unity Gizmo 验证它与可见墙体一致。
2. 增加启动校验：重复 ID、无效尺寸、出生点重叠、碰撞体越界直接报错。
3. 客户端连接时比较 `mapId + collisionRevision`；版本不一致时明确报错，而不是带着不同地图继续预测。
4. 地图变复杂后，再做 Unity Editor 导出器；导出器只是生成碰撞数据，不把完整 Unity Physics 搬进服务器。

静态墙体无需进入每帧快照。客户端和服务器加载相同版本即可。

## 16.1：Tank 二维移动碰撞

### 推荐模型

- Tank：二维 OBB；若实际手感证明 OBB 增加了不必要的墙角卡顿，可保留可配置 Circle 对照模式并记录取舍。
- 静态墙体：AABB/OBB。
- 粗检测：形状外包 AABB。
- 精确检测：SAT 或对应形状查询。

### 移动处理

```text
读取已校验输入
-> 计算本 Tick 期望旋转与位移
-> 将过长位移拆成有限子步，避免越过薄墙
-> 每个子步收集可能碰撞的静态障碍
-> 精确检测并得到法线/穿透深度
-> 推出重叠，并移除位移中朝向墙内的分量
-> 保留切向分量，形成滑墙
-> 迭代次数达到上限后停止，避免墙角死循环
```

旋转也可能让 OBB 角部进入墙体，因此旋转候选状态必须检测；第一版可以拒绝造成穿透的旋转，后续再评估更自然的旋转滑动。

### 需要配置并解释的参数

- Tank 半尺寸或半径。
- `skinWidth/epsilon`。
- 每个子步的最大移动距离。
- 单 Tick 最大碰撞迭代次数。
- 世界边界。

这些值必须集中配置并由测试覆盖，不能散落在客户端、服务器和 Inspector 中。

### 验收

- 正面撞墙停止；斜向撞墙沿墙移动。
- 连续顶墙不抖动、不逐 Tick 渗入。
- 墙角不会无限循环或被推出地图。
- 旋转靠墙时不会把 OBB 角塞进墙内。
- 30Hz、7m/s 基线下不能跨过训练场最薄墙体。

### 16.1 实现记录（2026-08-20）

- 已新增经过 ID、尺寸与世界边界校验的只读 `TankCollisionMap2D`，静态 OBB 预计算外包 AABB。
- 已新增纯 C# `TankWorldCollision2D`：候选旋转拒绝、有限移动子步、AABB 宽相、OBB SAT 窄相、最深穿透推出、滑墙、世界边界、子步与迭代上限。
- 已覆盖正撞、斜滑、120 Tick 持续推墙、双墙角、靠墙转身、窄通道、世界边界、30 Hz/7 m/s 薄墙和异常大位移等自动测试。
- 已提供仅供临时测试物体挂载的 `TankCollision2DPlayground`；没有修改 Scene、Prefab、现有 Tank 或 Rigidbody 联网设置。
- 16.2 已在后续步骤接入 `GameWorld`、客户端即时预测、未确认输入重放和地图版本握手；本条只描述 16.1 当时的完成边界。

## 16.2：服务器权威与客户端预测闭环

### 服务端

`GameWorld.SimulatePlayer()` 不再直接把位移无条件累加到 X/Z，而是向 `WorldCollision` 请求合法移动结果。服务器是最终位置裁决者。

### 客户端

- 不通过简单取消 `disableLocalCollisionInNetworkMode` 来恢复 PhysX 阻挡。
- 本地即时预测经过相同的地图与碰撞查询。
- `BuildReconciledLocalState()` 和未确认输入重放必须经过碰撞；否则即时移动正确、重放结果仍会穿墙。
- 远端 Avatar 继续由快照插值驱动，不使用延迟后的远端 Transform 推动本地玩家。

### 协议

第一版无需每 Tick 增加碰撞字段；只需确保握手或加载配置能确认地图版本。快照中的权威位置仍是最终恢复基线。

### 验收

- 正常网络下本地撞墙响应及时，没有每帧被服务器拉回。
- 100--200ms 延迟、抖动和少量丢包下，本地预测与权威结果最终一致。
- 故意让客户端加载错误碰撞版本时能够明确拒绝或报错。
- 修改客户端碰撞参数不能让服务器玩家穿过权威墙体。

### 16.2 实现与验收记录（2026-08-20 至 2026-08-22）

- 已新增唯一共享配置 `TrainingCollisionMap2D`：当前版本为 `sample-scene-training-ground@3`，包含 SampleScene 三个现有方块、世界边界、Tank Body 半尺寸与随朝向旋转的根节点中心偏移。

- 联网 Rigidbody 仍保持 kinematic；没有通过恢复本地 PhysX 阻挡伪造权威碰撞。
- `ClientHello`、`ServerWelcome` 和 `ServerReject` 已加入地图版本确认；不一致连接在注册玩家前明确拒绝。

- 用户已于 2026-08-22 完成正常网络、双客户端及 100--200 ms 弱网验收，确认同一持续输入擦过障碍时两端结果一致、最终收敛且不穿墙；**16.2 正式完成**。

## 16.3：射击遮挡、出生与玩法查询

### 射击遮挡

```text
构造服务端权威 FireRay
-> 查询最近静态墙体距离
-> 查询延迟补偿历史玩家命中距离
-> 墙体距离更近：子弹被遮挡
-> 玩家距离更近：按现有伤害规则处理
```

静态墙体不需要历史回溯；移动门、动态平台若以后加入，则必须记录历史状态或明确不参与历史遮挡。

### 出生与重生

- 出生点必须在世界边界内。
- Tank OBB/Circle 不得与静态墙重叠。
- 是否允许与其他玩家重叠由玩法规则明确；第一版可按候选出生点顺序选择空位。
- 找不到合法点时输出明确错误，不能默默生成到墙内。

### 技能接口预留

只预留查询语义，不实现技能系统：

- `OverlapCircle/Sphere`：范围技能。
- `Raycast`：hitscan、视线。
- `SweepCircle/Capsule`：冲刺、突进。
- `OverlapObb`：近战或矩形技能区域。

### 16.3 revision 4 实现与验收记录（2026-08-22 至 2026-08-29）

## 16.4：3C 人物 Capsule、斜坡与台阶（后续）

进入条件：离线 3C 场景已完成基本人物移动、相机与角色模型，能够实际测试坡道和台阶手感。

### 角色移动核心

- Capsule Sweep 计算可移动距离。
- Ground Probe 获取地面点和法线。
- 用 `dot(normal, up)` 或对应夹角判断坡度。
- 可行走坡面：把期望位移投影到坡面。
- 过陡坡面：视作墙或产生下滑分量。
- Ground Snap 解决下坡短暂悬空。
- Step Offset 解决限定高度台阶；超过高度则阻挡。
- Jump/Gravity 只修改 LogicRoot 的逻辑速度，动画只跟随状态。

### 与动画的边界

- Root Motion 可以提供动作期望位移，但最终位移仍经过权威碰撞与服务器校验。
- LogicRoot 保存真实碰撞位置；VisualRoot 平滑追随，不能用模型骨骼反向覆盖权威根位置。
- 相机防穿墙属于 Camera Collision，读取世界空间查询，但不改变角色权威位置。

## 16.5：骨骼 HitBox 与延迟补偿（后续）

进入条件：人物模型、Animator、骨骼命名和基本战斗动画已经稳定。

## 八、替代方案与为什么当前不选

### 直接重新开启 Unity Rigidbody 碰撞

实现最快，但客户端 PhysX 与 .NET 服务端直接位移规则不同，会重新产生穿墙、拉回和弱网分叉。只适合离线模式，不能作为联网权威方案。

### 改为 Unity Headless/Dedicated Server

可以复用 Unity Scene 和 PhysX，适合以后需要完整三维物理的项目；代价是迁移现有独立 .NET 服务端、部署方式和测试边界。本阶段保持现有架构，不做迁移。

### 引入 BEPU、Bullet、Jolt 等第三方物理库

能获得更多形状和动态刚体能力，但会同时引入库学习、Unity/服务器形状映射、版本与部署成本。当前目标是理解并完成玩法碰撞子集，不引入。

### 自己实现完整刚体物理引擎

会扩展到冲量、摩擦、角速度、堆叠、约束和连续碰撞求解，远超项目目标。本阶段明确停止在权威静态空间、角色移动与战斗查询。
