# 模块二：本地预测、服务端校正与远端插值复习笔记

> 使用方式：每个知识点按“结论 -> 工作过程 -> 代码定位 -> 面试背诵”复习。最后的“重点疑惑回顾”专门记录我实际卡住过的概念。

---

## 一、模块总览

```text
本地玩家：立即预测 -> 保存输入 -> 快照确认 -> 重建预测状态 -> 分级校正
远端玩家：缓存快照 -> 延迟播放 -> 两帧插值 -> 断档保持
```

本地玩家拥有自己的后续输入，重点是操作跟手；远端玩家不知道对方接下来会按什么，重点是画面平滑。

---

## 二、本地预测：先响应，再由服务器裁决

### 结论

服务端权威不能让本地操作等待服务器往返。本地预测让 Tank 在按键当下立即移动，同时把同一份输入发送给服务器，之后再以权威快照校正。

### 工作过程

1. `TankController.Update()` 读取移动、转向和瞄准。
2. `TankController.FixedUpdate()` 调用 `TankMotor`，立即移动本地 Tank。
3. `UdpNetworkClient.SendInputAtNetworkTick()` 以 30Hz 生成 `PlayerInput`，递增 `inputTick`。
4. 客户端在发送前把这条输入保存到 `localInputHistory`。
5. 服务器在自己的 Tick 中使用输入计算权威位置，随后通过快照确认处理进度。

默认移动速度约 `7 m/s`，转向约 `180 度/s`。客户端本地物理更新与服务器 Tick 并非严格同一套确定性模拟，因此后续仍必须校正。

### 代码定位

- `Assets/Code/TankController.cs`：读取输入、本地即时移动。
- `Assets/Code/TankMotor.cs`：预测阶段移动/转向。
- `Assets/Code/UdpNetworkClient.cs`：`SendInputAtNetworkTick()`、`SendPlayerInput()`、`SaveLocalInput()`。

### 面试背诵

> 本地预测解决服务器权威带来的操作滞后。客户端按键后立即使用本地输入驱动 Tank，并把带 `inputTick` 的输入发给服务器；服务器返回权威快照后客户端再校正，所以既保留跟手感，也保留服务器最终裁决。

---

## 三、输入历史与服务器确认

### 结论

客户端必须保存未确认输入。服务器快照中的 `lastProcessedInputTick` 用来确认：服务器已经把本地哪一条输入纳入权威世界。

### 工作过程

假设客户端已经本地执行并发送了 `101、102、103` 三条输入。服务器快照返回 `lastProcessedInputTick=101`：

```text
找到输入 101 的发送时间 -> 计算输入确认延迟
删除 101 及更早输入 -> 它们已属于服务器权威历史
保留 102、103 -> 本地已执行，但服务器尚未确认
```

这份剩余历史是之后“重建预测状态”的必要材料。若直接丢弃，客户端就不知道服务器快照之后自己又做过哪些操作。

用已确认输入的 `SentTime` 到当前快照到达时间计算的是**输入端到端确认延迟**：客户端上行 + 等服务器 Tick + 等快照发送 + 服务器下行。它不是纯 Ping，却更接近玩家一次输入被服务器认可所需的时间。

### 代码定位

- `UdpNetworkClient.StoreAuthoritativeLocalSnapshot()`：保存本地权威基线。
- `UdpNetworkClient.UpdateRttFromAcknowledgedInput()`：用最新确认输入计算确认延迟。
- `UdpNetworkClient.RemoveAcknowledgedLocalInputs()`：删除已确认历史。

### 面试背诵

> 我为每条本地输入保存 `inputTick` 和发送时间。快照返回 `lastProcessedInputTick` 后，客户端知道服务器已处理到哪条输入：已确认部分可以删除，未确认部分必须保留给回放；同时用最新已确认输入的发送时间估算端到端确认延迟，而不是把它误认为纯网络 Ping。

---

## 四、重建预测状态：不能直接覆盖服务器位置

### 结论

**重建预测状态**是指：从服务器刚确认的权威状态出发，重新执行本地尚未被确认的输入，得到“按服务器基准推算到现在，本地角色应该在哪里”。

### 工作过程

服务器快照到达时，客户端的 Tank 通常已经继续执行了好几条输入。比如服务器确认到 `inputTick=101`，而本地已经执行到 `103`：

```text
服务器快照：权威位置 A，确认到输入 101
本地历史：102、103 仍未确认

不能直接把 Tank 设为 A
-> 会抹掉 102、103 的正常本地操作
-> 画面会突然往后跳，操作产生割裂

正确做法：从 A 重放 102、103
-> 得到重建目标位置 B
-> 再比较当前本地预测位置 C 与 B 的误差
```

`ReplayCurrentPartialInput()` 还会补上“最近一次网络输入发送后，到当前时刻”的小段移动。原因是 Tank 在每个 `FixedUpdate` 都持续移动，而网络输入只以 30Hz 发送；不补这段时间会让重建目标总是略微落后当前预测。

### 代码定位

- `UdpNetworkClient.BuildReconciledLocalState()`：从权威快照重放未确认输入。
- `UdpNetworkClient.ReplayBufferedInput()`：重放完整历史输入。
- `UdpNetworkClient.ReplayCurrentPartialInput()`：补网络 Tick 之间的部分输入。
- `UdpNetworkClient.ReconcileLocalPrediction()`：比较当前位置和重建目标。

### 面试背诵

> 服务器快照确认的只是较早时刻的状态，本地此时可能已经继续执行了多条输入，所以不能直接用权威位置覆盖 Transform。我的做法是从权威快照开始重放所有未确认输入，重建到当前时刻的预测目标，再用该目标与当前本地状态比较并校正。这样不会把网络往返期间本来就合理的移动误判为错误。

---

## 五、分级校正与当前移动中的边界

### 结论

重建目标与当前预测接近时不处理，中等误差平滑收敛，大误差立即修正；但当前项目在持续移动期间会延后所有校正。

### 工作过程

`ReconcileLocalPrediction()` 比较当前位置 C 与重建目标 B：

```text
误差 <= Dead Zone（约 0.15m）
-> 忽略微小浮点/网络误差

Dead Zone < 误差 < Hard Threshold（约 1.25m）
-> 设置平滑目标，逐步追向 B

误差 >= Hard Threshold
-> 立即应用 B
```

不过当前 `TankMotor` 在 `FixedUpdate` 推动 Rigidbody，`NetworkTankAvatar` 在 `Update` 也会尝试修正同一个 Rigidbody/Transform。若玩家持续按移动键时平滑拉回，两个模块会互相争夺位置，产生明显拉扯。

因此当前实现是：有移动/转向输入或停止后约 0.2 秒内，先暂缓校正，等空闲快照再收敛。按当前代码顺序，移动期间连硬修正也会被延后。这是为当前 Tank Demo 做的手感取舍，风险是两端规则明显分叉时，误差可能在松手后才集中暴露。

### 代码定位

- `UdpNetworkClient.ReconcileLocalPrediction()`：死区、平滑、硬修正及移动中延后逻辑。
- `NetworkTankAvatar.SmoothToPredictedServerState()`：设置修正目标。
- `NetworkTankAvatar.SmoothLocalPredictionCorrection()`：执行平滑追赶。

### 面试背诵

> 我不是每收到快照就强制拉回位置，而是基于重建误差做分级处理：小误差忽略，中等误差平滑收敛，大误差硬修正。当前逻辑层和表现层仍共用一个 Tank Rigidbody，为避免本地移动和校正同时写位置产生拉扯，我在持续输入时延后校正；这是当前实现的明确边界，未来会通过逻辑根与表现根分离解决。

---

## 六、逻辑层与表现层分离：后续为何要做双层根节点

### 结论

当前项目尚未彻底拆分逻辑与表现。更成熟的方案会让逻辑位置立即正确，让模型视觉平滑追赶，从而同时保证规则正确和画面稳定。

### 工作过程

当前 Tank 的碰撞、预测、权威修正和模型表现基本作用于同一个对象，因此“立即校正”与“平滑展示”会互相影响。

后续可改为：

```text
LogicRoot：碰撞箱、预测、服务器校正、开火基准
-> 收到权威结果时立即到正确位置

VisualRoot：坦克模型、炮塔、动画、特效
-> 每帧平滑追赶 LogicRoot
```

这样开火与碰撞使用的是已经正确的 `LogicRoot`，不会因为视觉缓动而拿到旧位置；玩家看到的模型则不会突然瞬移。它不是重复计算，而是分开“游戏事实”和“画面表达”。

### 面试背诵

> 当前项目的逻辑与表现还没有彻底拆开，所以移动中需要延后校正避免争夺 Rigidbody。更成熟的升级是双层根节点：逻辑根立即应用预测和权威校正，保证碰撞与开火基准正确；表现根平滑追赶逻辑根，降低视觉跳变。这样把同步正确性和画面观感解耦。

---

## 七、远端 Avatar 与快照缓冲

### 结论

本地玩家预测自己的未来；远端玩家没有对方后续输入，因此不做输入预测，而是缓存服务器快照后播放历史状态。

### 工作过程

服务器快照到达后，客户端按玩家 ID 查找或创建远端 Tank Avatar。这里的 Avatar 是“网络玩家在 Unity 场景中的 Tank 表现对象”，不是 Unity 导入模型时的 Mecanim Avatar 资源。

`NetworkTankAvatar.AddRemoteSnapshot()` 把远端状态按 `serverTick` 放进缓冲区：同 Tick 新状态覆盖，乱序包按 Tick 插入，超过上限删除最旧状态。之后在 `Update` 中，`PlayRemoteSnapshotBuffer()` 从缓冲区取两份包围播放时间的快照进行插值。

### 代码定位

- `UdpNetworkClient.ApplyPlayerSnapshot()`：区分本地校正和远端处理。
- `UdpNetworkClient.GetOrCreateRemoteAvatar()`：创建/查找远端 Tank。
- `NetworkTankAvatar.AddRemoteSnapshot()`：维护快照缓冲。
- `NetworkTankAvatar.PlayRemoteSnapshotBuffer()`：消费缓冲并显示。

### 面试背诵

> 远端玩家没有本地输入可用于预测，所以我为每个远端玩家维护独立的 `NetworkTankAvatar` 和按 `serverTick` 排序的快照缓冲。快照到达后先处理同 Tick 覆盖和乱序插入，再由 Avatar 在客户端历史时间线上插值播放，优先保证远端观感平滑。

---

## 八、renderTick 与远端快照插值

### 结论

`renderTick` 是客户端播放远端快照的历史时间点。客户端故意显示“稍早的服务器状态”，以保证插值时已经拥有前后两份快照。

### 工作过程

客户端不会收到一份快照就立即显示它，而是根据最新到达快照、插值延迟和本地经过时间计算 `renderTick`：

```text
renderTick
= 最新快照 Tick
- 有效插值延迟
+ 最新快照到达后经过的本地时间换算 Tick
```

随后找到：

```text
olderTick <= renderTick <= newerTick
```

位置用 `Lerp`、旋转用 `Slerp`、瞄准点用 `Lerp`。如果直接播放最新快照，就没有“下一份已知状态”作为插值终点，UDP 到包间隔稍有波动就会停顿或跳动。

### 面试背诵

> `renderTick` 是客户端播放远端历史快照的位置，不是新的服务器 Tick。客户端刻意落后几个 Tick，在两个已到达的权威快照之间进行位置和旋转插值，用少量远端视觉延迟换取对 UDP 抖动的缓冲和稳定画面。

---

## 九、低频复制与自适应插值延迟

### 结论

服务器始终以 30Hz 模拟，但会按距离和战斗状态以不同频率向不同客户端复制实体；低频实体需要更大的插值延迟，避免缓冲区提前耗尽。

### 工作过程

当前复制策略大致为：

```text
自己、近距离或战斗实体：30Hz
18--45m 的非战斗远端实体：5Hz
45m 外：不复制
```

5Hz 不代表该实体只被服务器模拟 5 次，而是服务器仍每 Tick 模拟，只是每秒只向此客户端发送约 5 次状态。30Hz 服务器下，5Hz 快照可能是 Tick `100 -> 106 -> 112`。

如果仍用短插值延迟，例如 3 Tick，客户端在 Tick 106 到达前就会用完 Tick 100 的缓冲，只能保持位置；新快照到达后再跳过去。当前用 `EffectiveRemoteInterpolationDelayTicks = max(默认延迟, 实际相邻快照 Tick 间隔 + 1)` 动态增加延迟，让播放时间尽量一直落在两帧之间。

### 代码定位

- `ClientReplicator.cs`：按客户端、距离和优先级筛选复制状态。
- `NetworkTankAvatar.AddRemoteSnapshot()`：统计观察到的 Tick 间隔。
- `NetworkTankAvatar.PlayRemoteSnapshotBuffer()`：使用有效插值延迟计算 `renderTick`。

### 面试背诵

> 我把服务器模拟频率和状态复制频率分开：服务器仍以 30Hz 推进世界，但远处非战斗实体可低频下发，减少带宽和序列化开销。低频快照间隔更大，因此客户端根据实际 Tick 间隔提高插值延迟，用更高的远端显示延迟保证持续有两帧可插值，避免保持后跳变。

## 十、断档保持与未实现的外推

### 结论

当前远端策略是“有两帧就插值，找不到配对就保持可用状态”，尚未做速度外推。

### 工作过程

当网络抖动或丢包导致下一份快照没有按时到达，客户端无法构造前后插值端点。此时当前实现保持最近可用显示，而不是根据旧速度猜测未来。

外推能减少短暂的停住感，但远端没有对方未来输入：对方可能刚好转向、撞墙或死亡，猜错后需要回拉，反而出现穿模或大跳变。因此本项目先选择保守、易解释的断档保持。后续可以只在极短时间窗口内做有限外推，超过上限立刻停止。

### 面试背诵

> 当前远端同步只实现了插值和断档保持，没有做速度外推。外推能减少短断档的停顿，但因为客户端没有远端玩家的后续输入，猜错后会引发回拉和穿模；我先选择保守策略，后续可限制在很短时间窗口内加入有限外推。

## 十一、本模块重点疑惑回顾

### 1. 为什么收到快照后，要用当前确认的输入计算 RTT？

因为 `lastProcessedInputTick` 明确说明哪条输入已经走完整个“客户端发送 -> 服务器 Tick 消费 -> 快照返回”链路。用它的发送时间计算，得到的是输入确认延迟；未确认输入还没走完链路，不能用来测量。

### 2. 一直移动时，延后校正会不会让误差越来越大？

会有这个风险。当前实现以避免同一 Rigidbody 的移动与校正拉扯为优先，依赖两端规则基本一致；明显分叉时误差会累积到空闲后再修正。未来拆分 `LogicRoot` 和 `VisualRoot` 后，可以逻辑立即校正、视觉继续平滑。

### 3. 低频增加插值延迟，是不是让游戏更卡？

它只增加低优先级远端实体的**视觉播放延迟**，不影响本地输入响应，也不降低服务器模拟频率。代价是远端看起来更“过去”，收益是低频包之间仍有两帧可插值，不会一停一跳。

### 4. Avatar 和 `renderTick` 分别是什么？

Avatar 是场景里代表网络玩家的 Tank 表现对象；`renderTick` 是该对象从快照缓冲中播放历史状态的位置。一个是实体对象，一个是历史播放时间点。

---

## 十二、30 秒模块总结

> 本地玩家按键后立即预测移动，并保存带 `inputTick` 的未确认输入。服务器快照返回后，客户端根据 `lastProcessedInputTick` 删除已确认输入，从权威状态重放剩余输入来重建当前预测目标，再按误差分级校正。远端玩家不预测输入，而是按 `serverTick` 缓存快照，使用 `renderTick` 延迟播放并在两帧之间插值；远端低频复制时动态提高插值延迟，当前断档保持、未做速度外推。当前逻辑与表现尚未彻底分离，是后续 3C 和表现优化的重要方向。
