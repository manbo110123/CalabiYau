# 模块一：服务器权威、Tick 与命令时间线复习笔记

> 使用方式：每个知识点按“结论 -> 工作过程 -> 代码定位 -> 面试背诵”复习。最后的“重点疑惑回顾”只收录我实际问过、需要优先复盘的问题。

---

## 一、服务器权威

### 结论

本项目中，客户端可以立即预测和表现，但只有服务器 `GameWorld` 计算出的状态才是最终游戏事实。客户端上传操作意图，不上传最终位置、伤害或死亡结果。

### 工作过程

1. 玩家按下移动或开火，客户端发送 `PlayerInput` 或 `FireRequest`。
2. `UdpGameServer` 收到 UDP 包后，只做身份、字段和时序的基础校验，再转交给 `GameWorld`。
3. `GameWorld` 在固定 Tick 中应用有效输入、计算移动、冷却、命中、血量和死亡。
4. 服务器把结果构建为快照或关键事件发回客户端。
5. 客户端把服务器结果作为基准：本地玩家做预测校正，远端玩家做快照插值。

如果让客户端直接提交 `Transform` 或“我命中了谁”，修改客户端就能伪造超速、瞬移或伤害。当前项目已经把最终裁决放在服务器，但完整障碍物碰撞、穿墙检测仍是后续工作，不能夸大为完整反作弊。

### 代码定位

- `Server/Server/UdpGameServer.cs`：UDP 收发、消息路由、Tick 循环。
- `Server/Server/GameWorld.cs`：权威位置、战斗、血量、死亡和重生规则。
- `Server/Server/SnapshotBuilder.cs`：把权威状态组织为快照。
- `Server/Server/ClientReplicator.cs`：按不同客户端筛选要复制的状态。

### 面试背诵

> 我采用服务器权威的状态同步架构。客户端只提交移动、瞄准和开火等意图，服务器在 `GameWorld` 中统一计算位置、命中、血量和死亡，再下发权威状态。客户端的本地移动只用于预测和表现，不能决定最终结果，因此能避免客户端直接伪造坐标或伤害。

## 二、固定 Tick 与三条时间线

### 结论

`serverTick` 是服务器推进权威世界的时间轴，当前默认 30Hz。它与客户端输入编号 `inputTick`、服务器快照编号 `snapshotSequence` 职责不同，不能混用。

### 工作过程

服务器每隔固定时间执行一次世界更新：取出待处理命令 -> 推进移动与冷却 -> 结算开火和命中 -> 生成快照。每执行一次，`serverTick` 加一。

固定 Tick 不依赖服务器真实帧率，所以 60 FPS 和 120 FPS 的机器不会因为 `Update` 次数不同而以不同节奏推进游戏规则。它提供稳定的权威时间坐标，便于快照排序、历史回溯和问题定位。

| 字段 | 生成方 | 工作内容 |
| --- | --- | --- |
| `serverTick` | 服务器 | 标记权威世界推进到第几步 |
| `inputTick` | 客户端 | 标记第几条本地输入，供确认和回放 |
| `snapshotSequence` | 服务器 | 标记第几份快照，客户端丢弃旧 UDP 快照 |

### 代码定位

- `UdpGameServer` 的固定 Tick 循环：驱动世界更新。
- `GameWorld`：在指定 `serverTick` 消费命令并推进状态。
- `WorldSnapshot`：携带 `serverTick`、快照序号和输入确认信息。

### 面试背诵

> `serverTick` 是服务器推进权威世界的统一时间轴，我的服务器以 30Hz 固定步长结算移动、冷却和战斗。它保证规则推进和快照比较的稳定；`inputTick` 只用于标识客户端输入及其确认进度，`snapshotSequence` 则用于过滤旧快照，三者不能替代。

## 三、命令时间线：收包不直接改世界

### 结论

UDP 包到达的先后不稳定，因此接收回调不能直接移动角色、扣血或判定命中。网络层先缓存命令，`GameWorld` 再在固定 Tick 中统一消费。

### 工作过程

```text
收到 UDP 包
-> UdpGameServer 校验客户端身份和消息字段
-> 将输入或开火写入 GameWorld 待处理缓存
-> 下一个 serverTick 统一消费有效命令
-> 修改权威世界状态
-> 构建快照、事件并发送
```

例如两名玩家的开火包可能在网络上先后到达，但服务器仍把它们放入本 Tick 的规则流程中，按统一的冷却、历史回溯和命中逻辑处理。这样网络收包只负责通信，游戏规则集中在 `GameWorld`，更容易单元测试和复现问题。

本项目还使用 `InputHoldTimeoutTicks = 6` 的输入租约：如果“松开移动键”的包丢失，服务器只短暂沿用上一次输入，租约到期后自动停下，避免角色永久前进。

### 代码定位

- `UdpGameServer.cs`：收包后路由，而非直接改战斗状态。
- `GameWorld.TryQueueInput()`：校验并缓存连续输入。
- `GameWorld.ConsumeLatestInputForTick()`：在 Tick 中消费移动意图。
- `GameWorld` 的 `PendingFires`：缓存待结算开火。

### 面试背诵

> 我把网络收包和游戏规则推进分开：UDP 回调只做校验和入队，`GameWorld` 在固定 Tick 中统一消费命令。这样不会让网络到达时刻直接决定伤害和位置，也使输入、开火、冷却等规则可以脱离 Socket 层单独测试。对于持续输入，我还加入输入租约，避免停止包丢失后角色一直移动。

## 四、消息分级：连续输入、离散命令和关键结果

### 结论

不同消息丢失后的影响不同，不能用一套“可靠/不可靠”规则处理全部消息。

### 工作过程

**连续输入：最新意图优先。**

移动和瞄准持续发生。服务器在一个 Tick 内可能收到多条 `PlayerInput`，`ConsumeLatestInputForTick()` 选最新有效意图；迟到的旧“向左移动”通常已被新的“向前移动”替代，不值得补走旧轨迹。输入租约在没有新包时防止旧意图永久生效。

**离散命令：去重、有限重发、Tick 结算。**

一次开火不能因为 UDP 重发而造成多次伤害。客户端为请求附加 `fireSequence`，未收到收据时有限重发原请求；服务器缓存收据并去重，同一序号只入队一次。之后在 `PendingFires` 中等待服务器 Tick 进行命中判定。`FireReceipt` 只表示“服务器已处理该请求的接收/排队决定”，不等于命中。

**关键结果：可确认、可去重、抗乱序。**

死亡、重生、击杀、结算使用 `eventId`、ACK、有限重发和客户端去重。不同生命周期事件还携带 `lifeStateVersion`：即便重生事件先到，旧死亡事件后到，也不会把玩家状态倒退。

| 数据类型 | 当前策略 | 原因 |
| --- | --- | --- |
| 移动、瞄准 | 最新意图 + 输入租约 | 旧值过期快，优先实时性 |
| 开火请求 | 序号、有限重发、服务器去重 | 防止漏射或重复结算 |
| 状态快照 | 新包优先 | 最新权威状态覆盖旧状态 |
| 死亡、重生、击杀 | ACK、重发、去重、版本号 | 关键结果不能轻易丢失或倒序 |
| 枪口火焰、命中特效 | 可丢失 | 主要是视觉，后续状态可兜底 |

### 代码定位

- `GameWorld.TryQueueInput()` / `ConsumeLatestInputForTick()`：连续输入。
- `GameWorld.TryQueueFireWithReceipt()`：开火序列去重和收据。
- `ReliableEventLedger.cs`：关键事件账本、ACK 与重发。
- `UdpNetworkClient.ProcessReliableEvent()`：客户端去重与应用生命周期事件。

### 面试背诵

> 我按业务语义而不是按“UDP 是否可靠”统一处理消息。移动是连续意图，迟到旧包价值低，所以消费最新输入；开火是离散命令，用序列号、有限重发和服务端去重保证不重复射击；死亡重生是关键结果，再增加 ACK、事件去重和生命状态版本，防止丢失或乱序覆盖。

## 五、当前方案与严格输入 Tick 模拟的取舍

### 结论

当前移动采用“最新意图消费”的状态同步，并非严格按 `inputTick` 逐条模拟的帧同步。

### 工作过程

严格输入 Tick 模拟会把每条输入映射到确定的服务器模拟帧，服务器按顺序逐条执行；客户端收到确认后，在同一输入序列上回滚重演，理论上两端结果更一致。

但它需要时钟映射、输入延迟缓冲、缺失输入策略、稳定的物理/数学结果和更复杂的丢包处理。本项目为保持可理解、可验证，选择每 Tick 只取最新移动意图，再由权威快照做校正。它对坦克持续移动已经足够自然，但迟到旧输入不会被补走，弱网下会有小轨迹误差。

### 面试背诵

> 我的项目不是严格帧同步。移动采用最新意图消费，优点是实现简单、实时性好，适合状态同步 Demo；代价是客户端与服务器不保证逐输入完全一致，所以通过权威快照和客户端预测校正收敛误差。若改为严格输入 Tick 模拟，需要额外处理时钟同步、输入缓冲和确定性问题。

## 六、本模块重点疑惑回顾

### 1. `serverTick` 是服务器推进世界的时间轴吗？

是。它标记服务器第几次固定步长地推进权威世界，但不表示某条输入一定被处理；输入确认看 `lastProcessedInputTick`。

### 2. 移动能消费最新意图，开火和死亡为什么不行？

因为旧移动方向通常会被新方向替代；而某一次开火、死亡或重生本身都有独立业务含义，不能因乱序或重传而随意丢掉、重复执行或覆盖新结果。

### 3. 服务器权威是否天然等于反作弊？

不等于。它限制客户端伪造最终结果，但速度上限、碰撞、射线合法性和异常时序检测仍需要服务器逐项实现；当前项目的服务器障碍物碰撞仍未完成。

---

## 七、30 秒模块总结

> 服务器以 30Hz 的 `serverTick` 推进 `GameWorld`。客户端提交输入和开火意图，网络收包先入队，固定 Tick 再统一结算权威状态。移动使用最新意图和输入租约，开火使用序号、收据、有限重发和 Tick 队列，死亡重生等关键结果使用 ACK、去重和生命版本。当前是服务器权威状态同步，不是严格帧同步，也仍保留服务器地图碰撞等后续边界。
