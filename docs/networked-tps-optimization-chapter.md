# 联机第三人称射击第二章：工程化优化与项目进阶计划

> 本文档承接《第三人称联网射击游戏递进开发任务书》。第一章已经完成一个可运行、可验证、能解释同步原理的联机 Tank 对战 Demo；第二章不急着堆新名词或模仿商业项目，而是将现有成果整理为一个结构清楚、可测试、可扩展、面试时真正讲得明白的工程化项目。

## 0. 第一章结项

### 已完成的能力

当前项目已经具备一个小型服务器权威状态同步对战游戏的完整闭环：

- Unity 双客户端通过 UDP + JSON 连接 .NET 服务器。
- 客户端只上报移动、转向、瞄准、开火等输入；服务器以固定逻辑帧（Tick）模拟权威位置、血量、死亡和重生。
- 服务器广播世界快照；本地玩家使用预测、输入重放与平滑校正，远端玩家使用快照缓冲、插值和短时状态维持。
- 开火、命中、扣血、死亡和重生由服务器裁决，客户端只负责即时表现和状态展示。
- 服务端维护短时历史状态，在即时射线（hitscan）射击时回看过去的位置，完成学习版射击延迟补偿。
- 运行时调试面板可观察往返延迟（RTT）、快照丢失估算、插值缓冲、预测误差、修正次数、逻辑帧和延迟补偿信息；已完成弱网测试。

### 第一章的定位

第一章的目标不是“商业级完整游戏”，而是证明你真正理解了服务器权威状态同步的主链路：

```text
本地输入
  -> 输入包
  -> 服务器固定逻辑帧模拟
  -> 权威世界状态
  -> 快照 / 战斗事件
  -> 本地预测校正、远端插值、表现层展示
```

这条链路已经是作品集最重要的技术主体。第二章不会推翻它，而是让它在功能变多时仍然站得住。

### 当前可接受的简化点

这些不是“错误”，而是第一章为了学习效率做出的明确取舍：

- 服务器代码仍集中在较少文件中，网络、模拟和快照职责尚未完全分离。
- 消息采用 JSON，易读但不适合高频、大规模正式线上同步。
- 快照默认向所有客户端广播，尚未按玩家视野、距离或带宽预算分别构造。
- 关键事件还没有完整的确认、重发与去重闭环。
- 延迟补偿使用客户端估计的往返延迟与插值延迟，并有服务端回退上限；时间同步和服务端独立延迟估算仍可加强。
- 命中检测仍是简化的平面射线/圆形命中半径；revision 4 已接入静态墙体遮挡并等待用户手动验收，但尚未接入真实炮塔模型、动态遮挡历史或骨骼 HitBox。移动侧的版本化二维地图碰撞已在 16.2 完成双客户端与弱网验收。
- 尚未做断线重连、房间、匹配、账号、云部署和复杂反作弊。

第二章的任务，就是有选择地把其中最有价值、最容易讲清楚的部分升级掉。

## 1. 第二章的最终目标

第二章完成后，项目希望达到以下定位：

> 一个采用服务器权威逻辑帧模拟、分层同步管线和可观测网络调试体系的联机第三人称射击技术 Demo。它不是生产级 MMO 或完整商业射击游戏，但能够展示你对权威模拟、快照复制、事件可靠性、延迟处理、性能取舍与工程化重构的理解。

你在面试中可以这样描述第二章的价值：

> 在完成基础服务器权威状态同步后，我将服务端重构为独立的权威世界模拟核心、网络收发层和状态复制层。网络层只负责消息收发，游戏规则集中在逻辑帧驱动的 `GameWorld` 中；再逐步实现按客户端构造快照、事件去重与可靠补偿、同步数据压缩实验、弱网自动化验证，从“能跑的网络 Demo”推进到“可验证、可演进的网络游戏原型”。

### 不把第二章做成什么

- 不为了术语强行实现完整帧同步 `GameCore`。
- 不一开始就上 ECS、反射消息框架、依赖注入、复杂泛型或分布式微服务。
- 不为了“商业级”一次塞入账号、匹配、排行榜、支付、热更新等与同步核心无关的系统。
- 不承诺高并发或上线级反作弊能力；性能结论必须建立在实际测量结果上。

这不是降低标准，而是把精力用在一个实习项目真正有含金量的地方。

## 2. 贯穿第二章的四条设计原则

### 2.1 权威规则只在服务器世界中改变状态

客户端可以说“我按了 W”“我要开火”“我看到自己立刻动了”，但不能直接决定最终位置、命中、血量或重生。

第二章要把这条原则落实到代码边界：任何会修改权威状态的规则，都通过 `GameWorld` 的逻辑帧或明确的游戏命令执行。`UdpClient`、JSON、Unity `Transform` 都不应该成为权威规则的一部分。

### 2.2 按数据流和职责划分，而不是按文件名或代码种类硬切

不要建立一个“快照管理器”，把输入接收和快照发送都塞进去，只因为它们都与网络状态有关。两者的数据方向与职责不同：

```text
客户端输入：Client -> Server，表达意图。
服务器模拟：Server 内部，产生权威结果。
状态快照：Server -> Client，复制当前结果。
战斗事件：Server -> Client，表达刚刚发生的事实。
```

模块的边界应围绕这些职责建立。一个模块可以处理多种数据，只要它们共同服务于同一个职责；例如 `GameWorld` 同时处理移动输入、开火命令和重生，是因为它们都在改变世界规则。

### 2.3 每次优化都回答“解决了什么问题，代价是什么”

例如，把 JSON 替换为 MessagePack 不是天然升级，而是用可读性和调试便利换取更小包体与更低序列化开销。没有测量到问题前，就先记录为候选项，不要抢跑。

每个阶段都应留下四项记录：问题现象、旧方案、选择的新方案、测试结果与代价。这会让项目从“我用了某技术”变成“我做出了工程判断”。

### 2.4 先保持行为不变，再优化结构；先测量，再优化性能

第一轮重构的验收不是新增功能，而是双客户端行为、协议字段、预测、插值、开火和延迟补偿全部保持正常。结构稳定后，再逐步升级协议、快照策略和可靠性。

## 3. 术语使用与项目边界

第二章会使用工业界常见术语，但每一个术语都必须对应可运行的代码、可观察的指标或明确的实验结论。术语不是简历装饰品。

| 标准术语 | 通俗理解 | 本项目的落地边界 |
| --- | --- | --- |
| **Incremental Refactoring**（增量重构） | 分小步调整内部结构，每一步都保持游戏可运行 | 先抽离权威世界核心，不重写协议和客户端 |
| **Authoritative Simulation Core**（权威模拟核心） | 服务器唯一决定世界规则的纯逻辑区域 | `GameWorld` 不依赖 UDP、JSON、Unity 表现层 |
| **Command Timeline**（命令时间线） | 按输入逻辑帧管理客户端意图，处理乱序和重复 | 有界输入缓冲、去重、过期拒绝，不做 lockstep 等待 |
| **Validation Gate**（权威校验门） | 服务器在命令影响世界前的合法性检查 | 移动范围、死亡状态、冷却、时间窗口、地图碰撞 |
| **Reconciliation**（状态校正） | 客户端把预测状态重新对齐服务器权威状态 | 已有回滚重放；后续标定软/硬校正阈值 |
| **Jitter Buffer**（抖动缓冲） | 暂存几份快照后再平滑播放，吸收网络抖动 | 已有远端快照缓冲；后续只做参数调优与指标化 |
| **Per-Client Replication**（按客户端状态复制） | 每个客户端收到的世界状态可以不同 | 由 `ClientReplicator` 选择实体和字段 |
| **AOI / Interest Management**（兴趣管理） | 只同步客户端当前真正需要关心的实体 | 先做距离兴趣管理；视锥裁剪是可选第二版 |
| **Delta Compression**（增量/差分复制） | 只发送相对基线发生变化的数据 | 先实现字段掩码和基线确认，再测量收益 |
| **Quantization / Bit Packing**（量化/位打包） | 用更少位表示坐标、角度和布尔状态 | 仅在二进制协议实验中实现，不对 JSON 硬做伪压缩 |
| **Reliable Event Ledger**（可靠事件账本） | 关键事件可确认、有限重发、重复不重复执行 | 只覆盖死亡、重生、结算等少数关键事件 |
| **Network Chaos Lab**（弱网混沌实验） | 主动制造延迟、抖动、丢包和乱序做验证 | 基于已有调试面板形成可重复测试预设 |
| **Checkpoint Replay**（检查点回放） | 从保存的权威状态和命令记录复现某段对局 | 服务端回放，不宣称客户端帧同步重演 |

以下概念会被记录为**远期研究项**，不进入本项目主线验收：多线程世界分片、跨服迁移、完整封禁系统、全量观战系统、局部帧同步混合架构。它们确实存在于大型项目，但需要更大规模实体、确定性逻辑、账号系统或运维基础才能合理落地。

### 候选技术的取舍卡

| 术语 | 是否进入第二章主线 | 原因与正确使用时机 |
| --- | --- | --- |
| **Entity Pooling**（实体对象池） | 条件进入 | 当前武器是即时射线，不需要大量权威子弹实体；若后续加入真实炮弹、特效或机器人，再分别为服务端实体和客户端表现对象做池化，避免频繁垃圾回收。 |
| **State Resync / Incremental Reconnect**（状态重同步/增量重连） | P2 候选 | 先完成事件账本后再做：重连时发送当前完整基线状态，再补齐基线之后的关键事件；小对局中全量基线本身并非坏事。 |
| **Spectator / Replay**（观战/回放） | 回放进入，观战候选 | 本项目先实现服务端检查点回放；自由视角观战需要额外的权限、兴趣管理和镜头逻辑，不必伪装成低成本功能。 |
| **World Partition / Sharding**（世界分区/分片） | 不进入主线 | 这是高实体规模或大地图服务端扩展方案。没有机器人压测数据时，多线程分区只会制造并发 Bug，不能证明承载能力。 |
| **Shared LogicCore / Hybrid Sync**（共享逻辑核心/混合同步） | 研究项 | 可以先让服务器战斗规则成为纯逻辑模块；但让客户端和服务器共同确定性模拟弹幕/AI，需要浮点确定性、随机数、版本一致和失步恢复设计，不能只因“帧同步”而接入。 |
| **Ban Pipeline**（封禁链路） | 不进入主线 | 当前可以做命令拒绝、违规计数和踢出房间；没有账号身份、持久化审计和后台治理，就不能声称具备封禁系统。 |

## 4. 目标架构：状态同步版的“服务器模拟核心”

帧同步中的 `GameCore` 强调所有客户端以相同输入重演同一套逻辑。你的项目是状态同步，不需要让客户端运行完全相同的权威世界；更适合的对应物是：

> 服务器独占运行一个不依赖 UDP、JSON、Unity 的权威世界模拟核心。

目标依赖方向如下：

```text
Unity 客户端
  输入 / 显示
        |
        v
UdpGameServer -------------------------> ClientRegistry
收包、发包、逻辑帧驱动                  连接与 playerId 映射
        |
        | InputCommand / FireCommand
        v
GameWorld
玩家状态、移动、战斗、死亡、重生、历史状态
        |
        | 只读 WorldState
        +---------------------> SnapshotBuilder -> ClientReplicator -> UDP 发包
        |
        +---------------------> EventLedger -> 关键事件发送 / 确认 / 去重
```

最重要的约束：

- `GameWorld` 不知道 UDP 端口、`IPEndPoint`、JSON 字符串或 Unity `Transform`。
- 网络层不直接 `player.Position += ...`，它只把包转换为命令后交给 `GameWorld`。
- `SnapshotBuilder` 只读取世界，不修改世界。
- 表现层只平滑追赶逻辑状态，不反过来决定服务器状态。

这比“多拆几个文件”多出来的价值，是让同一段世界逻辑可以离线测试、回放、统计和复现。

## 6. 阶段 9：增量重构与权威核心抽离

### 为什么现在做

当前功能已经足够多：输入、逻辑帧、快照、开火、命中、死亡、重生、历史状态、统计。继续直接在一个 `Program.cs` 上加功能，会让“网络收发”和“游戏规则”互相缠绕，后续难以定位 Bug，也很难独立验证延迟补偿或战斗逻辑。

这里的“增量重构”指“小步、可验证地替换内部结构”：每抽出一个职责就编译、双客户端验收一次，而不是开一个大分支重写服务器。当前不需要引入复杂的双实现长期并行方案。

### 要做什么

保持协议与游戏表现不变，只调整服务器内部边界。第一轮不追求几十个文件，建议控制在以下六类：

| 文件/模块 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `Program.cs` | 读取配置，启动服务器，处理退出 | 游戏规则、消息细节 |
| `UdpGameServer.cs` | UDP 收发、消息路由、逻辑帧循环、调用复制层 | 直接修改玩家位置/血量 |
| `ClientRegistry.cs` | `playerId`、昵称、`IPEndPoint`、连接/超时状态 | 移动、命中、快照内容 |
| `GameWorld.cs` | 玩家状态、输入消费、移动、战斗、死亡、重生、历史状态 | JSON、UDP、客户端地址 |
| `SnapshotBuilder.cs` | 从 `GameWorld` 的只读状态构建 `WorldSnapshot` | 世界模拟、发送网络包 |
| `Messages.cs` | 输入、快照、事件等 DTO 与协议字段 | 业务处理 |

### 一个关键例子

重构前可能是：

```csharp
// 收到 PlayerInput 后，在网络收包函数里直接改位置。
player.Position += move * speed * deltaTime;
```

重构后应该是：

```csharp
// 网络层：只转换输入并交给世界。
world.ReceiveInput(playerId, inputCommand);

// 逻辑帧中：世界统一消费输入并推进一帧。
world.Tick(tickDeltaTime);
```

这样做以后，即使以后 UDP 改成 LiteNetLib，或 JSON 改为 MessagePack，移动规则也无需重写。

### 验收标准

- `dotnet build` 通过。
- Unity 客户端的既有协议字段不改变，双客户端仍可连接并正常战斗。
- 预测、插值、死亡重生、延迟补偿和调试统计保持原有行为。
- 可以只创建 `GameWorld`，不启动 UDP，也能手动推进逻辑帧并检查玩家位置、血量、死亡状态。
- 每个新文件都能用一句话解释“它拥有的数据”和“它不应该做的事”。

### 暂不做

- 不立即拆出 `MovementSystem`、`CombatSystem`、`RespawnSystem` 等更细系统。
- 不引入 ECS、事件总线、依赖注入框架或反射分发。

这些留到 `GameWorld` 真正变大以后再做；第一轮先把错误的依赖方向切开。

## 7. 阶段 10：命令时间线与权威校验门

### 解决的问题

UDP 包可能迟到、乱序或重复到达。现在“保存最新输入”对小 Demo 足够，但随着开火、不同输入逻辑帧、弱网测试增多，服务器需要更清晰地知道：哪一份输入属于哪个时间点、是否过旧、是否重复、是否可信。

### 核心思想

将客户端输入统一转换为 `InputCommand`，放入每个玩家有限长度的命令队列。服务器每个逻辑帧按规则取出合适的命令推进世界。

```text
网络包到达顺序：  101 -> 103 -> 102 -> 103
服务器命令缓冲：  按 inputTick 记录，重复 103 丢弃
服务器逻辑帧：     在可接受窗口内消费命令，过旧命令拒绝
```

这不是严格帧同步：客户端无需等待所有玩家的同一帧输入，服务器仍然独立权威推进。它只是给状态同步增加一条清楚、可验证的输入时间线。

### 具体任务

- 为每个玩家保存有限长度的输入缓冲，按 `inputTick` 去重与排序。
- 定义输入接受窗口，例如过旧输入丢弃、未来过远输入暂存或限制。
- 统一输入合法性校验：玩家是否存在、是否存活、数值是否有限、移动轴是否在范围内、瞄准向量是否合理、开火冷却是否结束。
- 为被拒绝的输入记录原因和统计计数，不必一开始全部发回客户端。
- 将 `FireRequest` 也经过明确的校验门，再进入战斗规则。
- 在调试面板或服务器控制台增加：重复输入、过期输入、非法输入、被拒绝开火的数量和原因。

### 加入状态校正策略参数化

第一章已实现预测回滚和软/硬修正。第二章不需要再发明一套“滤波器”，而是把现有策略从散落常量整理为可观察的“误差预算校正”：

- 小误差：逻辑层完成确认输入后的重放；表现层在限定时间内平滑追赶。
- 大误差、复活、碰撞失败：逻辑层直接回到权威位置，再重放未确认输入。
- 远端实体：保持既有抖动缓冲插值；短时断档可有限外推，超过时限停止外推并等待快照。
- 将软/硬修正阈值、最大平滑时间、插值延迟记录到调试面板，结合往返延迟观察，而不是凭感觉调数值。

不建议把“高延迟时关闭本地预测”作为默认策略。对玩家自身而言，关闭预测通常会让操作明显失去跟手；更合理的是限制校正幅度、提高插值缓冲、收紧服务器校验，并在极端网络状态下给出网络质量提示。

### 可替代方案

- 继续只保留“最新输入”：代码最简单，但无法细讲乱序、重复和输入边界。
- 完整 lockstep 帧同步：一致性更严格，但需要等待与追帧机制，明显超出当前状态同步项目目标。

### 验收标准

- 人为发送重复或乱序的输入逻辑帧，不会让角色多移动或倒退。
- 极端移动值、NaN、死亡后开火等请求不会改变权威状态。
- 日志能解释服务器为何接受或拒绝一条命令。
- 正常弱网下操作表现不比第一章明显变差。

## 8. 阶段 11：按客户端状态复制管线

### 为什么不是“所有人一份全量快照”

现在房间只有两辆坦克，向所有人广播完整 `WorldSnapshot` 很合理。假如以后有 16 名玩家，每秒 20 次快照，每次都复制所有玩家的全部字段，带宽与序列化成本会随着人数快速增长。

第二章不需要真的支撑几百人，但可以搭建一条正确的复制管线：服务器先决定“这个客户端此刻需要知道什么”，再构建和发送它的快照。

### 具体任务

- 新建 `ClientReplicator` 概念：每个连接拥有自己的复制状态，而不是单纯全局广播一个 JSON。
- `SnapshotBuilder` 从 `GameWorld` 读取所有权威状态；`ClientReplicator` 决定发送给某个客户端哪些玩家、哪些字段、以什么频率发送。
- 引入实体优先级和同步频率分级：始终发送自己；近处或交战中的远端玩家高频发送；远距离、静止或低重要性实体低频发送。
- 将“发送频率”和“服务器模拟逻辑帧”分开配置。例如服务器仍以 30 Hz 模拟，快照以 15 或 20 Hz 发送。
- 对本地玩家和远端玩家区分字段优先级：自己需要确认输入逻辑帧、生命状态等；远端重点是位置、朝向、动画/战斗状态。

### 预留基线与差分复制接口

全量快照是最简单也最稳妥的第一版。实体多起来后，再让每个 `ClientReplicator` 记录“该客户端已经确认的上一份实体状态”，以此构造差分：

```text
基线状态：位置、朝向、血量、存活。
本帧变化：只有位置变化。
发送内容：entityId + changeMask(Position) + 新位置。
```

- 第一版先实现 `changeMask`（字段变化位掩码）与全量回退开关。
- 第二版增加 `baselineTick` 与客户端确认；基线未知、过期或客户端重连时发送全量状态。
- 差分只用于状态复制，不能代替死亡、重生等关键事件。

不要在没有“基线确认”时直接依赖 UDP 上一包作为差分基线。上一包可能丢失，客户端会无法正确还原状态；这也是差分同步比“少发几个字段”更需要设计的地方。

### 这一步与兴趣管理的关系

`ClientReplicator` 是结构，兴趣管理是它将来可使用的一种规则。先把“按客户端构建”做出来，再加距离过滤，避免在全局广播代码里硬塞 `if`。

### 验收标准

- 两名玩家时，表现和第一章一致。
- 服务器日志可以显示每个客户端的快照玩家数、字节数和发送频率。
- 可以通过一个开关对比全量快照与距离过滤快照。
- 客户端未收到远端状态时，能正确移除/冻结对应表现对象，不产生残影或异常瞬移。

## 9. 阶段 12：可靠事件账本

### 要区分“状态”和“事件”

位置快照丢一两包通常没关系，下一份更新会覆盖它；死亡、重生、击杀、房间结束则不能悄悄丢失。

```text
状态快照：可丢、可覆盖、以最新为准。
关键事件：必须最终到达，重复到达也不能重复执行。
```

### 具体任务

- 为关键事件增加 `eventId` 与 `serverTick`。
- 客户端维护最近处理过的事件 ID，重复收到时只确认、不重复播放伤害或重生表现。
- 客户端发送 `EventAck`，确认已处理到的事件 ID。
- 服务端为每个客户端维护短期“待确认事件账本”，超时后有限次数重发。
- 区分事件等级：
  - 不可靠即可：枪口火焰、普通 `FireEvent`。
  - 需要最终到达：死亡、重生、击杀、结算。
  - 以快照兜底：血量和存活状态，即使事件丢失也能被下一帧状态修正。
- 增加事件重发次数、重复事件数量、确认延迟等调试指标。

### 阶段 11 完成后的实施前提与注意事项

阶段 11 已提供按客户端构建快照、距离过滤、频率分级和客户端复制范围清理；阶段 12 必须在这条既有状态管线上增加**独立的关键事件账本**，而不是把可靠语义塞回 `WorldSnapshot` 或让快照等待事件确认。

建议按以下顺序实施：

1. 为死亡、重生等关键事实定义带 `eventId`、`serverTick` 和明确事件类型的网络 DTO；普通枪口火焰继续保持不可靠。
2. 服务端按客户端维护短期未确认事件列表。每个客户端的事件发送、确认、重发计数必须相互隔离，不能重新退化为一次全局广播后就认为已送达。
3. 客户端以有界的最近事件 ID 集合去重：首次收到时播放/应用，重复收到时只回 `EventAck`，绝不重复播放致命表现或重复结算。
4. 收到 `EventAck` 后才从该客户端的待确认账本删除事件；超过重发间隔且未超过次数上限时重发，达到上限时记录失败指标而不是无限重发。
5. 保持快照独立、可覆盖且不等待确认。血量和存活状态仍由快照兜底；事件用于保证死亡/重生等“发生过一次”的语义最终可见。

开始阶段 12 前必须明确以下边界：

- `ClientGoodbye` 和客户端超时是连接/成员生命周期处理，不是可靠战斗事件账本的替代品；不要把它们伪装成已确认的游戏结算事件。
- 当前 `changeMask` 与 `isFullState` 仍是无确认基线下的全量回退接口。阶段 12 不应提前实现基于上一 UDP 包的状态差分；`baselineTick` 与基线确认应留给后续状态压缩工作。
- 现有 `HealthChangedEvent` 同时承载普通伤害反馈和死亡/重生状态。实施时应按事件等级明确拆分或标记：普通命中表现可以不可靠，死亡/重生必须进入账本；权威血量/存活状态始终由快照兜底。
- 验收必须在可控丢包、重复和乱序下进行：关键事件最终一致且不重复执行；普通快照仍按当前频率流动，远端插值和复制范围清理不能因可靠事件重发而卡住。

阶段 12 完成后，服务端日志至少应能按客户端查看：待确认事件数、重发次数、重复事件数、确认延迟、超过重发上限次数；客户端调试面板至少应能查看最近已处理事件数和重复事件丢弃数。

### 为什么不直接改用 TCP

TCP 的可靠有序特性很适合登录或聊天，但把高频移动和关键战斗事件全部塞进 TCP，容易让旧包阻塞新状态。当前选择是在 UDP 上只为少量关键事件补一层轻量可靠机制，既能理解差异，也符合实时游戏的消息分级思路。

### 验收标准

- 在模拟丢包下，死亡/重生最终在两个客户端一致显示。
- 重复事件不会重复扣血、重复死亡或重复生成表现。
- 普通快照仍不会因等待可靠事件而卡住。

## 10. 阶段 13：序列化基准与快照压缩

### 先做测量基线

- 每秒发送、接收的字节数与包数。
- JSON 序列化/反序列化耗时。
- 2、4、8、16 个模拟玩家时的变化。

### 推荐升级路线

1. 保留 JSON 协议作为可读基线和调试模式。
2. 选择一个 C# 友好的二进制序列化方案做对照实现。
3. 在同一批消息、同一频率、同一玩家数量下比较包体、耗时、代码复杂度。
4. 只有收益足够清楚时，再将运行模式切换到二进制协议。

### 压缩技术的正确落地顺序

差分复制、量化和位打包都属于快照压缩，但解决的问题不同，推荐按以下顺序做：

1. **字段级差分复制**：依赖阶段 11 的 `baselineTick` 和 `changeMask`，不变字段不发送。
2. **定点量化**：为已知地图范围选择精度。例如将位置映射为整数网格、将角度映射为 `ushort`；必须写清楚可表示范围和误差上限。
3. **位打包**：将存活、开火、受击等少量布尔状态压入位掩码；仅在二进制序列化后才真正节省传输字节。
4. **发送抑制**：位置变化小于量化精度时不发该字段，客户端继续通过插值播放；需有最大静默时间，避免状态长时间不刷新。

JSON 文本里即使把多个布尔拼成数字，字段名与标点仍会占用大量空间，收益有限。因此 JSON 阶段重点是建立正确的字段模型和测量工具；真正的量化/位打包应放在 MessagePack、Protocol Buffers 或自定义二进制实验中验证。

### 方案选择建议

| 方案 | 优点 | 代价 | 本项目建议 |
| --- | --- | --- | --- |
| JSON | 易读、调试方便、现有实现可用 | 包大、字段名重复、性能一般 | 保留为学习/调试基线 |
| MessagePack | C# 易接入，体积和速度通常较好 | 字段顺序/兼容性需要管理 | 推荐第一候选 |
| Protocol Buffers | 成熟、跨语言、协议定义规范 | `.proto` 与代码生成增加学习负担 | 可作为对比或第三版 |
| MemoryPack | C# 内性能突出 | 跨语言与版本演进理解成本更高 | 有余力再尝试 |
| 自定义二进制 | 最可控 | 最难调试、最易出错 | 不建议作为当前主线 |

### 验收标准

- 有一张真实记录表，而不是只写“二进制更快”。
- 同一份 `WorldSnapshot` 在 JSON 与候选协议下可以正确往返序列化。
- 客户端协议升级不改变上层预测、插值和事件逻辑。
- 能清楚说出新方案的收益以及放弃 JSON 可读性的代价。

## 11. 阶段 14：兴趣管理与复制预算

### 什么时候值得做

只有你已经能让 4 到 8 个玩家或机器人同时存在时，这一步才会显得真实。两辆坦克时做兴趣管理，技术上可以做，展示上却像在解决不存在的问题。

### 核心思想

服务器不能把每一份数据以相同频率、相同精度发送给每一个客户端。它需要在有限带宽预算内优先传递“对当前玩家最重要的信息”。

简单优先级示例：

```text
自己：每次快照都发送，包含确认输入逻辑帧和完整生命状态。
近处、正在交战的敌人：高频发送，位置/朝向优先。
较远玩家：低频发送，必要时简化字段。
不可见或极远玩家：暂不复制，或只保留粗略状态。
关键事件：独立可靠通道，不被快照预算挤掉。
```

### 实现路线

- 第一版：距离兴趣管理。仅复制一定半径内的玩家。
- 第二版：频率分级。近、中、远实体使用不同快照频率。
- 第三版：视锥兴趣裁剪。服务器根据自己的权威角色朝向、固定视角和近远距离，进一步降低“身后且很远”实体的优先级。
- 第四版：每个客户端每逻辑帧有字节预算，`ClientReplicator` 按实体优先级挑选内容，即复制预算。
- 进阶：用均匀网格（spatial hash/grid）查询附近实体，避免每个玩家都遍历所有其他玩家。

这里的“视锥裁剪”是**服务器侧的近似兴趣规则**，不是相信客户端告诉服务器“我屏幕上看到了什么”。对于第三人称相机，还要注意它能看到角色背后或侧方，因此第一版更推荐距离兴趣管理；视锥只能作为带滞后时间的优化条件，不能让正在交战、刚受击或被锁定的敌人突然消失。

真正基于墙体的可见性裁剪属于视线/遮挡裁剪，需要服务端拥有地图空间数据并频繁做射线检测，成本高于距离兴趣管理。本项目把它放到阶段 16 的可选实验，不将其当作主线硬目标。

### 不宜过早做的内容

- 复杂四叉树、八叉树、动态遮挡剔除。
- 多地图分区、跨服兴趣管理、海量实体管理。

对于你的项目，一个清楚的距离兴趣管理加优先级发送，已经足够有说服力。

### 验收标准

- 使用 8 个以上模拟玩家时，距离过滤能降低每客户端快照实体数与字节数。
- 玩家重新进入范围后，客户端能平滑创建/恢复远端实体。
- 近处目标仍保持更好的同步频率和观感。
- 调试面板可展示兴趣范围、当前关注实体数、跳过实体数、快照预算使用量。

## 12. 阶段 15：弱网混沌实验与检查点回放

### 已有基础

第一章已经做过人工弱网测试和调试面板。第二章要把它从“一次演示”升级为“可重复验证的实验”。

### 具体任务

- 预设网络方案：`LAN`、`100ms`、`200ms`、`100ms + 抖动`、`100ms + 1% 丢包`。
- 记录每套方案下的往返延迟、快照缺失估算、预测误差、修正次数、插值缓冲长度、事件重发次数。
- 为服务器增加轻量命令日志：记录某段时间内的输入命令、关键事件和逻辑帧。
- 每隔固定逻辑帧保存一个世界检查点（玩家状态即可，不需要完整存档）。
- 提供开发用回放入口：从检查点读取后重放一段命令，验证关键状态是否能复现。

### 内置弱网模拟的边界

现有外部工具适合第一轮观察；后续可在客户端网络层加入仅供开发使用的内置弱网模拟器：发送/接收包先进入延迟队列，再按配置注入丢包、抖动、乱序和重复包。这样可以在不影响整台电脑网络的情况下复现实验。

这套工具只应改变网络包到达时间和是否投递，不能修改游戏规则。每次测试需要记录随机种子或固定配置，才能称为可重复的弱网混沌实验。

### 为什么回放有价值

这不是把项目改成帧同步。它是为了回答一个工程问题：

> 某个弱网 Bug 出现时，我能否保存当时的输入与状态，然后在不连 Unity 客户端的情况下复现服务器的判定？

它与 `GameWorld` 解耦后可独立运行的价值直接相连，也是“服务器模拟核心”最有说服力的展示之一。

### 验收标准

- 能在项目文档中展示至少三组弱网结果，而不仅是口头描述。
- 某段录制的命令在回放后，关键位置/血量/死亡结果与原始记录一致或差异可解释。
- 指标能帮助你判断问题更偏向网络丢包、客户端预测还是服务器规则。

## 13. 阶段 16：服务端空间校验

状态：**16.0--16.2 已完成；16.3 revision 4 已完成代码、自动测试、服务器/Unity 编译和协议冒烟，等待用户手动验收；16.4--16.5 尚未开启。** 用户已于 2026-08-22 完成 revision 3 的双客户端及 100--200 ms 弱网验收，联网权威移动碰撞正式完成。revision 4 新增共享静态空间查询、墙体优先射击裁决、合法出生/重生选择和查询遥测。具体范围与测试矩阵见 `docs/stage-16-authoritative-collision-and-3c-foundation.md`，实现记录见 `docs/stage-16-0-collision-core-implementation.md`、`docs/stage-16-1-tank-static-collision-implementation.md`、`docs/stage-16-2-authoritative-prediction-collision-implementation.md` 和 `docs/stage-16-3-gameplay-space-query-implementation.md`。

### 为什么它属于网络优化篇

加入地图不只是“让大平地好看”。一旦存在墙体、掩体和遮挡，服务器必须拥有与客户端一致的基础空间规则，否则会出现“客户端看到墙后，服务器仍判定命中”或“客户端绕过障碍，服务器穿墙”的问题。

服务器使用自己的碰撞形状和空间查询验证移动与射击，而不是相信客户端说“我没有穿墙”或“我看见了目标”。它是反作弊的基础校验层，不等于完整反作弊产品。

### 重新规划后的递进实现方式

1. **16.0 碰撞数学实验（已完成）**：已实现并测试 AABB、OBB、Circle、Ray、二维投影与 SAT，并提供可选调试 Gizmo；尚未修改联网移动。
2. **16.1 Tank 二维静态碰撞（已完成离线/纯模拟层）**：Tank 使用二维 OBB，静态墙体使用 AABB/OBB；已实现有限子步、宽相/窄相、穿透修正、滑墙、旋转拒绝、世界边界和安全上限，但尚未接入联网推进。
3. **16.2 权威与预测闭环（已完成）**：服务端固定 Tick 和客户端即时预测/未确认输入重放使用同一地图与命令语义；联网 Tank Rigidbody 仍保持 kinematic。动态物块冲突已通过显式联网冻结和无物理推力子弹隔离；30 Hz/50 Hz外层调用都拆为150 Hz内部命令微步，并由障碍接触自动测试固定一致结果。用户已完成正常网络、双客户端及 100--200 ms弱网验收。
4. **16.3 战斗空间查询（revision 4 已实现，待手动验收）**：服务器分别比较最近静态墙距离与历史玩家圆表面距离，墙更近时不扣血；出生与重生按候选顺序校验世界边界、静态占用和存活玩家占用。共享 `TankMapQueries2D` 提供 Ray、Circle/OBB overlap 与边界语义；自动测试、编译和版本握手冒烟已通过。用户验收后当前 Tank 阶段收口。
5. **16.4 人物移动碰撞**：实际 3C 出现后再加入 Capsule、地面探测、斜坡、台阶、贴地、跳跃和冲刺 Sweep。
6. **16.5 骨骼 HitBox**：人物模型与动画稳定后，再用 Sphere/Capsule/OBB 组成骨骼 HitBox，并明确其服务端权威与历史回溯语义。

当前网络项目可以在 3C 前完成的是 16.0--16.3。16.4 和 16.5 是后续人物阶段的正式接口，不在没有角色 Motor、坡道和骨骼模型时提前制造空实现。

### 三层服务端校验门

- **移动校验**：单逻辑帧最大位移、速度上限、边界和障碍碰撞；异常时丢弃命令或回到最近权威位置。
- **开火校验**：玩家存活、冷却、合法射线起点/朝向、回溯窗口上限，以及射线是否先撞到墙体。
- **时序校验**：`inputTick` 与服务器当前逻辑帧的可接受窗口、重复输入和未来输入限制，防止补发很久以前的操作影响当前判定。

处理策略分级保持克制：第一次异常记录并拒绝或校正；重复异常可踢出当前房间。没有账号、UID、持久化审计和后台人工流程时，不应声称实现了“封禁系统”或完整反作弊闭环。

### 可替代方案

- 只重新开启 Unity Rigidbody 碰撞：本地表现会先停住，但服务器仍穿墙，预测与权威再次分叉，不能采用。
- 服务器直接复用 Unity Physics：需要迁移到 Unity Headless/Dedicated Server，会改变现有独立 .NET 服务器和测试边界，当前不采用。
- 引入第三方物理库：能获得更多形状和动态刚体能力，但增加映射、部署和学习成本；当前先完成纯 C# 玩法碰撞子集。
- 自己实现完整刚体物理引擎：会扩展到冲量、摩擦、角动量、堆叠和约束，超出项目目标。

### 验收标准

- 纯数学查询有分离、接触、重叠、旋转、边界和容差自动测试。
- Tank 正面撞墙停止、斜向撞墙滑动、持续顶墙不抖动或渗入，有限子步下不能跨过训练场薄墙。
- 客户端无法仅靠本地修改位置穿过服务器定义的边界或障碍。
- 客户端即时预测、权威快照和未确认输入重放在同一地图版本下使用一致碰撞规则。
- 墙后目标不能被服务器射线直接命中；延迟补偿目标也先受静态墙遮挡。
- 出生和重生不会落入静态墙体；地图版本不一致时明确报错。
- 地图能让双客户端对战产生掩体、绕侧和出生点，而不只是大平地互射。

## 15. 阶段 18：独立服务器运行化

### 先澄清：当前项目已经是独立服务器形态

UE 中常见的多人运行方式有两种：

```text
Listen Server（主机模式）
玩家 A：既运行客户端，也运行服务器权威逻辑
玩家 B：连接玩家 A

Dedicated Server（独立服务器）
玩家 A：纯客户端 ─┐
                  ├─> 独立服务器进程
玩家 B：纯客户端 ─┘
```

当前项目属于第二种：`.NET Server` 是单独启动的进程，两个 Unity 客户端都只发送输入、接收状态，不拥有最终游戏裁决权。因此它在**运行拓扑**上已经是独立服务器，而不是 P2P 或主机模式。

UE 的独立服务器通常是从同一 Unreal 工程编译出的无渲染服务端程序；你的项目是 Unity 客户端加独立 C# 服务端。两者的程序形式不同，但设计原则一致：服务器没有本地玩家、没有相机/模型/UI，不依赖表现层，独立维护对局世界。

### 为什么不现在就做

独立服务器不是在已有代码外面再套一个框架，也不是把服务器“拆成第三端”就自动更厉害。你已经有独立服务端进程；现在缺的是让它具备更完整的生命周期与运行边界。

若在阶段 9 前先做端口、房间和远程部署，网络、游戏规则和复制逻辑仍然混在一起，之后每项 DS 配置都会把复杂度带回 `Program.cs`。因此本阶段安排在服务器模拟核心、输入校验、事件可靠性、复制管线和基础地图规则稳定之后，作为第二章后段的架构整合任务。

### 阶段目标

将当前“本机运行的服务器控制台程序”整理成可独立启动、可配置、可观察、可承载一个或多个对局世界的学习版独立服务器。目标是理解 UE 独立服务器的架构思想，不是复刻 UE 引擎内部网络框架。

### 第一部分：服务端运行边界

- `Program.cs` 只负责读取启动参数、创建 `UdpGameServer`、处理进程退出。
- 支持最少量的命令行配置：端口、逻辑帧频率、最大玩家数、房间人数、日志级别。
- 用明确默认值保证双击/简单 `dotnet run` 仍可启动；命令行配置是扩展入口，不变成复杂配置系统。
- 服务器启动日志应清楚显示：监听地址、端口、逻辑帧频率、最大玩家数、当前房间数和运行模式。
- 客户端可配置服务器 IP，至少完成 `127.0.0.1` 与同一局域网 IP 的联调；远程公网部署作为可选展示项。

示例启动形式：

```text
dotnet run -- --port 7777 --tickRate 30 --maxPlayers 8
```

这里的价值不是命令行本身，而是让服务器不再把“开发者电脑上的固定常量”当作运行环境的一部分。

### 第二部分：对局世界与房间生命周期

第一章的 `GameWorld` 可以理解为“一局游戏世界”。独立服务器阶段让这个概念明确出来：一个服务器进程负责管理世界，一个世界负责一局对战。

第一版房间设计保持小而直白：

```text
独立服务器进程
  -> RoomManager
       -> Room "training-01"
            -> GameWorld
            -> ClientRegistry / ClientReplicator
```

- `RoomManager` 负责创建、查找、销毁房间，不处理移动、命中或快照字段。
- `Room` 持有一个 `GameWorld`，负责这一局的玩家加入/离开、开始/结束和逻辑帧生命周期。
- `GameWorld` 继续只关注权威规则，不知道房间名、网络地址或进程参数。
- 第一版可以只有一个默认房间；先写清楚接口和生命周期，再考虑真正多房间。
- 第二版才允许多个固定房间，例如 `training-01`、`training-02`；不做匹配、观战或跨房间迁移。

这一步和“拆文件”不同：它明确了**进程 -> 房间 -> 对局世界 -> 玩家**的所有权关系。以后你讲独立服务器时，可以说清楚服务器进程与单局 GameWorld 并不是同一个概念。

### 第三部分：无表现层、可恢复、可观测

UE 独立服务器的重要特点是没有渲染和本地玩家。你的独立 .NET 服务端天然满足这一点，后续应进一步保证：

- 服务端没有 Unity `Transform`、动画、特效、相机和 UI 依赖。
- 玩家断线后由服务器进行超时清理，并向房间其他玩家复制离开结果。
- 空房间在一段时间后可停止逻辑帧或销毁，避免无意义占用资源。
- 服务器能周期性输出每个房间的在线人数、逻辑帧耗时、快照字节数、事件重发数和命令拒绝数。
- 进程结束时能停止收包、停止逻辑帧并写出简短汇总日志；不要求持久化玩家账号数据。

### 第四部分：与 UE 思路对齐，但不盲目模仿

| UE 中的概念 | 本项目中的对应实现 | 当前是否需要完整复刻 |
| --- | --- | --- |
| 独立服务器构建 | 独立 .NET Server 控制台进程 | 已具备，无需改成 Unity Headless |
| GameMode / Match Rules | `Room` 的对局生命周期与 `GameWorld` 规则 | 做学习版即可 |
| GameState | 可复制的 `WorldSnapshot` / 房间状态 | 可逐步补充 |
| PlayerState | 服务器 `PlayerState`，快照复制到客户端 | 已具备，继续整理 |
| PlayerController | Unity 输入层 + 网络输入命令 | 不必照搬 UE 类名 |
| Replication Graph | `ClientReplicator` + 兴趣管理/复制预算 | 先做简化距离兴趣管理 |
| Server Travel / Session | 多地图、会话切换 | 当前不做 |

学习 UE 架构最有价值的是理解职责，而不是把类名改成 UE 的名字。你的代码应保持 C# 项目最自然、你自己最能解释的样子。

### 验收标准

- 可以独立启动服务器，再启动两个 Unity Build 客户端连接它；不依赖 Unity Editor 作为主机。
- 服务端参数可控制端口、逻辑帧频率和最大玩家数，日志可验证配置实际生效。
- 客户端可连接局域网地址；两台设备联调成功是加分项，公网部署不作为硬性要求。
- 客户端断开后，服务器会清理对应玩家，其他客户端不再保留幽灵坦克。
- 一个 `GameWorld` 只负责一局对战；即使第一版只有一个房间，代码边界也允许后续创建第二个世界。
- 预测、插值、事件、延迟补偿、地图碰撞等既有功能仍由各自模块负责，不因加入 `Room` 概念而混进启动代码。

### 面试时可以怎么讲

> 项目采用独立 C# 服务器，而非房主主机模式。服务端进程独立维护房间和权威 `GameWorld`，客户端只上报输入并接收状态复制。对局世界与 UDP 收发、客户端连接、快照复制职责分离，因此可以在不依赖 Unity 表现层的情况下运行、测试和扩展多房间能力。

这段话成立的前提是你完成了上面的边界和验收；因此它会是第二章很有分量的一部分。

## 17. 下一项实际任务：阶段 10 启动指令

下一次开始编码时，直接使用下面这段任务描述：

```text
请帮我开始第二章的阶段 10：命令时间线与权威校验门。

阶段 9 已完成第一轮服务端职责重构。现在以 GameWorld、UdpGameServer、ClientRegistry、SnapshotBuilder 和 Messages 的边界为基础，增强输入时序与服务端校验；不要重写阶段 9，也不要新增无关玩法。

目标：
1. 将客户端 PlayerInput 转换为 GameWorld 的 InputCommand，并为每名玩家维护有限长度、可去重的输入缓冲。
2. 按 inputTick 处理重复、乱序、过旧和过远输入；服务器仍独立按固定 Tick 推进，不做 lockstep 等待。
3. 将移动轴、瞄准数据、存活状态、开火冷却和 FireRequest 统一经过明确的服务端校验门。
4. 为接受和拒绝的输入/开火记录可观察的原因与统计，但第一版不必把所有拒绝原因发回客户端。
5. 保持现有 Unity 协议字段、预测、插值、开火、死亡重生和延迟补偿行为不变。

要求：
- 继续使用 UdpClient + JSON，以及清晰的 switch (messageType) 分发；第一轮不改为反射分发、复杂网络库或二进制协议。
- UdpGameServer 只负责把 DTO 转为命令和记录发送者身份，不能直接修改权威玩家状态。
- GameWorld 不依赖 UDP、JSON、Unity Transform 或 IPEndPoint；校验和规则必须在这里可离线测试。
- 优先复用现有 inputTick、requestTick 和服务端 Tick，不为“看起来高级”而新增没有测量价值的协议字段。
- 为缓冲长度、接受窗口和拒绝计数设置直白、可配置的常量，并说明每个数值解决的问题与代价。
- 每完成一个小改动先执行 dotnet build；完成后进行双客户端回归，重点测试重复/乱序输入、死亡后输入、开火冷却和正常弱网操作。
- 不引入 ECS、事件总线、依赖注入、反射分发或第二轮 MovementSystem/CombatSystem 拆分。
```

### 后续开发的共同约束

以下规则从阶段 10 开始持续适用，除非后续文档明确、带理由地修改它们。

1. **先解释，再实现。** 每项技术选择都记录：当前问题、旧方案、选定方案、常见替代方案、为何现在采用，以及测试结果与代价。优化不能只因为“看起来更高级”。
2. **优先直白代码。** 保持 `UdpClient + JSON`、显式 `switch (messageType)`、简单的 `if` 和小职责类；不为了抽象而引入反射、复杂泛型链、事件总线、ECS 或依赖注入。
3. **职责按数据流划分。** 网络层只收发和路由，`ClientRegistry` 只管理连接身份，`GameWorld` 只拥有权威规则，`SnapshotBuilder` 只读世界构造快照，表现层只显示和插值。一个模块不应跨过这些边界写入别人的数据。
4. **服务器始终权威。** 客户端只能表达输入、瞄准和开火意图；最终位置、命中、血量、死亡、重生和以后加入的动态物体状态都由服务器决定。客户端预测只改善本地手感，不能替代权威结果。
5. **本地与远端表现分工明确。** 本地角色优先本地输入与预测，远端角色优先快照缓冲与插值；服务器快照不能在本地转向或瞄准期间与表现脚本争抢同一个 Transform。出现抖动时先检查是否存在多个写入者。
6. **协议先稳定，演进要可测。** 默认保持已有 JSON 字段名和语义。确需改协议时，先说明兼容策略、客户端改动点和可观察收益；没有包体或 CPU 基线时，不提前改用二进制协议或位打包。
7. **只做代码修改。** 后续开发默认不直接修改 Unity Scene、Prefab、资源、组件挂载或 Inspector 配置；需要这些操作时由用户在 Unity 编辑器中完成，代码必须保留合理默认值并说明所需引用。
8. **增量验证，不做大爆炸重写。** 每个小步骤至少通过对应项目的构建；涉及网络行为时再做双客户端验证。记录已验证、未验证和已知限制，不能把“能编译”写成“已完成全部玩法验收”。
9. **不使用客户端假同步掩盖服务器缺口。** 服务器现在拥有 16.2 的共享二维静态移动障碍和 16.3 revision 4 的权威静态射击遮挡，但仍不运行 Unity Physics，也不拥有可推动物体状态；因此不添加只在本地生效的碰撞或推动补丁。动态对象模拟、历史与复制必须在对应后续阶段以权威方式实现。
10. **性能结论必须来自数据。** 日志、Network Debug 面板、弱网实验、包体大小、Tick 耗时和机器人压测优先于主观判断；任何阈值、频率、缓冲长度或压缩方案都要能解释其收益和代价。

## 18. 第二轮拆分的边界提示

只有在阶段 9 后 `GameWorld` 已经明显变大时，再按下面方式拆第二轮：

- `MovementSystem`：根据已校验输入推进位置和车身朝向。
- `CombatSystem`：开火冷却、命中检测、伤害与死亡触发。
- `RespawnSystem`：出生点选择、重生逻辑帧、状态恢复。
- `HistoryBuffer`：保存和查询延迟补偿所需的历史状态。
- `ServerTelemetry`：统计逻辑帧耗时、输入、快照、事件、拒绝原因。

判断标准不是“一个文件超过多少行”，而是：修改开火规则时，是否还必须理解移动、重生、网络统计的细节；如果答案是“必须”，则说明职责还可以继续分离。

# 第三章：角色表现升级与高阶网络研究储备

第三章在第二章的主线目标完成后启动。它有两条并行但不混淆的路线：一条让项目从“两个坦克的网络技术原型”升级为更完整的第三人称射击展示；另一条把当前过于超前的网络课题存成研究任务，等你具备足够基础、也确实有规模需求时再选择进入。

## 20. 第三章术语与总原则

| 首次英文术语 | 后续统一称呼 | 在项目中的含义 |
| --- | --- | --- |
| **Character, Camera, Controls (3C)** | 3C | 角色、相机、操作控制三者共同决定第三人称射击的操作手感。 |
| **Presentation Layer** | 表现层 | 模型、动画、相机、特效、音效和 UI；它追随逻辑层，不拥有权威规则。 |
| **Animation State Replication** | 动画状态同步 | 同步“跑、瞄准、开火、受击、死亡”等语义状态，不逐骨骼同步动画结果。 |
| **Authoritative Projectile** | 权威投射物 | 服务器生成并按逻辑帧推进的真实炮弹/子弹实体，命中时间由飞行过程决定。 |
| **Object Pooling** | 对象池 | 复用高频生成和销毁的炮弹、命中特效、远端实体表现对象，降低垃圾回收波动。 |
| **Bot Load Test** | 机器人压测 | 由程序生成虚拟玩家或输入，用来测量人数增长时的逻辑帧、带宽和 CPU。 |

第三章仍遵守同一条底线：逻辑层决定“发生什么”，表现层决定“看起来怎样”。换人物模型、动画和特效不能让客户端重新获得位置、命中或血量的最终决定权。

## 21. 阶段 19：角色、相机、操作控制与人物模型接入

### 目标

将 Tank 原型逐步替换为适合第三人称射击展示的人物角色，同时保持第一、二章的网络同步结构不被模型和动画反向绑架。

### 任务

- 选择一套来源清楚、允许作品集展示的人物模型和动画资源；记录来源与许可，不把资源质量误写成个人美术能力。
- 用独立的角色表现预制体替换坦克外观：模型、武器挂点、枪口点、受击点和名称/血量显示都属于表现层。
- 保留网络逻辑角色的简化碰撞体和位置；模型跟随逻辑角色平滑追赶，不能直接把动画根运动当作服务器权威位移。
- 完成最小 3C：第三人称相机跟随、肩射/瞄准视角、移动、转向、瞄准和开火手感。
- 为本地角色和远端角色分别设置表现策略：本地角色优先输入反馈，远端角色优先快照插值的稳定观感。

### 验收标准

- 同一局的两名玩家使用人物模型时，移动、瞄准、开火、受击、死亡和重生仍由既有服务器规则决定。
- 本地相机、武器模型和 UI 不会被网络快照直接拉扯。
- 远端角色的模型与逻辑位置之间的追赶关系可在调试模式下观察。

## 22. 阶段 20：动画状态同步与战斗表现对齐

### 目标

建立“同步状态，不同步骨骼”的动画同步方式，让角色模型看起来在正确地跑、瞄准、射击和死亡。

### 任务

- 从权威逻辑状态推导移动速度、是否瞄准、是否存活、最近开火时间等动画参数。
- 本地开火可立即播放枪口火焰、后坐力和音效；远端开火以服务器事件驱动表现。
- 使用服务器权威血量和死亡状态驱动受击/死亡动画；表现事件重复到达时不能重复播放致命效果。
- 不同步 Animator 的逐帧骨骼变换，也不把动画状态机的结果回写为服务器位置。

### 为什么值得做

动画状态同步会让你的项目从“网络逻辑正确”进入“网络逻辑与角色表现一致”。它同样是逻辑层与表现层分离的直接展示：同步的是少量语义状态，而不是高频、昂贵且容易失真的骨骼数据。

## 23. 阶段 21：小地图战斗空间与权威投射物（二选一递进）

这一阶段不要求立刻做真实炮弹。先根据你希望展示的战斗类型选择：

- **即时射线武器路线**：保留现有服务器回溯命中判定，把飞行子弹改为曳光、枪口火焰和命中特效，消除“子弹还没飞到、血量已扣”的视觉误解。
- **真实炮弹路线**：服务器生成权威投射物，按逻辑帧推进位置、检测地图/角色碰撞，并在命中时广播事件；客户端只做预测性表现或跟随服务器投射物。

选择真实炮弹路线后，再为服务端投射物和客户端特效加入对象池。对象池只解决频繁创建销毁的性能波动，不解决网络同步正确性；不要为了使用对象池而先把简单即时射线武器复杂化。

## 24. 阶段 22：重连重同步与对局恢复

这是第二章可靠事件账本和按客户端复制管线的自然延伸，适合在独立服务器运行化之后完成：

- 客户端重连时先收到当前完整世界基线，再恢复正常差分状态复制。
- 服务器补发基线之后仍有价值的关键事件，客户端以事件编号去重。
- 对于已过期的枪口火焰、普通受击表现，不追求补播；生命状态和存活状态以最新权威快照为准。
- 断线超时、保留角色时长、重连身份识别先做学习版规则；没有账号系统时不伪装成正式会话恢复。

## 25. 阶段 23：回放、观战与机器人压测

这一阶段的建议顺序是：先完成服务器检查点回放，再加入只读观战，最后做机器人压测。

- 回放：使用权威检查点、输入命令和关键事件复现服务器判定，重点用于问题复现和面试展示。
- 观战：观战客户端不发送玩家输入，只接收一个可配置兴趣范围内的状态和关键事件；可先做固定相机，再考虑自由镜头。
- 机器人压测：让虚拟玩家以可控输入进入房间，收集逻辑帧耗时、快照字节、事件重发、兴趣实体数和内存分配数据。

机器人压测的目标不是宣传“支持百人”，而是得到一张可信的规模曲线：2、4、8、16 个虚拟玩家分别带来多少 CPU、带宽和快照开销。这份数据会决定兴趣管理、量化压缩或空间网格是否真的值得继续做。

## 26. 第三章研究抽屉：暂不承诺实现的高阶课题

| 课题 | 为什么先记录 | 进入条件 |
| --- | --- | --- |
| 世界分区/分片与多线程逻辑 | 能提高大地图、大量实体的服务端扩展性，但会引入线程安全、跨区消息和状态所有权问题 | 已有机器人压测瓶颈，且理解锁、任务划分与并发调试 |
| 共享逻辑核心与混合同步 | 高密度弹幕或大量 AI 可能减少状态复制量，但要求两端逻辑确定性和失步恢复 | 已将服务器战斗逻辑抽为纯模块，并能解释浮点、随机数和版本一致性 |
| 复制图与复杂空间索引 | 可进一步优化大量实体的兴趣筛选，但在十几名玩家前收益有限 | 距离兴趣管理已测到全量遍历或带宽瓶颈 |
| 完整观战、录像导出和慢放检视 | 展示效果好，但依赖可靠事件、回放数据和镜头系统 | 检查点回放稳定，且 3C 镜头已完成 |
| 账号、匹配、排行榜和封禁后台 | 属于产品服务与运维范围，不是网络同步项目的必要证明 | 想将项目扩展为完整线上服务时另开专题 |

第三章的原则是“从数据和实际玩法中选择一两个方向深入”，而不是把表格里的所有名词都做一遍。对你而言，优先完成 3C、动画状态同步、小地图和机器人压测，已经能让项目从技术 Demo 变成一个更完整、更有展示力的联机第三人称射击作品。
