# 阶段 11：按客户端状态复制管线

## 问题与旧方案

旧服务器每个逻辑帧构造一次完整 `WorldSnapshot`，并把同一段 JSON 广播给所有客户端。两人局可用，但玩家数量、快照频率和序列化成本会一起增长，也没有清晰的位置可插入兴趣管理规则。

## 本阶段方案

`GameWorld` 仍只负责权威模拟。`SnapshotBuilder` 只读 `GameWorld` 并产出完整的权威候选状态；每个 `ConnectedClient` 拥有一个独立的 `ClientReplicator`，由它决定该客户端的实体范围、实体优先级和发送频率。

```text
GameWorld --只读--> SnapshotBuilder --候选状态--> ClientReplicator (每连接一个)
                                                       |
                                                       v
                                           WorldSnapshot + UDP JSON
```

- 服务器逻辑与自身/高优先级快照默认均为 30 Hz，二者仍分别配置；低优先级实体默认 5 Hz。
- 自己始终随每份快照发送，保证输入确认帧、生命和重生状态可用于本地校正。
- 默认使用距离过滤；使用 `--full-snapshots` 启动服务器时，所有玩家每份快照都有完整状态，以保持第一章行为并便于对比。
- 距离过滤时：自身始终保留；18 米内或最近 30 个逻辑帧参与战斗的远端玩家高频；18–45 米的非战斗远端玩家低频（默认 5 Hz）；45 米外玩家不在该客户端复制范围内。
- 快照的 `replicatedPlayerIds` 表示当前客户端仍应保留的远端对象。低频实体即使本包没有状态更新，也留在该列表里，因此客户端不会因频率分级而错误销毁它。
- 远端插值延迟会根据相邻快照的实际服务器 Tick 间隔自适应。高优先级实体维持原本短延迟；5 Hz 低优先级实体使用约一个更新间隔的缓冲，代价是更高的视觉延迟，收益是不会在两包之间耗尽缓冲而保持/跳变。
- 客户端收到更新后的复制范围，会销毁范围外的远端对象，避免残影；旧服务器快照没有该字段时，客户端退回以 `players` 列表判断，兼容旧格式。
- 正常关闭 Unity 客户端会发送 `ClientGoodbye`，服务器立即从 `ClientRegistry` 与 `GameWorld` 移除该玩家；崩溃或断网时没有 UDP 断开信号，服务器以 8 秒无收包超时移除。移除后的下一份快照会令其他客户端清理该远端头像。
- 本地预测在持续移动及输入结束后的 0.2 秒内不施加网络位置校正，避免 Rigidbody 预测与校正目标在点按操作时产生可感知的拉扯；平滑校正计数按一次连续校正过程记录，而不是按每份快照记录。

## 基线与差分预留

协议添加了每个实体的 `changeMask` 与快照 `isFullState`。当前 `isFullState=true`，每个已发送实体的 `changeMask=All`；这是安全的全量字段回退。

尚未实现基于上一 UDP 包的差分。原因是客户端还没有确认 `baselineTick`：若基线包丢失，后续差分无法还原。后续阶段应先增加基线确认、重连全量回退和过期基线处理，再让 `changeMask` 产生真正的字段节省。死亡、重生和命中仍由独立事件处理，绝不由差分状态替代。

## 取舍

没有引入 ECS、反射分发、二进制协议或客户端假同步。代价是每个状态更新仍发送完整 JSON 字段，且低频实体的 `replicatedPlayerIds` 有少量额外字节；收益是复制决策已按客户端隔离、调试清晰，并且不会建立在 UDP 未确认包之上。

## 联调中发现的问题与处理

| 现象 | 原因 | 处理与结果 |
| --- | --- | --- |
| 两名玩家即使相距很远，`Replication scope` 仍为 2。 | 初版将全量快照模式作为默认启动配置；直接执行 `dotnet run` 时，距离过滤本来没有启用。 | 改为距离过滤默认启用；只有显式传入 `--full-snapshots` 才使用全量模式。重启服务器后，距离超过 45 米时对应客户端的 scope 变为 1，远端对象被移除。 |
| 一个客户端直接关闭后，另一个客户端仍保留它的坦克，服务器 `players` 仍为 2。 | UDP 没有连接断开回调，旧 `ClientRegistry` 只注册连接，不维护最后收包时间，也没有从 `GameWorld` 删除玩家。 | 增加 `ClientGoodbye` 的正常退出路径与 8 秒静默超时兜底；两者都会从连接表和权威世界移除玩家。实测正常退出后服务端从 `players=2` 变为 `players=1`，另一端 scope 同步变为 1。 |
| 两名玩家相距约 30–45 米时，远端坦克出现保持、跳动或“闪烁”感。 | 该距离进入 5 Hz 低优先级档，状态间隔约 6 个服务器 Tick；原远端插值固定仅 3 Tick，缓冲会在下一包到来前耗尽。 | 根据相邻状态的实际 Tick 间隔自适应远端插值延迟。5 Hz 时活跃延迟约为 7 Tick：表现更滞后，但连续平滑。联调验收确认此距离区间已流畅。 |
| 本地移动时能感到轻微拉扯；延后校正后，`Smooth corrections` 又在松手时一次增加很多。 | 本地预测 Rigidbody 与每份快照的平滑校正目标同时写位置；旧计数还把每次更新目标都当成一次校正。 | 自身/高优先级确认恢复为 30 Hz；持续输入及输入结束后 0.2 秒不施加位置校正；同一连续校正过程只计一次。联调中本地移动手感恢复平稳，计数语义也与实际校正过程一致。 |

这里的“低频实体”只代表更低的状态更新频率，**不代表允许视觉闪烁**。正确取舍是以更多播放延迟换取连续插值；超出 45 米后的不显示则是明确的复制范围裁剪结果。

## 配置与人工验收结论

默认启动命令为：

```powershell
dotnet run
```

它启用距离过滤。若要和第一章的全量复制基线直接对比，使用：

```powershell
dotnet run -- --full-snapshots
```

本阶段已完成的双客户端人工验收：

- 近距离两人移动、瞄准、开火、受击、死亡和重生保持正常。
- 18 米内远端高频且流畅；18–45 米远端低频但连续平滑；超过 45 米双方不再显示对方，`Replication scope` 相应降为 1。
- 正常关闭客户端会立即清理远端对象；无法发送退出包时，服务器在 8 秒后超时清理。
- 本地持续移动时不再因网络微校正反复拉扯；停止输入后允许进行一次平滑对齐。

## 阶段边界与交接

阶段 11 已完成“按客户端构建和消费状态快照”的管线，但没有把 UDP 变成可靠传输：`FireEvent`、`HitEvent`、`HealthChangedEvent` 仍是当前的直接 UDP 广播，没有 `eventId`、确认、去重或有限重发。

`changeMask` 与 `isFullState` 只是为后续差分复制预留的协议接口；在客户端尚未确认 `baselineTick` 前，必须继续发送完整字段，不能把上一份 UDP 快照当作差分基线。死亡、重生等关键事实也不能依赖状态差分来“补可靠”。这些正是阶段 12 应处理的事件可靠性边界，而真正的状态差分确认属于后续序列化/压缩阶段。

已通过：

- `dotnet build Server/Server/Server.csproj`
- `dotnet build Server/Server.Tests/Server.Tests.csproj`
- `dotnet run --project Server/Server.Tests/Server.Tests.csproj`

测试覆盖自身必发、距离过滤、低频实体保留在复制范围、全量模式与第一章的等价行为，以及全量字段回退的 `changeMask`。

本机 UDP 冒烟验证使用距离过滤并模拟两名客户端握手：服务器保持 30 Hz 模拟与 30 Hz 高优先级快照；两名相距 4 米的玩家均为高优先级。该结果验证管线和遥测；Unity 双客户端的可视表现仍应按验收步骤人工检查。

另一次本机 UDP 验证模拟两名客户端连接，再由玩家 1 发送 `ClientGoodbye`：服务端日志从 `players=2` 变为 `players=1`，玩家 2 的遥测从 `statePlayers=2, scopePlayers=2` 变为 `statePlayers=1, scopePlayers=1`。
