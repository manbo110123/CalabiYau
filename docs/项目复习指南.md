# 联机 Tank TPS Demo 复习与面试讲解文档

本文档用于复习本项目的最终实现。重点不是背术语，而是能把“为什么需要它、它解决什么问题、代码中怎么实现、还有什么可优化”讲清楚。

## 一句话介绍

这是一个 Unity 客户端 + .NET C# UDP 服务器实现的第三人称联机射击同步 Demo。客户端只上报输入，服务器以固定 Tick 权威模拟玩家位置、血量和命中结果，并广播状态快照；客户端通过本地预测、服务端校正、远端插值、调试面板和射击延迟补偿，在弱网环境下保持可玩的同步体验。

## 简历版描述

联机 TPS 状态同步对战 Demo - Unity 客户端 / .NET C# 服务器个人项目

项目描述：基于 Unity 和 .NET C# 开发服务端权威的第三人称联网射击 Demo，以 Tank 作为轻量级玩家实体，采用客户端输入上报、服务器固定 Tick 模拟、状态快照广播的同步架构，实现多客户端玩家生成、本地预测、服务端校正、远端快照插值、网络开火事件、服务器命中判定、血量死亡重生、运行时调试面板和射击延迟补偿；重点解决高延迟下本地操作响应、远端玩家平滑表现、UDP 快照丢失估算、服务器权威战斗结算和同步过程可视化调试问题。

## 项目文件地图

- `Assets/Code/UdpNetworkClient.cs`  
  Unity 客户端网络入口。负责 UDP 收发、消息分发、本地输入发送、本地预测校正、远端玩家生成、事件处理、RTT 与丢包估算、调试面板。

- `Assets/Code/NetworkTankAvatar.cs`  
  网络玩家表现脚本。负责远端快照缓冲与插值、服务器状态应用、血量显示、受击闪红、死亡染色、世界空间状态文字、开火与命中特效入口。

- `Assets/Code/TankInput.cs` / `TankInputData.cs`  
  本地输入采集和输入数据结构。网络层发送的是输入数据，不是 Transform。

- `Assets/Code/TankMotor.cs`  
  坦克移动逻辑。本地预测重放时也复用同样的移动规则思想。

- `Assets/Code/TankAim.cs`  
  鼠标射线瞄准和炮塔朝向。

- `Assets/Code/TankWeapon.cs`  
  武器表现入口。联网状态下本地武器直接结算被关闭，开火由服务器事件驱动表现。

- `Server/Server/Program.cs`  
  .NET UDP 专用服务器。负责连接、玩家状态、服务器 Tick、输入消费、快照广播、开火校验、命中判定、血量死亡重生、延迟补偿历史状态。

## 启动和演示流程

1. 启动服务器：

```powershell
cd "D:\unity project\CalabiYau\CalabiYau\Server\Server"
dotnet run
```

2. 启动两个 Unity 客户端。

- 一个用 Unity Editor。
- 一个用打包后的 Windows 客户端。

3. 两个客户端进入同一场景后，观察：

- 服务器控制台出现 `ClientHello`、`PlayerInput`、`FireRequest` 和 Tick 统计。
- 客户端左上角出现 `Network Debug` 面板。
- 两辆坦克互相可见、可移动、可开火、可扣血、可死亡和重生。

4. 按 `F3` 显示或隐藏调试面板。

## 核心同步流程

完整链路可以这样讲：

```text
客户端读取键盘鼠标输入
-> 按网络 Tick 发送 PlayerInput
-> 服务器保存最新输入
-> 服务器 30 Hz Tick 权威模拟玩家状态
-> 服务器广播 WorldSnapshot
-> 本地玩家用快照做校正和输入重放
-> 远端玩家用快照缓冲做插值显示
```

开火链路：

```text
客户端按下开火
-> 本地只发送 FireRequest，不自己决定命中
-> 服务器校验玩家状态、射速、瞄准方向
-> 服务器使用权威状态和延迟补偿历史帧做射线命中检测
-> 服务器广播 FireEvent / HitEvent / HealthChangedEvent
-> 客户端播放炮口、命中、扣血、死亡、重生表现
```

## 为什么客户端只发输入，不发位置

如果客户端直接上传 Transform 位置，玩家可以本地改速度、瞬移或改内存，然后告诉服务器“我就在这里”。这对竞技游戏不公平。

本项目选择服务器权威：

- 客户端发送 `moveAxis`、`turnAxis`、`aimX`、`aimZ`、`fire`。
- 服务器根据统一移动参数计算最终位置。
- 快照中的位置才是权威位置。

面试回答可以说：

> 我没有让客户端直接决定位置，而是让客户端只上传输入。服务器固定 Tick 消费输入并计算权威状态，这样即使客户端本地改移动速度，也不能改变服务器认可的位置。

## Tick 是什么

Tick 是服务器固定频率更新世界的节拍。本项目服务器使用 30 Hz：

```text
1 秒 30 次
每次间隔约 33.3 ms
```

不用每帧 Transform 同步的原因：

- Unity 客户端帧率不稳定，有的 60 FPS，有的 144 FPS。
- 不同机器直接按帧同步会导致时间轴不一致。
- Tick 能让服务器、输入、快照和回滚都挂在同一条时间线上。

项目中常见 Tick：

- `inputTick`：客户端输入序号。
- `serverTick`：服务器模拟世界的序号。
- `lastProcessedInputTick`：服务器已经处理到本地玩家哪一帧输入。
- `hitTestServerTick`：延迟补偿时用于命中检测的历史服务器 Tick。

## 本地预测

问题：如果本地玩家按键后必须等服务器快照回来再移动，100 ms 延迟下会明显卡手。

解决：客户端按键后先在本地移动自己，同时把输入发给服务器。

本项目做法：

- `UdpNetworkClient.SendPlayerInput()` 每个网络 Tick 发送输入。
- `SaveLocalInput()` 保存输入历史和发送时间。
- 本地 `TankController` 继续立即响应输入。
- 收到服务器快照后再校正。

面试回答：

> 本地预测解决的是操作响应问题。玩家按下移动键时客户端先移动，服务器之后返回权威快照。如果预测和服务器一致，玩家感觉就像单机一样顺；如果不一致，再通过校正修回来。

## 服务端校正和回滚重放

预测可能会错，原因包括：

- 丢包或延迟。
- 客户端和服务器状态不同步。
- 碰撞、死亡、重生等权威状态由服务器决定。
- 本地预测参数和服务器参数不完全一致。

项目做法：

1. 服务器快照带 `lastProcessedInputTick`。
2. 客户端收到快照后，移除已经被服务器确认的输入。
3. 从服务器权威位置开始，重放还没被确认的输入。
4. 得到一个“按服务器状态重建后的本地预测位置”。
5. 当前本地位置与重建位置比较：
   - 误差很小：忽略。
   - 误差中等：平滑修正。
   - 误差很大：硬修正。

关键代码位置：

- `UdpNetworkClient.StoreAuthoritativeLocalSnapshot()`
- `UdpNetworkClient.UpdateRttFromAcknowledgedInput()`
- `UdpNetworkClient.RemoveAcknowledgedLocalInputs()`
- `UdpNetworkClient.ReconcileLocalPrediction()`
- `UdpNetworkClient.BuildReconciledLocalState()`

面试回答：

> 我用服务器确认的 `lastProcessedInputTick` 删除已经处理过的输入，然后从服务器权威快照开始重放未确认输入。这样既保持服务器权威，又尽量保留本地即时操作手感。

## 远端玩家快照插值

远端玩家不能用本地输入预测，因为客户端不知道别人未来会按什么键。

本项目做法：

- 每个远端玩家维护 `remoteSnapshotBuffer`。
- 快照按 `serverTick` 排序插入。
- 显示时故意落后约 `remoteInterpolationDelaySeconds`。
- 在两个历史快照之间用 `Vector3.Lerp` 和 `Quaternion.Slerp` 平滑播放。

关键代码位置：

- `NetworkTankAvatar.AddRemoteSnapshot()`
- `NetworkTankAvatar.PlayRemoteSnapshotBuffer()`

注意：当前实现是“快照插值 + 断档保持”。当找不到可插值快照时，会保持最早或最新快照。严格说，这还不是基于速度的短时外推。

面试回答：

> 远端玩家我不预测输入，而是缓存服务器快照并延迟一点播放，在两个已知快照之间插值。这样能吸收 UDP 包到达不均匀造成的抖动。

## 短时外推的当前状态

当前项目没有做严格意义上的速度外推。

已有：

- 远端快照缓冲。
- 按 Tick 排序。
- 插值播放。
- 断档时保持最后快照。

未做：

- 根据最近两个快照算速度。
- 快照断档时用 `position + velocity * time` 短暂向前预测。
- 设置最大外推时间，例如 100 ms。

如果面试官问外推，可以诚实说：

> 当前版本主要实现了远端快照插值和断档保持，还没有加入速度外推。后续可以用最近两个快照计算速度，在缺少新快照时最多外推 100 ms，超过阈值后停止，避免预测过头导致回拉。

## 网络开火和命中

本项目开火采用：

```text
本地即时请求 + 服务器权威判定 + 客户端事件表现
```

客户端发送 `FireRequest`，包含：

- `playerId`
- `requestTick`
- 瞄准点
- 炮口位置
- 开火方向
- 估算 RTT
- 远端插值延迟

服务器校验：

- 发送者是否完成连接。
- 发送者是否拥有这个 `playerId`。
- 玩家是否存活。
- 武器冷却是否结束。
- 瞄准点是否和服务器已知瞄准状态接近。
- 开火方向是否合理。

服务器广播：

- `FireEvent`：播放开火表现。
- `HitEvent`：播放命中反馈。
- `HealthChangedEvent`：同步扣血、死亡和重生倒计时。

面试回答：

> 客户端不能直接说“我打中了”。客户端只能请求开火，服务器基于权威玩家状态做命中检测，再广播扣血和死亡结果。

## 射击延迟补偿

延迟补偿解决的问题：

玩家 A 延迟 100 ms，A 在自己屏幕上看到 B 在某个位置并开火。这个请求到服务器时，B 可能已经移动了。如果服务器只用当前 B 的位置判定，A 会觉得“我明明打中了但服务器说没中”。

项目做法：

1. 服务器每个 Tick 保存玩家历史状态。
2. 历史状态保存约 1 秒。
3. 客户端开火时上报估算 RTT 和远端插值延迟。
4. 服务器计算回溯时间：

```text
rewindSeconds = estimatedRttSeconds + interpolationDelaySeconds
```

5. 服务器限制最大回溯时间，目前约 0.35 秒。
6. 服务器把命中检测 Tick 换成：

```text
hitTestServerTick = currentServerTick - rewindTicks
```

7. 命中检测时使用目标在历史 Tick 的位置。

关键代码位置：

- `Program.cs StorePlayerHistory()`
- `Program.cs BuildLagCompensationFrame()`
- `Program.cs GetPlayerFrameAtOrBefore()`
- `Program.cs FindFirstHitPlayer()`

为什么要限制最大回溯：

如果完全相信客户端说“我延迟很高”，作弊客户端可以让服务器回到很久以前的位置判定命中，对低延迟玩家不公平。

面试回答：

> 延迟补偿不是让客户端决定命中，而是服务器保存历史状态。收到延迟到达的开火请求时，服务器回到射手当时大概看到的目标位置做检测，同时限制最大回溯窗口，避免高延迟或作弊客户端获得过大优势。

当前实现的简化点：

- RTT 主要由客户端估算后上报，服务器做最大值限制。
- 历史状态按整数 Tick 获取，没有做 Tick 间插值。
- 命中体使用 2D 圆形半径，不是复杂 HitBox。
- 更严谨版本可以由服务器维护 RTT、做时钟同步、历史帧插值和分部位 HitBox。

## 血量、死亡和重生

战斗状态由服务器维护：

- 最大血量：`maxHealth`
- 单次伤害：`fireDamage`
- 死亡状态：`IsAlive`
- 重生 Tick：`RespawnServerTick`

玩家死亡后：

- 服务器停止模拟该玩家移动。
- 客户端本地停止移动预测和开火请求。
- 客户端显示死亡状态和重生倒计时。
- 到达服务器重生 Tick 后，服务器恢复血量并广播状态。

为什么血量也放进快照：

UDP 事件可能丢失。如果只靠 `HealthChangedEvent`，某个客户端漏掉事件后可能长期显示错误血量。把血量和死亡状态放进 `WorldSnapshot`，可以让后续快照把状态拉回正确结果。

## 调试面板

调试面板是项目展示的核心工具之一。它不是玩法逻辑，而是观察网络同步状态。

显示内容：

- `playerId`：服务器分配的玩家 id。
- `Connection`：连接和快照状态。
- `RTT`：输入发出到收到服务器确认的往返时间估算。
- `Estimated latency`：约等于 RTT 的一半。
- `Server tick`：基于最后快照 Tick 和本地时间估算的服务器 Tick。
- `Local input tick`：本地输入序号。
- `Last snapshot tick`：最后收到的服务器快照 Tick。
- `Snapshot buffer`：远端玩家快照缓冲数量。
- `Prediction corrections`：本地预测修正次数。
- `Last prediction error`：最近一次预测误差距离。
- `Packet loss rate`：基于快照 Tick 跳号估算的快照丢失率。
- `Snapshot missing`：估算丢失快照数和已接收快照数。
- `Lag compensation`：最近一次开火是否使用回溯、回溯时间和检测 Tick。
- `Pending inputs`：还没被服务器确认的本地输入数量。
- `Gameplay events`：收到的玩法事件数。
- `Fire requests`：本地发出的开火请求数。

关键代码位置：

- `UdpNetworkClient.DrawNetworkDebugPanel()`
- `UdpNetworkClient.RecordSnapshotStats()`
- `UdpNetworkClient.UpdateRttFromAcknowledgedInput()`
- `UdpNetworkClient.GetEstimatedSnapshotLossRate()`

注意：

当前丢包率严格来说是“快照丢失率估算”，不是所有 UDP 包的精确丢包率。因为项目没有给每个 UDP 包都加统一包序号。

你已经做过弱网测试，建议在最终提交或简历讲解前，把具体数值补到这里。当前可按下面格式整理。

测试工具建议：clumsy。

```text
udp and (udp.DstPort == 7777 or udp.SrcPort == 7777)
```

推荐测试档位：

| 场景 | 延迟 | 丢包 | 观察重点 | 结论 |
| --- | --- | --- | --- | --- |
| 正常网络 | 0 ms | 0% | 移动、开火、扣血、重生是否稳定 | 项目基础联机闭环可运行 |
| 中等延迟 | 100 ms | 0% | 本地预测是否跟手，远端插值是否平滑 | 本地操作基本不等待服务器 |

| 轻微丢包 | 100 ms | 2% | 快照丢失率、远端移动抖动、事件表现 | 快照丢失可被插值缓冲部分吸收 |
| 较差网络 | 200 ms | 5% | 开火命中、死亡重生、状态恢复 | 快照中的血量和死亡状态可纠正漏事件造成的显示偏差 |

面试讲法：

> 我用 clumsy 模拟 100 ms、200 ms 延迟和少量丢包。调试面板可以看到 RTT、快照丢失估算、预测修正次数和未确认输入数量变化。弱网下本地玩家依靠预测保持操作响应，远端玩家依靠快照插值减少抖动，射击命中通过服务器历史状态做延迟补偿。

## 当前项目的真实简化点

这些点不是缺陷，而是实习项目中合理的取舍。面试时可以主动讲清楚。

1. 协议使用 JSON。
   - 优点：可读、易调试、适合学习。
   - 缺点：包体较大、序列化慢。
   - 后续：可替换 MessagePack 或 Protocol Buffers。

2. 传输层使用 .NET `UdpClient`。
   - 优点：底层清楚，没有隐藏细节。
   - 缺点：连接管理、可靠消息、重发机制都要自己写。
   - 后续：可替换 LiteNetLib 或 KCP。

3. 关键事件没有完整可靠确认。
   - 当前通过把血量、死亡、重生状态放进快照来避免长期错误。
   - 后续可以给关键事件加 `eventId`、ACK 和有限重发。

4. 远端玩家没有速度外推。
   - 当前是插值和断档保持。
   - 后续可以加入最多 100 ms 的有限外推。

5. 命中体是简单圆形半径。
   - 当前适合 Tank Demo 和服务端 2D 平面射线。
   - 后续可以升级为 AABB、胶囊体或分部位 HitBox。

6. 没有服务端地图障碍判定。
   - 当前适合大平地或简单竞技场。
   - 后续如果加入掩体，服务器也要维护障碍数据并参与射线遮挡检测。

7. 逻辑层和表现层分离还可以更彻底。
   - 当前 `NetworkTankAvatar` 已承担部分表现平滑。
   - 后续可以拆成 `TankLogicRoot` 和 `TankVisualRoot`，Collider 使用逻辑位置，模型平滑追赶。

## 如果面试官问“为什么不用 Protobuf”

可以这样答：

> 我知道 JSON 不适合高频实时游戏的最终性能方案。这个项目第一版选择 JSON，是因为我希望在学习阶段能直接打印和理解每个消息内容，重点先放在 Tick、快照、预测、回滚和服务器权威。后续协议层可以替换为 MessagePack 或 Protocol Buffers。替换时上层消息语义不变，只改变序列化方式，并对比包体大小和 CPU 开销。

## 如果面试官问“为什么不用现成网络框架”

可以这样答：

> 现成框架能更快做功能，但也会隐藏很多同步细节。我这个项目的目标是学习和展示网络同步原理，所以先用 `UdpClient` 自己实现连接、输入、快照和事件。这样我能讲清楚每个包在做什么。后续如果要工程化，可以把传输层替换成 LiteNetLib 或 KCP，上层服务器权威和预测校正逻辑仍然保留。

## 如果面试官问“你的项目和真正商业游戏差在哪”

可以这样答：

> 我的项目是实习展示级 Demo，重点是完整同步链路和可解释性。和商业项目相比，它还缺少完整可靠 UDP、兴趣管理、复杂反作弊、服务器地图碰撞、协议压缩、服务端部署、匹配房间、完整动画同步和更严格的时钟同步。但核心链路已经具备：客户端输入上报、服务器 Tick 权威模拟、快照同步、本地预测、服务端校正、远端插值、服务器命中判定、血量死亡重生、调试面板和射击延迟补偿。

## 五分钟讲解稿

可以按这个顺序讲：

1. 项目目标  
   我做的是 Unity 客户端和 .NET UDP 服务器的联机射击同步 Demo，重点是验证服务端权威同步，而不是做复杂美术。

2. 总体架构  
   客户端不上传位置，只上传输入；服务器 30 Hz Tick 模拟世界，并广播 `WorldSnapshot`。

3. 移动同步  
   本地玩家用客户端预测保证手感，收到服务器快照后根据 `lastProcessedInputTick` 删除已确认输入，再重放未确认输入做校正。

4. 远端显示  
   远端玩家不预测输入，而是维护快照缓冲，在历史快照之间插值，减少网络包离散到达造成的抖动。

5. 战斗同步  
   客户端只发送 `FireRequest`，服务器校验射速、存活状态和瞄准方向后做命中判定，并广播开火、命中、扣血、死亡和重生事件。

6. 延迟补偿  
   服务器保存最近约 1 秒历史状态。开火请求延迟到达时，服务器根据 RTT 和插值延迟回溯目标历史位置做检测，同时限制最大回溯时间防止不公平。

7. 调试和弱网  
   我做了运行时调试面板，显示 RTT、快照丢失估算、预测误差、修正次数、未确认输入、延迟补偿状态等，并用 clumsy 做过 100 ms、200 ms 和丢包环境测试。

8. 项目取舍  
   当前使用 JSON 和 `UdpClient` 是为了学习和调试，后续可以升级到 MessagePack/Protobuf 和 LiteNetLib/KCP；当前没有做完整可靠消息和服务器地图障碍，但核心同步链路已经完整。
