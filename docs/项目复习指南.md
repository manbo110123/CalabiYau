# 联机 Tank TPS Demo 复习与面试讲解文档

本文档用于复习本项目的当前实现。重点不是背术语，而是能把“为什么需要它、它解决什么问题、代码中怎么实现、还有什么可优化”讲清楚。

文档以当前代码为准，最后核对时间：2026-08-08。文中“已实现”表示代码和测试或联调记录已经覆盖；“后续”表示明确保留的优化方向，不能写进已完成的简历内容。

## 一句话介绍

这是一个 Unity 客户端 + .NET C# UDP 服务器实现的第三人称联机射击同步 Demo。客户端只上报输入和开火意图；服务器以固定 Tick 权威模拟位置、血量、死亡、重生和命中结果，再向每名客户端构建对应的状态快照。客户端通过本地预测、服务端校正、远端快照插值、有限可靠结果事件、按客户端状态复制和射击延迟补偿，在弱网环境下保持可玩的同步体验。

## 简历版描述

联机 TPS 状态同步对战 Demo - Unity 客户端 / .NET C# 服务器个人项目

项目描述：基于 Unity 和 .NET C# 开发服务端权威的第三人称联网射击 Demo，以 Tank 作为轻量级玩家实体，采用客户端输入上报、服务器固定 Tick 模拟、按客户端状态快照复制的同步架构，实现多客户端玩家生成、本地预测、服务端校正、远端快照插值、网络开火、服务器命中判定、血量死亡重生、射击延迟补偿和运行时网络调试面板；进一步实现输入命令校验、开火收据与有限重发、关键结果事件 ACK/去重、生命状态版本防乱序，以及距离分级复制。

## 项目文件地图

### Unity 客户端

- `Assets/Code/UdpNetworkClient.cs`  
  Unity 客户端网络入口。负责 UDP 收发、按 `type` 分发消息、输入发送、本地预测校正、远端玩家生成、开火有限重发、可靠事件 ACK/去重、RTT 与快照丢失估算、复制范围清理和 F3 调试面板。

- `Assets/Code/NetworkTankAvatar.cs`  
  单个网络玩家的表现脚本。负责远端快照缓冲和插值、服务器状态应用、血量显示、受击闪红、死亡染色、重生倒计时、开火与命中特效入口。

- `Assets/Code/TankInput.cs` / `TankInputData.cs`  
  本地输入采集和输入数据结构。网络层发送的是移动、转向和瞄准输入，不是 `Transform`。

- `Assets/Code/TankMotor.cs` / `TankAim.cs` / `TankController.cs`  
  Tank 的移动、瞄准和本地控制。预测重放沿用同一套移动规则，减少客户端与服务器逻辑漂移。

- `Assets/Code/TankWeapon.cs`  
  武器表现入口。联网模式下客户端不自行结算命中；枪火和命中表现由服务器结果事件驱动。

### .NET 服务器

- `Server/Server/Program.cs`  
  服务器组合根。只负责读取启动参数、配置 Tick/复制参数并启动 `UdpGameServer`，不再堆放游戏规则。

- `Server/Server/UdpGameServer.cs`  
  UDP 收发、消息路由、固定 Tick 循环、客户端超时清理、快照/事件发送和服务端遥测。它不直接修改 `PlayerState`。

- `Server/Server/GameWorld.cs`  
  纯权威世界核心。不依赖 UDP、JSON 或 Unity，负责输入/开火命令校验、命令缓存、移动模拟、射击、伤害、死亡、重生和延迟补偿历史状态。

- `Server/Server/ClientRegistry.cs`  
  管理 endpoint 与 `playerId` 的映射、最后收包时间、每客户端复制器和可靠事件账本。

- `Server/Server/SnapshotBuilder.cs`  
  只读 `GameWorld`，把权威 `PlayerState` 转为可复制的候选状态，不做网络发送决策。

- `Server/Server/ClientReplicator.cs`  
  每个连接独立拥有。决定该客户端能看到哪些实体、实体是高频还是低频、每个快照的独立序号和复制范围。

- `Server/Server/ReliableEventLedger.cs`  
  每个客户端一份的关键结果事件账本。保存待 ACK 的原始 JSON、有限重发次数和 ACK 延迟遥测。

- `Server/Server/Messages.cs`  
  服务端 JSON DTO 与快照字段定义。Unity 客户端在 `UdpNetworkClient.cs` 底部保留对应 DTO；两端字段语义必须一致。

- `Server/Server.Tests/Program.cs`  
  无 Unity 依赖的服务器自动检查，覆盖命令时间线、复制、开火收据、可靠事件和生命状态版本等关键规则。

## 核心同步流程

项目中最重要的职责划分是：客户端负责“立即响应和表现”，服务器负责“最终规则和事实”。

```text
Unity 客户端读取键鼠输入
-> 本地立即预测移动
-> 发送 PlayerInput / FireRequest
-> UdpGameServer 只反序列化并路由命令
-> GameWorld 在固定 Tick 消费命令、模拟权威状态
-> SnapshotBuilder 读取权威状态
-> ClientReplicator 为每名客户端构建 WorldSnapshot
-> 客户端用快照校正本地玩家、插值显示远端玩家
```

开火链路：

```text
客户端按下开火
-> 生成带 fireSequence 的 FireRequest
-> 服务器回 FireReceipt：仅说明是否已入队
-> GameWorld 下一次 Tick 校验冷却、延迟补偿和命中
-> 产生 FireEvent / HitEvent / HealthChangedEvent
-> 血量、死亡和重生持续写入 WorldSnapshot
-> DeathEvent / RespawnEvent / KillEvent 额外走有限 ACK/重发账本
```

可靠结果补充链路：

```text
服务器 Tick 产生 DeathEvent / RespawnEvent / KillEvent
-> 每个接收客户端的账本保存 eventId 并有限重发
-> 客户端首次收到后 ACK，重复包只 ACK 不重复处理
-> 生命周期事件按 playerId + lifeStateVersion 拒绝旧状态
-> Avatar 尚未创建时缓存最新生命周期结果，快照创建 Avatar 后再落地
-> WorldSnapshot 持续携带 health、isAlive、lifeStateVersion 作为恢复基线
```

## 为什么客户端只发输入，不发位置

如果客户端直接上传 `Transform` 位置，玩家可以本地改速度、瞬移或改内存，然后告诉服务器“我就在这里”。服务器若相信这个位置，就失去公平性。

本项目选择服务器权威：

- 客户端发送 `moveAxis`、`turnAxis`、`aimX`、`aimZ` 和输入序号。
- 服务器根据统一的移动速度、转向速度和 Tick 间隔计算最终位置。
- `WorldSnapshot` 中的位置才是权威位置。

面试回答可以说：

> 我没有让客户端直接决定位置，而是让客户端只上传输入。服务器固定 Tick 消费输入并计算权威状态，因此客户端即使篡改本地移动速度，也不能改变服务器认可的位置。

## Tick 是什么

Tick 是服务器固定频率更新世界的节拍。本项目默认服务器使用 30 Hz；真实值由 `ServerWelcome.serverTickRate` 下发给客户端。

```text
1 秒 30 次
每次间隔约 33.3 ms
```

不用“每帧同步 Transform”的原因：

- Unity 客户端帧率不稳定，有的 60 FPS，有的 144 FPS。
- 不同机器直接按帧推进会处在不同时间轴。
- Tick 能让输入、快照、回滚、冷却和延迟补偿都挂在同一条服务器时间线上。

项目中常见的序号和版本：

- `inputTick`：客户端给连续输入编号，用于确认和预测重放；它不是服务器 Tick。
- `serverTick`：服务器每模拟一次世界加一，是权威时间轴。
- `lastProcessedInputTick`：服务器已消费到本地玩家的哪个输入，用于客户端删除已确认输入。
- `requestTick`：开火请求产生时对应的客户端输入 Tick，用于命令时序校验。
- `snapshotSequence`：每个客户端各自的快照数据报编号，用于估算快照丢失；它必须独立于 `serverTick`。
- `fireSequence`：单个玩家的离散开火编号，用于开火有限重发去重。
- `eventId`：跨关键结果事件的唯一编号，用于 ACK 和重复包去重。
- `lifeStateVersion`：每位玩家独立的生命状态版本；死亡、重生各加一，用来拒绝 UDP 乱序的旧生命周期事件。

## 命令时间线与服务端校验

阶段 9/10 后，服务器不再在 UDP 收包回调中直接改变血量或位置。收包层只做“谁发来的、包能否解析”；真正的规则全部进入 `GameWorld`。

### 输入命令

`GameWorld.TryQueueInput()` 会检查：

- endpoint 对应的身份是否正确（由 `UdpGameServer` 和 `ClientRegistry` 保证）。
- 玩家是否存在、是否存活。
- `inputTick` 是否为正、是否过旧或过于超前。
- 移动轴是否在 `[-1, 1]`，瞄准坐标是否为有限数且距离合理。
- 缓冲区是否重复或超过容量。

服务器将输入暂存为按 `inputTick` 排序的 `PendingInputs`。每个 Tick 取当前可用的最新输入，旧输入被记为 superseded 后丢弃；这是一种“最新意图”模型，而不是严格逐 Tick 重演所有历史输入。

`InputHoldTimeoutTicks` 默认是 6 Tick。若服务器连续一段时间没有消费到更晚输入，就把移动和转向归零、保留最后合法瞄准点。它解决的是“松开按键的包丢失后，服务器角色永久前进”的问题，也叫输入租约（input lease）。

### 离散开火命令

`GameWorld.TryQueueFireWithReceipt()` 检查 `fireSequence`、`requestTick`、瞄准点、RTT 和插值延迟是否合法，然后将开火放入 `PendingFires`。只有 `GameWorld.Tick()` 中的 `ResolveQueuedFireRequests()` 才会统一执行冷却、命中、伤害、死亡和事件生成。

这样做的价值是：网络到包快慢不会直接改变规则结算时机；命中和移动都在同一条权威 Tick 时间线上推进。

面试回答可以说：

> 收包回调只负责把网络消息转换为命令，不能直接修改战斗状态。服务器在固定 Tick 统一消费命令并推进世界，这样能避免网络线程/到包时机影响游戏规则。

## 本地预测

问题：如果本地玩家按键后必须等服务器快照回来再移动，100 ms 延迟下会明显卡手。

解决：客户端按键后先在本地执行移动，同时把输入发给服务器。

项目做法：

- `UdpNetworkClient.SendPlayerInput()` 按输入频率发送 `PlayerInput`。
- `SaveLocalInput()` 保存输入历史和发送时间。
- 本地 `TankController` 与 `TankMotor` 立即响应输入。
- 收到服务器快照后，再用权威状态确认或校正。

本地预测不是“客户端拥有位置”，而是“客户端提前猜测服务器之后大概率会得到的结果”。一旦猜错，必须服从服务器。

面试回答：

> 本地预测解决的是操作响应问题。玩家按下移动键时客户端先移动，服务器之后返回权威快照；预测正确时体验接近单机，预测错误时再由服务器校正回来。

## 服务端校正和回滚重放

预测可能会错，原因包括：

- 延迟、抖动和丢包。
- 客户端与服务器命令处理时机不同。
- 死亡、重生、冷却和命中只能由服务器决定。
- 后续加入服务器碰撞时，客户端预测可能与服务器阻挡结果不同。

项目做法：

1. 服务器快照带 `lastProcessedInputTick`。
2. 客户端收到本地玩家快照后，移除已经被服务器确认的输入。
3. 从服务器权威位置开始，重放还没被确认的输入。
4. 得到“按服务器状态重建后的本地预测位置”。
5. 当前本地位置与重建位置比较：误差小则忽略，误差中等则平滑收敛，误差大则硬修正。

关键代码位置：

- `UdpNetworkClient.StoreAuthoritativeLocalSnapshot()`
- `UdpNetworkClient.UpdateRttFromAcknowledgedInput()`
- `UdpNetworkClient.RemoveAcknowledgedLocalInputs()`
- `UdpNetworkClient.ReconcileLocalPrediction()`
- `UdpNetworkClient.BuildReconciledLocalState()`

逻辑层与表现层的思想：权威/重建位置是逻辑真相；模型可以在若干帧内平滑追向逻辑位置。这样不为视觉平滑牺牲服务器正确性。

面试回答：

> 我用服务器确认的 `lastProcessedInputTick` 移除已处理输入，然后从服务器权威快照重放未确认输入，重建本地预测状态。这样既保持服务器权威，也尽量保留本地即时操作手感。

## 远端玩家快照插值

远端玩家不能使用本地输入预测，因为客户端不知道别人下一帧会按什么键。

项目做法：

- 每个远端玩家维护 `remoteSnapshotBuffer`。
- 快照按 `serverTick` 排序插入。
- 显示时故意落后约 `remoteInterpolationDelaySeconds`。
- 在两个历史快照之间用 `Vector3.Lerp` 和 `Quaternion.Slerp` 平滑播放。
- 低频实体的插值延迟会根据相邻状态的实际 Tick 间隔自适应，避免 5 Hz 更新时缓冲提前耗尽。

关键代码位置：

- `NetworkTankAvatar.AddRemoteSnapshot()`
- `NetworkTankAvatar.PlayRemoteSnapshotBuffer()`
- `UdpNetworkClient.GetRemoteInterpolationDelaySeconds()`

面试回答：

> 远端玩家不预测输入，而是缓存服务器快照并延迟一点播放，在两个已知状态之间插值。这个播放延迟换来了对 UDP 包到达不均匀的吸收能力，因此远端观感更稳定。

## 短时外推的当前状态

当前项目没有做严格意义上的速度外推。

已有：

- 远端快照缓冲、按 Tick 排序和插值播放。
- 高/低优先级实体根据实际更新间隔调整插值延迟。
- 缓冲断档时保持可用状态，而不是无边界猜测未来。

未做：

- 根据最近两帧计算速度。
- 快照断档时使用 `position + velocity * time` 短暂向前预测。
- 设置最大外推时长，例如 100 ms，超时后停止。

面试时应诚实说：

> 当前版本重点实现了插值与分级复制下的自适应插值延迟，断档时保持最后可用状态；还没有实现速度外推。后续可限制在约 100 ms 内做短时外推，超过阈值后等待新快照，避免预测过头造成明显回拉。

## 按客户端状态复制

阶段 11 解决的问题不是“让两个 Tank 能同步”，而是“实体增加后，不能再把同一份全量 JSON 无差别广播给所有人”。

```text
GameWorld --只读--> SnapshotBuilder --候选状态--> ClientReplicator（每客户端一份）
                                                         |
                                                         v
                                             WorldSnapshot + UDP JSON
```

当前规则：

- 自己始终进入每份快照，保证预测确认、生命状态和重生状态连续。
- 18 米内的远端玩家，或最近 30 Tick 发生过战斗的玩家，使用高优先级状态更新。
- 18--45 米的非战斗远端玩家低优先级更新，默认 5 Hz。
- 超过 45 米的远端玩家离开复制范围，客户端清理其 Avatar。
- `replicatedPlayerIds` 表示“仍然存在于本客户端复制范围”的实体；低频实体即使本包没有状态更新，也不能被误删。
- 每名客户端的 `snapshotSequence` 独立递增，用于判断该客户端自己的快照包缺口，不能拿 `serverTick` 代替。
- 当前每次实际发送的实体状态仍是完整字段：`isFullState=true`、`changeMask=All`。`changeMask` 只是未来差分复制的协议预留。

关键代码位置：

- `SnapshotBuilder.Capture()`：从权威世界生成候选状态。
- `ClientReplicator.BuildSnapshot()`：按接收者筛选、分级和控制频率。
- `ClientReplicator.CloneAsFullState()`：复制完整状态，包括 `lifeStateVersion`。
- `UdpNetworkClient.RemoveRemoteAvatarsOutsideReplicationScope()`：清理范围外表现对象。

这是一种距离与战斗优先级复制，不是完整的视锥裁剪、遮挡裁剪或真正 AOI 网格系统。它的价值在于先把“权威模拟”和“对谁复制什么”拆开，为后续兴趣管理留出独立入口。

## 网络开火和命中

本项目开火采用：

```text
本地开火意图 + 服务器权威判定 + 客户端事件表现
```

`FireRequest` 包含：

- `playerId`
- `fireSequence`
- `requestTick`
- `aimX` / `aimZ`
- `estimatedRttSeconds`
- `interpolationDelaySeconds`

客户端不再上传炮口位置和射线方向。服务器根据自己的权威玩家状态、服务器已知瞄准点与校验后的请求瞄准点，推导射线起点和方向。这样客户端不能直接伪造“我从墙后面射出一条射线”。

服务器在 Tick 中校验和执行：

- 玩家身份、存活状态和请求时间窗口。
- `fireSequence`、瞄准点、RTT/插值延迟的数值范围。
- 武器冷却。
- 请求瞄准点与服务器已知瞄准状态是否合理接近。
- 延迟补偿后的射线和简化圆形命中体检测。
- 伤害、死亡、重生 Tick 和玩法事件生成。

服务器广播：

- `FireEvent`：播放开火表现，允许丢失。
- `HitEvent`：播放受击闪红/命中特效，允许丢失。
- `HealthChangedEvent`：只做可观察战斗提示，允许丢失，不能修改客户端生命状态。
- `WorldSnapshot`：血量、存活、倒计时的持续权威基线。
- `DeathEvent` / `RespawnEvent` / `KillEvent`：关键一次性结果，走有限可靠账本。

### 开火收据与有限重发

UDP 下，开火请求本身可能丢失。阶段 12A 加入：

```text
FireRequest(fireSequence)
-> FireReceipt(accepted, reason, serverTick)
```

收据的语义要说准确：`accepted=true` 仅表示服务器已接收并将请求放入开火队列，不表示已经命中、扣血或击杀；真正结算仍发生在下一次 `GameWorld.Tick()`。

客户端保存原始 JSON，约 0.2 秒没收到对应收据时以相同 `fireSequence` 重发，最多重发 3 次。服务器为每位玩家缓存有限数量的 `fireSequence -> FireReceiptDecision`；同一序号重发只回放第一次决定，绝不重复入队或伤害。

当前边界：不同 `fireSequence` 不构成严格有序可靠通道。若较新的序号先到，迟到的旧序号允许被拒绝为 `duplicate-or-out-of-order-fire`。这是一种“有限重发 + 去重 + 收据确认”语义，不应描述为“每一发严格按按键顺序可靠结算”。

关键代码位置：

- `UdpNetworkClient.SendFireRequest()` / `UpdatePendingFireRequests()` / `HandleFireReceipt()`
- `GameWorld.TryQueueFireWithReceipt()`
- `GameWorld.ResolveQueuedFireRequests()`

面试回答：

> 客户端只能请求开火，不能声明命中。为避免 UDP 丢失开火意图，我对同一个开火序号做有限重发，服务器缓存收据并去重；真正的射击、冷却、命中和伤害仍统一在服务器 Tick 内结算。

## 射击延迟补偿

问题：玩家 A 延迟较高时，A 在自己屏幕上看到 B 的位置与服务器当前看到 B 的位置不同。若服务器只用当前目标位置检测，A 会觉得“我明明瞄到了却没有命中”。

项目做法：

1. `GameWorld.StorePlayerHistory()` 每个 Tick 保存最近约 1 秒玩家历史状态。
2. 客户端开火时上报 RTT 估算和远端插值延迟。
3. `BuildLagCompensationFrame()` 计算回溯时间：

```text
rewindSeconds = estimatedRttSeconds + interpolationDelaySeconds
```

4. 服务器将回溯限制在最多约 0.35 秒，换算为 `hitTestServerTick`。
5. 命中检测读取该历史 Tick 的射手/目标状态，而非只读当前状态。

为什么限制最大回溯：若完全相信客户端上报的超大延迟，作弊客户端可以让服务器回到很久以前的位置来判定命中，对低延迟玩家不公平。

关键代码位置：

- `GameWorld.StorePlayerHistory()`
- `GameWorld.BuildLagCompensationFrame()`
- `GameWorld.GetPlayerFrameAtOrBefore()`
- `GameWorld.FindFirstHitPlayer()`

面试回答：

> 延迟补偿不是客户端决定命中，而是服务器保存短历史。收到延迟到达的开火请求后，服务器回看射手大概率看到的历史世界做检测，同时限制回溯窗口，兼顾高延迟玩家体验和公平性。

当前实现的简化点：RTT 主要由客户端估算后上报，服务器只做范围和最大回溯保护；历史帧按整数 Tick 取样；命中体是 2D 圆形半径；服务器没有地图障碍遮挡判定。

## 血量、死亡和重生

战斗状态只在 `GameWorld` 中维护：

- 最大血量：`MaxHealth`
- 单次伤害：`FireDamage`
- 存活状态：`IsAlive`
- 重生 Tick：`RespawnServerTick`
- 生命状态版本：`LifeStateVersion`

玩家死亡后，服务器将血量置零、停止其移动和开火命令、清空待处理命令，并设置未来的重生 Tick。重生时服务器恢复位置、朝向、血量和存活状态。死亡、重生都会把该玩家 `LifeStateVersion` 加一。

为什么血量必须进入快照：UDP 事件可能丢失。如果客户端只依赖一次 `HealthChangedEvent`，漏包后可能长期显示错误血量。快照持续携带血量、`isAlive` 与重生倒计时，任何后续快照都能把状态拉回正确结果。

面试回答：

> 血量、死亡和重生是服务器权威状态，快照负责持续恢复；事件只负责让客户端及时播放一次性表现。这样即使普通命中提示丢失，最终生命状态仍会收敛到服务器结果。

## 可靠关键结果事件

阶段 12B 为死亡、重生、击杀和预留的结算事件加入有限可靠语义，但没有把所有 UDP 消息都改成可靠有序通道。

### 消息分级

- `WorldSnapshot`：不可靠、可覆盖。新快照比旧快照更有价值。
- `FireEvent`、`HitEvent`、`HealthChangedEvent`：不可靠表现/观察事件。漏掉特效允许，不能承担权威状态。
- `FireReceipt`：确认开火意图是否被服务器接收并入队，不确认命中结果。
- `DeathEvent`、`RespawnEvent`、`KillEvent`、`MatchEndEvent`：带 `eventId`，有限 ACK、重发和去重。

### 服务端账本

每个 `ConnectedClient` 各有一个 `ReliableEventLedger`。账本保存原始 JSON、关联玩家、首次/上次发送时间、发送次数和重发次数；默认约每 250 ms 检查一次，最多重发 4 次。收到该客户端的 `EventAck` 后，只从该客户端自己的账本删除事件并记录 ACK 延迟。

快照不会因为等待可靠事件 ACK 而停止发送；可靠事件也不会阻塞后面的状态快照。

### 为什么 eventId 还不够

`eventId` 只能回答“这一条事件以前是否处理过”，不能回答“同一玩家的死亡和重生哪个更新”。UDP 可让 `RespawnEvent v3` 先到、`DeathEvent v2` 后到；两个事件 ID 都不同，单纯去重会错误地把已经重生的玩家切回死亡。

修复是每个玩家维护单调递增的 `lifeStateVersion`：

```text
死亡 v2 -> 重生 v3 -> 迟到死亡 v2
客户端只接受版本更高的生命周期结果，因此丢弃 v2。
```

`PlayerSnapshotMessage`、`DeathEventMessage` 和 `RespawnEventMessage` 都携带该版本。客户端按 `playerId` 记录已知最大版本，旧事件和旧快照均不能覆盖更新状态。

### Avatar 尚未创建时怎么办

UDP 事件可能比该玩家的第一份快照更早到达。旧做法若立刻记下 `eventId` 并 ACK、但找不到 Avatar，事件便会在表现层永久丢失。

当前做法是：客户端首次收到可靠事件后仍 ACK，随后按 `playerId` 缓存最新一条待应用的死亡/重生结果。`GetOrCreateRemoteAvatar()` 在快照创建 Avatar 后调用 `ApplyPendingLifecycleEventIfReady()`；若同版本或更新的快照已经恢复状态，缓存会被版本比较安全淘汰。

这体现了两个不同概念：

- 网络传输已确认：服务器可以停止重发。
- 业务状态已可表现：Unity Avatar 已存在，或客户端已把足够的结果缓存为待落地状态。

### 有限窗口边界

客户端 `RecentReliableEventIds` 默认只保留最近 128 个 ID。它的准确语义是“有限重发窗口内至多一次处理”，不是永久 `exactly-once`。当第 129 个不同事件到来，最旧 ID 会淘汰；一个极旧的重复包理论上可能再次被视为新包。该取舍依赖服务端有限重发次数、短会话和快照兜底。

关键代码位置：

- `ReliableEventLedger.QueueInitial()` / `CollectDueResends()` / `Acknowledge()`
- `UdpGameServer.SetReliableEventId()` / `HandleEventAck()`
- `UdpNetworkClient.ProcessReliableEvent()`
- `UdpNetworkClient.ApplyOrCacheDeathEvent()` / `ApplyOrCacheRespawnEvent()`
- `UdpNetworkClient.ShouldApplyLifecycleVersion()`

## 当前项目的真实简化点

这些不是需要掩盖的缺点，而是学习型实习项目的明确取舍。面试时主动讲清楚，比把“预留接口”说成已完成更专业。

1. 协议使用 JSON。
   - 优点：可读、可直接打印、适合学习与定位协议问题。
   - 缺点：包体较大、序列化开销高。
   - 后续：可在保持消息语义不变的前提下替换为 MessagePack 或 Protocol Buffers，并实测对比包体和 CPU。

2. 传输层使用 .NET `UdpClient`。
   - 优点：UDP 丢包、乱序、ACK、重发等细节可见，便于学习。
   - 缺点：连接管理和关键消息可靠性要自行实现。
   - 后续：可评估 LiteNetLib 或 KCP，但不能因此丢掉对消息分级的理解。

3. 可靠语义是有限的，不是通用可靠有序通道。
   - 关键结果已有 ACK、去重和有限重发；开火有收据和有限重发。
   - 开火不同序列乱序允许丢弃；去重窗口会淘汰旧 ID。
   - 后续：如玩法真的需要严格有序离散命令，应单独设计乱序窗口、超时和队头阻塞策略。

4. 当前不是实际差分同步。
   - `changeMask` 与 `isFullState` 已预留，但所有发送状态仍为全字段。
   - 原因：UDP 基线未经客户端确认时，差分包丢失会让之后状态无法还原。
   - 后续：先实现基线 ACK、超时全量回退和重连基线，再谈真正字段差分。

5. 兴趣管理是距离分级复制，不是完整 AOI。
   - 当前按距离和近期战斗状态决定范围与频率。
   - 未做视锥、遮挡、网格分区、跨区实体管理。

6. 远端没有速度外推。
   - 当前使用插值、分级延迟和断档保持。
   - 后续可加入有限时长外推，并严格限制最大时长。

7. 服务端命中与地图仍是简化模型。
   - 命中体是 2D 圆形半径。
   - 服务器尚未维护地图障碍、掩体遮挡、复杂碰撞或分部位 HitBox。
   - 后续引入地图时，障碍判定必须进入服务器权威逻辑，不能只依赖 Unity 客户端 Physics。

8. 延迟补偿仍是学习版。
   - RTT 主要由客户端估算并上报，服务器只做上限保护。
   - 历史状态按整数 Tick 读取，不做历史帧插值。
   - 后续可做服务器 RTT 估算、客户端/服务器时钟同步和更细粒度 HitBox 历史。

9. 尚未实现断线重连和完整对局服务。
   - 当前有 `ClientGoodbye` 正常退出与 8 秒静默超时清理。
   - 未做大厅、匹配、独立 BattleSession、重连后的全量基线与事件补偿。

10. 3C 和表现仍是验证级。
    - 当前用 Tank 验证网络闭环，尚未接入正式人物模型、第三人称相机、动画状态机和程序化武器表现。
    - 后续应先把逻辑与表现根节点分离，再逐步接入角色 3C，而不是让动画反向决定权威状态。

## 如果面试官问“为什么不用 Protobuf”

可以这样答：

> 我知道 JSON 不适合高频实时游戏的最终性能方案。第一版选择 JSON，是为了在学习阶段能直接打印和理解每个消息内容，先把 Tick、快照、预测、校正、事件可靠性和服务器权威做正确。后续可以把序列化层替换为 MessagePack 或 Protobuf；上层消息职责不变，只需要对比包体和序列化耗时。

## 如果面试官问“为什么不用现成网络框架”

可以这样答：

> 现成框架能更快完成联机功能，但会隐藏一部分同步细节。这个项目的目标是学习服务端权威状态同步，因此先基于 UdpClient 自己实现输入、快照、ACK、有限重发和事件去重。我会在后续项目中比较 KCP 或 LiteNetLib，但不会把框架调用当成已经理解同步原理。

## 如果面试官问“你的项目和真正商业游戏差在哪”

可以这样答：

> 这是实习展示级 Demo，重点是完整且可解释的服务端权威同步链路。和商业项目相比，它还缺少完整可靠有序通道、真正差分同步、复杂 AOI、服务器地图碰撞、二进制协议、断线重连、匹配房间、完善反作弊、正式角色动画和部署体系。但核心链路已具备：输入上报、固定 Tick 权威模拟、按客户端快照复制、本地预测校正、远端插值、服务器命中判定、延迟补偿、血量死亡重生、开火收据和关键结果事件的有限可靠语义。

## 五分钟讲解稿

> 这是一个 Unity 客户端加 .NET C# UDP 服务器实现的第三人称联机 Tank TPS Demo。我选择服务端权威状态同步：客户端不上传 Transform，只上报移动、转向、瞄准和开火意图；服务器以 30 Hz 固定 Tick 统一消费命令，维护位置、血量、死亡、重生和命中结果。这样客户端即使篡改本地位置，也无法改变服务器认可的世界状态。  
>  
> 为解决延迟下的操作手感，本地玩家按键后会立即做预测移动，并保存输入历史。服务器快照带回 `lastProcessedInputTick` 后，客户端删除已经确认的输入，从权威快照开始重放剩余输入，按误差大小进行平滑或硬校正。远端玩家不预测输入，而是维护服务器快照缓冲，故意延迟一点在历史快照之间插值，因此能吸收 UDP 到达间隔不稳定带来的抖动。  
>  
> 服务器端我把传输、权威世界、快照构建、按客户端复制和可靠事件账本拆开。UDP 收包不会直接扣血；它只把输入或开火转换为命令，`GameWorld` 在下一次 Tick 统一处理冷却、命中和伤害。开火请求带独立序号，客户端有限重发，服务器回收据并缓存决定，保证同一个开火序号不会重复入队。  
>  
> 射击命中由服务器判定。服务器每 Tick 保存约一秒历史状态，开火请求到达后会在受限窗口内回看历史位置做射线检测，解决高延迟玩家“看到命中却判空”的问题。客户端只播放 `FireEvent` 和 `HitEvent` 表现，血量和存活始终以快照为准。  
>  
> 对死亡、重生、击杀等一次性结果，我没有把全部 UDP 改成可靠通道，而是做了有限账本：事件带 `eventId`，客户端 ACK，服务器有限重发，客户端去重。之后又补充了每玩家 `lifeStateVersion`，避免 UDP 乱序导致“已经重生又收到旧死亡事件”的状态倒退；Avatar 尚未创建时，客户端缓存最新生命周期结果，等快照创建对象后再应用。  
>  
> 性能上，服务器不再对每个人广播同一份世界快照，而是为每个客户端按距离和近期战斗状态做高低频复制；当前仍保留全字段快照，不把未确认 UDP 包当差分基线。项目还提供 F3 调试面板和弱网测试入口，用于观察 RTT、快照丢失估算、预测误差、复制范围、开火收据和可靠事件遥测。后续我会在保持权威逻辑不变的前提下接入服务端障碍判定和角色 3C 表现。
