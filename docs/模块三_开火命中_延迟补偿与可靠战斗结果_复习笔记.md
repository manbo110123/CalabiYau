# 模块三：开火、命中、延迟补偿与可靠战斗结果复习笔记

> 复习重点：能讲清一发子弹从本地按下，到服务器判定命中、扣血、死亡重生的完整链路；能说清当前延迟补偿和可靠事件的边界。

---

## 一、整条战斗链路

```text
鼠标按下
-> 本地即时开火表现 + FireRequest
-> 未收到 FireReceipt 时有限重发
-> 服务器校验并放入 PendingFires
-> FireReceipt 确认“接收/入队”
-> 下一个 serverTick 结算冷却与命中
-> 查询历史状态做延迟补偿
-> 修改权威血量
-> Fire / Hit / HealthChanged 表现事件
-> Death / Kill 可靠事件
-> Tick 到达后 Respawn 可靠事件 + 快照兜底
```

**核心原则：** 客户端只表达“我想在这里开火”，服务器决定“是否实际开火、是否命中、扣多少血、谁死亡”。

---

## 二、一次真实的 FireRequest 如何发出

### 工作过程

本地按下鼠标后有两件事同时发生：

```text
TankController
-> TankWeapon.TryFire()
-> 立即播放本地子弹/开火表现

UdpNetworkClient.SendFireRequestIfPressed()
-> 读取 FirePressed 和当前瞄准点
-> 创建 FireRequest
-> 写入 pendingFireRequests
-> UDP 发送
```

请求包含：

```text
fireSequence：本次开火唯一序号
requestTick：按下开火时的本地输入 Tick
aimX / aimZ：瞄准的地面坐标
estimatedRttSeconds：输入确认延迟估算
interpolationDelaySeconds：基础远端插值延迟
```

若客户端在设定时间内未收到收据，会重发**同一个** `fireSequence` 的原始请求，最多 3 次。重发不是新开火，目的是让服务器至少能对这一请求做一次决定。

### 代码定位

- `Assets/Code/UdpNetworkClient.cs`：`SendFireRequestIfPressed()`、`QueueFireRequestForReceipt()`、`RetryPendingFireRequests()`。
- `Assets/Code/TankController.cs`、`TankWeapon.cs`：本地即时表现。

### 面试话术

> 玩家按下开火后，客户端先播放本地表现以避免输入滞后，同时发送带 `fireSequence`、`requestTick` 和瞄准点的 `FireRequest`。客户端会暂存请求，短时间未收到服务器收据时重发同一序号。这样 UDP 丢包不会轻易漏掉一次开火请求，而重复发送也不会被当成新的射击；客户端从始至终不上传命中对象和伤害结果。

---

## 三、FireReceipt 到底确认了什么

### 工作过程

服务器收到 `FireRequest` 后，`UdpGameServer` 先确认发送方已连接且 Endpoint 确实属于该 `playerId`；随后 `GameWorld.TryQueueFireWithReceipt()` 检查玩家是否存活、字段是否合法、请求 Tick 是否异常、序号是否重复/乱序、队列是否已满。

通过后：

```text
将 FireCommand 放入 PendingFires
缓存 fireSequence 对应的处理结果
回 FireReceipt(accepted=true, reason="queued")
```

同一个序号重传时，服务器返回缓存收据，不再重复入队。

最重要的区别：

```text
FireReceipt：服务器已接收并决定是否入队
FireEvent：服务器 Tick 中真正结算了一次开火
HitEvent：这次已结算的开火命中了目标
```

### 代码定位

- `Server/Server/UdpGameServer.cs`：`HandleFireRequestAsync()`。
- `Server/Server/GameWorld.cs`：`TryQueueFireWithReceipt()`。
- `Assets/Code/UdpNetworkClient.cs`：`HandleFireReceipt()`。

### 面试话术

> `FireReceipt` 不等于命中确认，它只表示服务器已经对该请求做出接收、拒绝或入队决定。服务器按 `fireSequence` 缓存首次结果，所以同一个 UDP 请求重传时只会返回同一份收据，不会多次加入开火队列。真正的冷却校验、命中检测和伤害修改都在后续固定 Tick 中完成。

---

## 四、服务器如何从命中走到死亡

### 工作过程

`GameWorld.Tick()` 先推进所有玩家的移动并保存历史状态，随后调用 `ResolveQueuedFireRequests()` 结算待开火请求：

```text
检查射手存活、冷却、瞄准合法性
-> 选择 hitTestServerTick
-> 查询射手和目标在同一个历史 Tick 的位置
-> 构造射线并检测最近目标
-> 命中：修改目标权威 Health
-> 生成 FireEvent、HitEvent、HealthChangedEvent

若 Health <= 0：
-> KillPlayer()
-> IsAlive = false，Health = 0
-> LifeStateVersion++
-> 设置 RespawnServerTick
-> 清空未消费输入和 PendingFires
-> 生成 DeathEvent、KillEvent
```

清空命令是为了避免玩家死亡前已经到达服务器、但还没来得及消费的移动或开火，在死亡后继续生效。

### 代码定位

- `Server/Server/GameWorld.cs`：`Tick()`、`ResolveQueuedFireRequests()`、`KillPlayer()`、`TryRespawnPlayer()`。

### 面试话术

> 服务器不会在收包回调里直接扣血，而是在 `GameWorld` 的固定 Tick 中统一结算。开火请求通过冷却和瞄准校验后，服务器使用历史状态重新做射线检测；命中时修改权威血量。血量归零会切换存活状态、递增生命版本、设置重生 Tick，并清空残留输入和待开火命令，避免出现死亡后移动或补发子弹。

## 五、延迟补偿：服务器回到哪个历史时刻

### 工作过程

高延迟玩家看到的远端目标是过去的位置。服务器每 Tick 在移动模拟后保存每个玩家的位置、朝向、瞄准和存活状态，默认保留约 `1 秒`、即 30Hz 下约 30 帧；开火时只查询历史表，不会真的让当前世界回滚。

`estimatedRttSeconds` 的当前测量过程是：快照确认某个 `inputTick` 后，客户端用“当前收到快照的时间 - 该输入发送时间”得到一次输入端到端确认延迟，再以 `Lerp(旧值, 新样本, 0.2)` 平滑。若尚无测量样本，才用“未确认输入数 / 30Hz”作临时估算；连权威快照也尚未收到时，当前只能上报 0。

当前回溯公式：

```text
requestedRewindSeconds
= estimatedRttSeconds + interpolationDelaySeconds

rewindSeconds
= min(requestedRewindSeconds, 0.35 秒)

rewindTicks
= round(rewindSeconds * serverTickRate)

hitTestServerTick
= 当前 serverTick - rewindTicks
```

回溯最终只能落在离散服务器 Tick 上；30Hz、最大 350ms 时约回溯 10 Tick，具体取整由 `MathF.Round` 决定。

例子：输入确认延迟 `0.18s`，基础插值延迟 `0.10s`，服务器为 `30Hz`：

```text
请求回溯 = 0.28s
回溯 Tick = round(0.28 * 30) = 8
当前 Tick 300 -> 在 Tick 292 检测
```

服务器从同一个 `hitTestServerTick` 读取射手和目标状态，再做二维射线-圆形检测。请求瞄准还需与服务器当前或历史已知瞄准足够接近；`eventId`、`requestTick` 都不直接参与该公式，`requestTick` 当前主要用于拒绝过旧或过于超前的请求。

服务器会先限制客户端上报的 RTT 和插值延迟范围，最后仍以 `0.35 秒`限制实际回溯。若关闭 `EnableLagCompensation`，回溯时长直接为 0，按当前服务器状态检测。

### 参数记忆

| 参数 | 当前项目的来源/含义 |
| --- | --- |
| `estimatedRttSeconds` | 输入发送到快照确认返回的平滑端到端时间，不是纯 Ping |
| `interpolationDelaySeconds` | 客户端基础远端插值延迟，默认约 `0.1s` |
| `rewindSeconds` | 经过最大 `0.35s` 限制后的实际回溯秒数 |
| `rewindTicks` | 回溯秒数换算出的服务器历史 Tick 数 |
| `hitTestServerTick` | 本次历史命中检测真正查询的 Tick |

### 面试话术

> 为解决高延迟下“客户端看见准星对准，服务器却按目标当前坐标判空”的问题，我在服务器保存有限历史状态。开火时用客户端测得的输入确认延迟和基础插值延迟估算回溯时长，限制在 350ms 内并换算为历史 Tick；服务器从同一历史 Tick 查询射手和目标状态，再重新做服务器射线检测。整个过程只查询历史数据，不回滚当前服务器世界。

## 六、消息分级与可靠生命周期

### 工作过程

```text
FireEvent / HitEvent / HealthChangedEvent
-> 可丢失的表现或提示
-> WorldSnapshot 持续同步 Health、IsAlive 等权威基线

DeathEvent / RespawnEvent / KillEvent / MatchEndEvent
-> eventId
-> 客户端去重并回 ACK
-> 服务器每 0.25s 有限重发，最多 4 次
```

服务器为每个接收客户端维护独立的待确认事件账本；客户端即使收到重复事件，也不会重复应用，但仍会回 ACK，让服务器停止重发。

`eventId` 只能防“同一个事件重传多次”。死亡和重生是两个不同事件，仍可能乱序，因此每次死亡和重生都会递增 `lifeStateVersion`。客户端只应用更高版本，避免旧死亡覆盖已生效的重生。

若可靠生命周期事件早于 Avatar 创建到达，客户端会先按玩家 ID 缓存，之后创建 Avatar 时补应用；事件已被逻辑层保存，所以可以正常 ACK。

### 面试话术

> 我没有把所有战斗消息都做成可靠消息。命中特效和血量提示即使丢失，后续快照仍会把权威血量和存活状态同步回来；死亡、重生、击杀和结算会改变生命周期，因此使用每客户端 ACK、有限重发和 `eventId` 去重。针对死亡重生乱序，再用递增的 `lifeStateVersion` 保证客户端只接受更新的生命状态。

## 七、当前边界与后续优化

### 延迟补偿

- `estimatedRttSeconds` 是完整输入确认延迟，不是精确一程时延；当前公式是近似估算，可能过回溯或少回溯。
- RTT 和插值延迟由客户端上报，服务器虽有范围和最大回溯限制，但尚未能完全信任或独立推导这些值。
- `requestTick` 只做时序合法性校验，尚未精确映射到服务器 Tick。
- 历史状态按 30Hz 离散保存，取目标 Tick 或更早最近帧，没有帧间插值。
- 当前只做二维射线-圆形检测，没有服务器地图遮挡、Collider 回溯或骨骼命中盒。

**优化方向：** 建立客户端/服务器时钟映射，服务器推导可信开火时间；补服务器障碍物碰撞后，再升级 Collider 或命中盒历史回溯。

### 低频复制与回溯估算

远端实体低频复制时，`NetworkTankAvatar` 会增大实际插值延迟；但 `FireRequest` 当前只发送基础 `0.1s`，没有携带目标实际的有效延迟。因此射击低频远端实体时，服务器可能少回溯，仍可能发生“客户端看似瞄准、服务器判空”。

**优化方向：** 由服务器根据复制节奏和时间同步推导显示延迟，或让客户端补充上报实际有效延迟；前者更可信。

### 开火与可靠事件

- `FireReceipt(queued)` 后，真正 Tick 结算仍可能因冷却拒绝；当前没有按 `fireSequence` 回发最终 `FireResult`。
- 本地即时子弹和自己的 `FireEvent` 可能重复播放，需要运行时确认。
- 同一序号重传能去重，但不同开火序号乱序时，旧序号会被拒绝，不是严格有序可靠开火。
- 可靠事件是有限重发，不是永久送达；断线重连后的事件补偿未实现。

**优化方向：** 增加 `FireResult`，将本地预测特效和服务器结果按序号合并；后期再做有限序号窗口、断线重连事件流补偿。

## 八、本模块重点疑惑回顾（保留我的实际提问）

### 1. `FireReceipt` 是不是代表子弹已经命中？

不是。它只确认服务器对开火请求作出了接收/拒绝/入队决定；`FireEvent` 才表示服务器实际结算开火，`HitEvent` 才表示命中特效。

### 2. 延迟补偿是不是把服务器整个回滚？

不是。服务器当前世界继续向前，只查询射手和目标在同一个历史 Tick 的保存状态，临时完成命中检测。

### 3. 我的问题：这些参数分别是什么意思，怎么计算的？

```text
estimatedRttSeconds：客户端发送某条输入，收到确认该输入的快照后，
                     用“快照到达时间 - 输入发送时间”测得；再用 0.2 的 Lerp 平滑。
                     它是输入端到端确认延迟，不是纯 Ping。

interpolationDelaySeconds：客户端播放远端历史快照的基础延迟，当前约 0.1 秒。

requestedRewindSeconds：estimatedRttSeconds + interpolationDelaySeconds，
                        即当前希望回到多久以前。

rewindSeconds：requestedRewindSeconds 经最大 0.35 秒限制后的实际回溯时间。

rewindTicks：round(rewindSeconds * 服务器 TickRate)，30Hz 时把秒数换成历史帧数。

hitTestServerTick：当前 serverTick - rewindTicks；服务器在该 Tick 查询射手和目标的历史状态。
```

### 4. 为什么 `eventId` 之外还需要 `lifeStateVersion`？

`eventId` 防同一事件重复，`lifeStateVersion` 防不同死亡/重生事件乱序。重生版本更高时，迟到的旧死亡不会覆盖它。

### 5. Avatar 尚未创建，为什么事件 ACK 后不会丢？

因为客户端会先缓存生命周期事件。ACK 表示客户端已经安全保存业务状态，等 Avatar 出现后再补应用，而不是直接丢弃。

---

## 九、60 秒模块总结

> 本地玩家开火时立即播放表现，同时发送带序号和瞄准信息的 `FireRequest`；客户端未收到收据会有限重发同一序号，服务器去重后将请求放入待处理队列。服务器在固定 Tick 中检查冷却和瞄准，并根据输入确认延迟与插值延迟查询射手和目标的同一历史 Tick，重新完成服务器命中判定。命中后由服务器修改权威血量，表现类事件可丢失并由快照兜底；死亡、重生、击杀等生命周期结果使用 ACK、有限重发、去重和生命版本防止丢失或乱序。当前仍有回溯时间近似、低频插值延迟未准确纳入、二维命中和有限可靠等边界。
