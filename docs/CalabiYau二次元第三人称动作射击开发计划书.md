## 0. 这份计划怎样使用

这份文档现在定位为**架构总纲与技术路线图**：用来说明项目最终要去哪里、阶段间为什么这样排序，以及网络、移动、相机、动画和技能采用什么原则。它不是要求 3C 新手直接照着 R0～R12 独立完成的操作教程。

实际开发请从 [3C 开发陪练手册：总目录与协作方式](3C开发陪练手册/00_总目录与协作方式.md) 进入。陪练手册已将本计划拆成 S00～S38 共 39 次可单独开启对话的小课，每课都会写清：

- 你开始前需要准备的模型、动作、截图或验收环境；
- Unity 中的菜单路径、Hierarchy 操作、组件添加、字段拖拽和建议初值；
- 由我检查、设计和编写的代码；
- 本课代码需要理解的核心含义；
- 自动测试、人工操作、双客户端和弱网验收；
- 完成记录与下一课进入条件。

当前只需阅读陪练手册总目录和 S00，不需要先看懂本文全部架构内容。

这不是一张需要一次性全部完成的功能清单，而是后续每轮学习、设计、实现、测试和复盘的总路线。

使用规则：

1. 每次只开启一个小阶段；不要同时改输入、人物碰撞、相机、动画和网络协议。
2. 每个阶段先回答“解决什么问题、谁有权决定、同步什么、怎样验收”，再修改代码。
3. 每个玩法都按“本地最小实现 -> 权威规则 -> 本地预测/校正 -> 远端表现 -> 弱网验证”闭环推进。
4. 自动测试通过只代表规则层通过；画面、手感和双客户端仍需人工验收。
5. 文档中的“计划”“候选”“进入条件”不等于已经实现。完成状态只由当前代码、测试和人工验收共同决定。
6. 旧 Tank 版本在人物主线稳定前保留为回归基线，不边迁移边删除所有旧实现。

推荐每轮对话只处理如下粒度：

```text
一个概念
-> 一个最小设计
-> 一组相关文件
-> 一次编译/自动测试
-> 一个离线或双客户端验收场景
-> 一页复盘记录
```

本文参考了 ElementWar 的《3C 与网络同步项目开发路线》和 CalabiYau `docs` 中的现有规划、实现记录与复习文档。参考文档用于提供思路；本计划的项目事实以 2026-08-29 的 CalabiYau 代码、包清单、场景和最新阶段记录为准。

## 1. 项目最终定位

CalabiYau 不再继续扩张为“拥有许多网络名词的 Tank Demo”，而是逐步变成一个小而完整的联网动作射击垂直切片：

> 在现有服务器权威网络底座上，实现一个有明确二次元视觉风格、操作响应及时、远端表现平滑、弱网下最终一致的第三人称角色战斗 Demo。

项目最终重点证明三类能力：

1. **3C 能力**：角色运动、相机、瞄准、动画、射击、动作状态和反馈能够共同形成手感。
2. **网络同步能力**：人物移动、开火、技能和生命周期仍遵守服务端权威、本地预测、校正重放和远端插值。
3. **工程解释能力**：能用调试数据、自动测试、弱网记录和问题复盘解释方案，而不是只展示画面。

### 1.1 P0：第一个可展示垂直切片

- 一名来源和许可清楚的二次元人物角色；
- 一张小型竞技训练场；
- 两个客户端进入同一权威世界；
- 八方向移动、瞄准移动、跳跃和一个冲刺动作；
- 第三人称环绕相机、相机防穿墙、越肩瞄准和肩位切换；
- 一把完整的 Hitscan 武器；
- 弹药、换弹、射速和服务器权威伤害；
- 基础移动动画、瞄准动画、开火、受击、死亡和重生表现；
- 本地预测、服务器校正、输入重放和远端插值；
- 静态地图权威碰撞、枪口遮挡和有限延迟补偿；
- 调试面板、碰撞/射线 Gizmo 和弱网测试记录；
- 一段能清楚展示正常网络与 100/200 ms 条件的演示。

### 1.2 P1：垂直切片之后的动作射击扩展

- 数据驱动的最小技能框架；
- 将 P0 冲刺整理进最小数据驱动技能框架；
- 一个权威投射物技能；
- 一个持续范围技能；
- 上半身动画层、Aim Rig、手部 IK；
- 更细的角色伤害 HitBox；
- 命中、后坐力、相机震动、音效和特效的完整反馈；
- 简单比分/胜负与重开一局；
- 机器人或录制输入，用于 2/4/8/16 人的基础压测。

### 1.3 P2：暂时不做

- 大量角色、武器、皮肤、地图和技能；
- 完整大厅、匹配、账号、数据库和云部署；
- 大世界、复杂 PvE、任务和养成；
- 自研完整刚体物理引擎或渲染管线；
- 在没有测量瓶颈前做多线程分片、复杂 AOI、位打包或更换网络框架；
- 为了“像商业项目”而提前制造没有玩法调用者的抽象层。

### 1.4 两个合理收口点

| 收口点 | 内容 | 用途 |
| --- | --- | --- |
| MVP 收口 | 人物、相机、动画、Hitscan、跳跃、冲刺、双客户端和弱网闭环 | 已经可以作为完整的联网 TPS 作品展示 |
| 扩展收口 | 再加入投射物、范围技能、细分 HitBox 和压测数据 | 展示动作系统、技能同步和更深的网络研究 |

如果时间或精力有限，应优先完成 MVP 收口，不要留下十个半成品系统。

### 2.4 代码层的迁移风险

- `UdpNetworkClient.cs` 约 2600 行，直接引用 `TankController`、`NetworkTankAvatar`、Tank 碰撞和所有协议 DTO；人物化时不能继续把所有职责塞进去。
- `NetworkTankAvatar.cs` 同时负责网络状态、插值、校正、Rigidbody、炮塔瞄准、血量、材质反馈和世界空间 GUI。
- `GameWorld` 的人物状态目前只有位置、车身 Yaw、地面瞄准点、血量和生命状态；没有速度、竖直速度、Grounded、移动模式或动作状态。

- 当前 `Player.cs` 是旧单体 Tank 脚本；迁移期间只作为历史代码，不应成为人物系统入口。
- 项目当前包清单没有 Input System、Cinemachine 和 Animation Rigging。应按阶段逐个引入并验证，不一次安装后同时开工。

## 3. 核心技术决策

### 3.1 网络架构：保留 UDP + JSON，先完成玩法

人物化阶段不同时更换网络框架、序列化协议和服务器形态。原因是这些变化不能直接改善 3C 手感，却会让所有问题难以归因。

进入二进制协议优化的条件：

- 人物垂直切片已经稳定；
- 已记录每秒包数、平均/峰值快照字节、序列化 CPU 和 GC；
- 数据证明 JSON 已经成为可见瓶颈。

### 3.2 输入：使用 Unity Input System，但网络层只接收普通命令数据

推荐引入 Input System，因为它适合组织 Move、Look、Aim、Jump、Fire、Reload、Dash 和肩位切换，也便于键鼠/手柄并存。

边界：

- Input Action 只存在于本地采样层；
- 模拟层不读取 `Keyboard.current`、`Mouse.current` 或 `PlayerInput`；
- 网络和测试只认识普通的 `CharacterInputCommand`；
- Pressed、Held、Released 必须在采样层变成明确边沿或序列号。

### 3.3 相机：Cinemachine 管镜头表现，自有 AimSolver 管瞄准语义

推荐在相机阶段引入与 Unity 2022.3 兼容的 Cinemachine 版本，用它处理跟随、轨道、阻尼、肩位和相机碰撞。这样能把学习精力集中到 TPS 瞄准、角色朝向和网络边界。

Cinemachine 不负责：

- 决定服务器 Aim；
- 直接修改角色权威位置；
- 决定伤害；
- 代替枪口遮挡检查。

`AimSolver` 负责把屏幕中心、相机射线、目标点、枪口方向和压缩后的 Aim Yaw/Pitch 联系起来。

如果选择自写相机，也必须保持同样的接口边界；不要让 `Camera.main` 散落在角色模拟和网络代码中。

### 3.4 人物移动：共享轻量 Kinematic Motor，而不是两套不同规则

现有服务器是独立 .NET 进程，无法直接运行 Unity `CharacterController` 或 PhysX。因此正式联网人物移动推荐继续走共享纯 C# 模拟：

```text
CharacterInputCommand
-> CharacterCommandSimulation
-> CharacterMotor / WorldQueries
-> CharacterState
```

Unity 客户端、服务端 `GameWorld` 和未确认输入重放调用同一公式。Unity 组件只负责转换数据和显示结果。

`CharacterController` 可以用于一次短小的手感实验，但不能成为最终客户端规则后再让 .NET 服务器写一套近似规则；那会在斜坡、台阶、跳跃和碰撞边缘产生持续分叉。

### 3.5 动画：第一版使用 In-Place，Root Motion 不拥有权威位移

第一版人物位移由代码模拟，Animator 读取速度、方向、Grounded、Aim 和动作状态。

Root Motion 只在以下条件满足后研究：

- 基础移动网络闭环已经稳定；
- 某个特殊动作确实需要动画位移；
- 可以把 Root Motion 转换为每 Tick 的“期望位移”，再经过同一权威碰撞；
- 预测重放不会推进 Animator 或重复产生表现副作用。

### 3.6 二次元风格：先保证角色可读性，再做渲染装饰

第一版使用 URP、清楚的角色轮廓、统一色调和可靠的角色资源许可。不要在移动和瞄准尚未完成时自研复杂卡通渲染。

推荐顺序：

```text
灰盒角色与相机比例
-> 正式模型和基础材质
-> 动画与武器轮廓
-> 简单描边/明暗分区
-> VFX、UI 和色彩统一
```

### 3.7 技能数据：权威数值不能只放在 ScriptableObject

独立 .NET 服务器不能读取 Unity `ScriptableObject`。因此：

- 冷却、伤害、位移速度、持续 Tick 等权威参数放在共享纯 C# 定义或版本化配置中；
- ScriptableObject 可以保存动画、音效、特效、图标和客户端展示参数；
- 两端通过稳定 `abilityId` 与 `gameplayRevision` 对齐；
- 地图和技能数据复杂后再制作 Unity Editor 导出器，不手工维护两份权威数值。

## 4. 目标架构

### 4.1 数据流

```text
Input System / Bot / Replay
          │
          ▼
CharacterInputCommand（Tick、二维移动、Aim、按键边沿）
          │
          ▼
CharacterCommandSimulation（共享纯 C#）
          │
          ├───────────────┐
          ▼               ▼
CharacterState       GameplayEvents
位置/速度/地面/动作     开火/命中/技能结果
          │               │
          ├──────┬────────┘
          ▼      ▼
网络快照/校正    本地与远端表现事件
          │
          ▼
CharacterPresentation
模型、Animator、Rig、VFX、Audio、UI、Camera
```

### 4.2 角色层级

```text
PlayerEntity（网络实体/组合根）
├─ LogicRoot
│  ├─ CharacterMotorProxy
│  └─ AuthoritativeBodyDebug
├─ VisualRoot
│  ├─ CharacterModel
│  ├─ Animator
│  ├─ Rig
│  ├─ WeaponSocket
│  └─ Muzzle
├─ CameraTarget
├─ AimTarget
├─ GameplayBody
└─ WorldSpaceUIAnchor
```

职责：

- `LogicRoot` 保存当前模拟认可的位置和朝向；校正首先改变它。
- `VisualRoot` 只做模型、动画和视觉平滑；不把 Transform 回写给逻辑状态。
- `CameraTarget` 可以对 LogicRoot 做本地平滑，避免相机直接吃到网络校正尖峰。
- `GameplayBody` 是根碰撞/权威移动形状；骨骼 HitBox 只服务于伤害查询。
- 本地和远端可以复用同一表现 Prefab，但输入、预测和插值驱动方式不同。

### 4.4 最小输入与状态

候选 `CharacterInputCommand`：

```text
inputTick
moveX / moveY
lookYaw / lookPitch 或 aimYaw / aimPitch
buttonBits：JumpHeld、AimHeld、SprintHeld 等
jumpSequence / dashSequence / reloadSequence（离散动作需要去重时）
```

候选 `CharacterState`：

```text
serverTick / lastProcessedInputTick
position
horizontalVelocity / verticalVelocity
facingYaw
aimYaw / aimPitch
isGrounded
movementMode（Grounded / Airborne / Dash / Disabled）
actionId / actionStartTick / actionPhase
health / isAlive / lifeStateVersion
```

不要同步：

- Camera Transform；
- 每根骨骼 Transform；
- Animator 每个参数；
- 本地相机震动、准星扩散动画和普通 UI 过渡；
- 客户端自行认定的最终命中、伤害和位置。

### 工作项

- 将 `moveAxis/turnAxis` 升级为 `moveX/moveY` 与人物 Facing/Aim 语义；
- 在协议握手增加明确 `protocolVersion` 和 `simulationRevision`，旧客户端应明确拒绝；

- 第一版人物足迹用 Circle2D，复用已有静态地图的边界、墙体查询和测试思想；
- 服务器、客户端即时预测、未确认输入重放调用同一人物平面模拟；
- 本地模型优先响应，远端模型继续使用快照插值；
- 快照增加水平速度、Facing Yaw、Aim Yaw 等动画将来需要的语义字段；

### 移动模式先固定

- 非瞄准：移动方向决定人物朝向；
- 瞄准：人物朝向 Aim Yaw，移动允许前后左右；
- 此时不做跳跃、坡道和 Root Motion；
- 冲刺留到 R9，避免把移动与技能一起调试。

### 自动测试

- 零输入、单位输入、斜向输入归一化；
- 加速/减速不会因帧率改变总结果；
- Circle 正面阻挡、斜向滑墙、墙角和边界；
- 30 Hz 与 50 Hz 外层步长通过共同微步得到足够接近的位姿；
- 服务器从异常移动输入中拒绝 NaN、Infinity 和范围外数值；
- 权威快照加未确认命令重放得到预期状态。

### 人工验收

- 0/100/200 ms 下本地移动立即响应；
- 两个客户端看到一致的墙边位置；
- 远端人物在高低频复制切换时不持续抖动；
- 持续顶墙不会让校正次数无限增长；
- F3 能显示移动模式、速度、预测误差和 Logic/Visual 偏移。

### 完成标准

人物已经替代 Tank 完成第一个“输入 -> 预测 -> 服务器 -> 快照 -> 重放 -> 插值”的闭环。没有这个闭环，不进入复杂相机和 3D Motor。

## R5：人物 3D Capsule、地面、斜坡、台阶与跳跃

这是从 Tank 2D 原型进入真正人物 3C 的最大技术阶段，应拆成 R5.1--R5.4，不能一次写完。

### R5.1：3D 数学和查询基线

- Vec3、Plane、AABB/OBB、Capsule；
- Raycast、Capsule Overlap 和 Capsule Sweep；
- 接触点、法线、距离/Time of Impact；
- 统一 epsilon、skin width、最大迭代和异常输入保护。

验收：分离、接触、穿透、斜面、内部起点、极小位移和高速位移有纯 C# 测试；尚不接网络。

### R5.2：地面与斜坡

工作项：

- Ground Probe 获取地面距离和法线；
- 用 `dot(normal, up)` 判断最大可走坡度；
- 可走坡面将期望移动投影到平面；
- 陡坡按墙体阻挡或滑落；
- Ground Snap 处理下坡短暂悬空；
- 记录 Grounded、groundNormal 和 verticalVelocity。

验收：平地稳定、缓坡可走、陡坡不可走、坡顶/坡底不明显弹跳，30/60/144 FPS 观感一致。

### R5.3：台阶、重力和跳跃

工作项：

- 有限 Step Offset：仅允许低于配置高度的台阶；
- 上台阶和下台阶分别处理；
- 重力、起跳速度、下落和着地；
- Coyote Time 与 Jump Buffer 先作为 P1 手感项，可在基础规则稳定后加入；
- 低天花板阻止继续上升；
- Jump Pressed 使用明确序列/边沿，重放不能多跳。

验收：不能爬高墙、不能穿低顶、台阶不卡顿、落地状态稳定、丢失松键不会无限跳。

### R5.4：权威、预测和弱网闭环

工作项：

- 服务器 `CharacterState` 加入 Y、竖直速度、Grounded 和移动模式；
- 快照和本地历史保存重放必需的完整状态；
- 服务端、即时预测、输入重放使用同一 Motor；
- LogicRoot 立即应用重建状态，VisualRoot 消化位置偏差；
- 相机跟随专用平滑目标，不直接追逐校正偏移；
- 地图握手升级为 3D map/simulation revision；
- 增加坡面、台阶、跳跃、低顶和边缘的服务器测试。

人工验收矩阵：正常网络、100/200 ms、少量抖动/丢包；分别测试上坡、下坡、贴墙跳、台阶、平台边缘和低顶。

### 完成标准

- 人物 Capsule、斜坡、台阶和跳跃由服务器最终裁决；

## R6：人物模型和动画表现

### 需要学习

- Humanoid Avatar 和动画重定向；
- Animator Controller、Blend Tree、Layer、Avatar Mask；
- 逻辑状态与动画状态不一一对应；
- Aim Rig、手部 IK 和执行顺序；
- 远端动作怎样从状态与开始 Tick 重建。

### 推荐顺序

1. Idle/Walk/Run 的 In-Place Blend Tree；
2. 瞄准状态下二维八方向移动；
3. 起跳、上升、下落、落地；
4. 上半身持枪层；
5. 开火、换弹、受击、死亡；
6. 基础 Animator 稳定后再安装并验证 Animation Rigging；
7. 最后加入 Aim Rig 和手部 IK；
8. Turn In Place、脚 IK 和 Motion Warping 只作为 P1。

### 动画输入

Animator 驱动器从模拟/快照读取：

- 局部前后速度；
- 局部左右速度；
- 速度比例；
- Grounded；
- verticalVelocity；
- isAiming；
- actionId、actionStartTick；
- isAlive。

Animator 不决定：

- 角色最终位置；
- 是否命中、扣血或死亡；
- 服务器动作开始时间；
- 技能是否因冷却而合法。

### 完成标准

- 移动方向与动画方向一致，脚滑处于可接受范围；
- 网络校正不会重新进入动画状态或重复触发开火；
- 本地动作反馈及时，远端动作开始时间合理；
- 关闭 Animator 后核心模拟、碰撞和服务器测试仍可运行；
- 死亡/重生乱序不会让动画状态倒退。

## R7：完整第三人称 Hitscan 武器

### 需要学习

- Hitscan 与视觉曳光的区别；
- 准星射线、目标点、枪口射线；
- 射速的 Tick 表达、弹匣、备弹和换弹状态；
- 服务器权威命中与客户端预测表现；
- 三维历史命中体与延迟补偿。

### 推荐射击流程

```text
本地屏幕中心射线取得目标点
-> 枪口到目标点做本地遮挡预览
-> 立即播放后坐力、枪声、枪口火焰和曳光
-> 发送带 fireSequence/requestTick/Aim 的 FireRequest
-> 服务器按权威位置、状态、弹药和射速校验
-> 服务器构造权威枪口射线并比较静态墙/角色命中距离
-> 在有限历史窗口内裁决命中
-> 返回 FireResult、Hit/Health/Lifecycle 状态
-> 客户端按 fireSequence 去重并修正表现
```

### 工作项

- 将当前地面 `aimX/aimZ` 升级为三维 Aim 语义；
- 服务端枪口由权威根位置、角色姿态和武器定义推导，不能信任客户端 Origin；
- 相机只帮助选择目标，最终射线必须从枪口/权威枪口出发；
- 增加弹匣、备弹、换弹开始 Tick 和换弹结束 Tick；
- 服务器验证射速、弹药、换弹、死亡、眩晕/动作互斥；
- 第一版命中使用根 Capsule；稳定后再进入 R11；
- 视觉子弹明确作为 Tracer，不再伪装成真实物理子弹；
- 本地立即表现与权威 FireEvent 使用同一 `fireSequence` 对齐；
- 增加墙面命中、玩家命中、未命中的不同反馈。

### 完成标准

- 贴墙时不能利用相机隔墙射击；
- 低帧率下射速和换弹时间由 Tick 保持正确；
- 修改本地弹药、射速或枪口位置不能改变服务器事实；
- 100 ms RTT 下开火反馈立即，权威伤害随后收敛；
- 200 ms 与少量丢包下不重复开火、伤害或死亡；
- 延迟补偿开关有可视化、可重复的对比用例。

## R9：动作状态与可预测冲刺

先用一个真实动作发现需求，再抽象通用技能框架，避免一开始制造复杂 Ability System。

### 需要学习

- 动作优先级、互斥、打断和取消窗口；
- 位移技能的预测、确认、拒绝和校正；
- Sweep 与沿墙滑动；
- 动作开始 Tick 和阶段重建。

### 最小动作状态

```text
Free
-> Windup（可选）
-> Active
-> Recovery
-> Free / Cooldown
```

### 工作项

- 定义 `actionId/actionStartTick/actionPhase`；
- 定义冲刺方向、速度曲线或每 Tick 位移规则；
- 本地按键立即预测冲刺；
- 服务器验证冷却、存活、地面/空中规则和方向；
- 冲刺位移经过 Capsule Sweep，撞墙停止或沿墙滑动；
- 未确认输入重放包含冲刺状态；
- 服务器拒绝时撤销状态并柔和终止表现；
- 远端通过动作开始 Tick 与位姿快照看到连续冲刺；
- 死亡、受控或更高优先级动作可以打断冲刺。

### 完成标准

- 0/100/200 ms 下本地冲刺立即响应；
- 撞墙不会穿透或无限校正；
- 重放不会重复消耗次数、重复音效或生成多个特效；
- 远端不表现为纯瞬移；
- 能清楚解释冲刺为什么属于模拟状态，而不只是一个动画 Trigger。

完成冲刺后，项目达到建议的 MVP 收口点。

## R10：最小技能框架、投射物和持续范围技能

### 抽象原则

只有冲刺暴露出真实需求后，再提取：

- 稳定 abilityId；
- 冷却和资源；
- 前摇/生效/后摇 Tick；
- 移动与转向许可；
- 优先级、打断和取消标签；
- 预测策略；
- 服务器权威效果；
- 表现资源引用。

避免用一个巨大 `switch` 塞入所有技能，也避免为了“通用”引入反射、ECS 或复杂依赖注入。

### 投射物技能

- 客户端立即生成带 predictionKey 的预测表现；
- 服务器生成权威投射物实体并按 Tick 推进；
- 使用 Sweep 防止高速穿透；
- 权威实体返回后与预测表现匹配，不显示两个；
- 爆炸范围和伤害由服务器只结算一次；
- 远端只根据生成/状态/销毁语义显示；
- 服务器和客户端调试面板显示投射物 ID、出生 Tick 和匹配状态。

### 持续范围技能

- 服务器权威创建和销毁区域；
- 周期效果按 Tick，不依赖客户端帧率；
- 维护进入/离开集合与重复伤害间隔；
- 快照携带 abilityId、owner、位置、startTick、duration；
- 晚加入或远端重新进入兴趣范围时可恢复剩余表现；
- 客户端 VFX 只显示，不决定目标集合。

### 完成标准

- 新增第三个技能时主要增加定义与小行为模块；
- 冷却、资源不足和非法状态会被服务器拒绝；
- 预测对象可以确认、拒绝和超时回收；
- 弱网下不会重复扣资源、重复伤害或双生成；
- 投射物和持续区域都有生命周期自动测试。

## R11：人物 HitBox 与延迟补偿升级

### 分级路线

1. **P0 根 Capsule**：移动体同时作为伤害粗判，先保证正确性。
2. **P1 头/躯干简化 HitBox**：头部 Sphere、躯干 Capsule/OBB；用于爆头或伤害倍率。
3. **研究项：姿态历史**：只在动画与姿态语义稳定后，研究历史 HitBox 重建。

### 关键难点

独立 .NET 服务器没有 Animator 和完整骨骼。不能简单把 Unity 客户端当前骨骼位置上传后当作权威历史。

可行演进：

- 服务器先保存根 Capsule 历史；
- 再保存少量可验证的姿态语义，如站立/下蹲、Aim Pitch、动作 ID 和开始 Tick；
- 服务端用简化规则重建头/躯干 HitBox；
- 只有数据和收益足够明确时才增加更细部位。

### 完成标准

- 静态墙、角色根 Capsule 和部位 HitBox 的最近命中顺序明确；
- 历史回溯不允许穿过当前一直存在的静态墙；
- HitBox Gizmo 能显示当前与回溯 Tick；
- 服务端没有收到并信任客户端骨骼矩阵；
- 文档准确说明当前是根碰撞、简化姿态还是完整部位历史。

## 9. 高风险清单与对策

### 9.1 一次性重写网络客户端

风险：`UdpNetworkClient` 当前承担过多职责，一次重写会同时破坏协议、预测、事件和调试。

对策：先增加人物驱动接口和独立组件；每迁移一条数据流就跑现有回归。等人物闭环稳定后再删除 Tank 专用入口。

### 9.2 客户端 CharacterController、服务器简化位移

风险：斜坡、台阶、边缘和跳跃产生两套不同规则，弱网下持续校正。

对策：正式联网使用共享 Kinematic Motor；Unity Physics 只做表现/环境辅助查询时也要明确权威数据来源。

### 9.3 模拟依赖 Animator/Root Motion

风险：服务器和输入重放没有 Animator，动画帧率会改变玩法结果。

对策：基础移动使用代码驱动；特殊位移先转换为按 Tick 可重放的期望位移。

### 9.4 逻辑状态等于动画状态

风险：动画过渡反向控制玩法，状态数量膨胀。

对策：`MovementMode/ActionState` 是玩法语义；Animator 可以用多个视觉状态表达一个玩法状态。

### 9.5 Animation Event 结算权威伤害

风险：无 Animator 服务器、掉帧和重放会产生不同结果。

对策：服务器 Tick/动作时间线结算；Animation Event 只用于脚步、音效、VFX 等表现提示。

### 9.6 直接同步 Transform 或 Animator 参数

风险：本地延迟、远端抖动、带宽浪费，且难以校正。

对策：同步命令和语义状态；本地预测，远端插值，动画从状态重建。

### 9.7 相机射线等同于枪口射线

风险：越肩视角隔墙射击。

对策：相机确定目标点，枪口/服务器权威枪口完成最终遮挡与命中。

### 9.8 预测重放产生副作用

风险：重复枪声、VFX、扣资源、伤害和投射物。

对策：模拟函数只产生可描述结果；权威副作用只在服务器；表现用事件 ID、动作序号或 predictionKey 去重。

### 9.9 技能框架过早抽象

风险：还不知道真实需求就制造大量接口、标签和配置。

对策：先完成冲刺，再用投射物作为第二个例子提取最小公共结构。

### 9.10 美术和系统范围膨胀

风险：角色很多，但 3C、网络和战斗都未形成闭环。

对策：固定一个角色、一把武器、一个地图；每增加一个技能必须对应新的技术问题。

## 12. Definition of Done

### 12.1 MVP 收口

下列条件全部满足后，CalabiYau 可以被描述为“二次元第三人称联网动作射击垂直切片”：

- 人物移动、瞄准、跳跃、冲刺、射击和换弹操作清楚且响应及时；
- 相机环绕、越肩、肩位切换和防穿墙稳定；
- LogicRoot、VisualRoot、Camera 和 Animator 职责清晰；
- 服务器最终裁决位置、碰撞、弹药、冲刺合法性、命中、伤害和生命状态；
- 客户端本地预测、服务器校正和未确认输入重放覆盖人物移动与冲刺；
- 远端使用快照/语义状态平滑重建移动、瞄准和动作；
- Hitscan 处理相机目标与枪口遮挡，延迟补偿有可视化对比；
- 弱网下不会重复冲刺、开火、伤害、死亡或重要表现；
- 正常、100/200 ms、抖动和丢包测试有记录；
- 自动测试覆盖共享模拟、碰撞、武器、冲刺和关键网络时序；
- Profiler、服务端 Tick 和网络包体有实测基线；
- 第三方模型、动画、音效和特效均有来源/许可记录；
- README、架构图、演示视频和至少三个问题复盘完成；
- 文档能严格区分已完成、待验收、P1 和研究项。

### 12.2 扩展收口

在 MVP 已完成的基础上，再满足以下条件，才把技能扩展写入最终项目能力：

- 最小数据驱动技能框架已经由冲刺和至少第二个真实技能验证；
- 一个服务器权威投射物技能具备预测表现、匹配和唯一结算；
- 一个持续范围技能具备权威生命周期、周期效果和晚加入恢复；
- 弱网下不会重复技能、投射物、资源消耗、伤害或重要表现；
- 自动测试覆盖技能状态、投射物、范围效果和关键网络时序；
- 可选部位 HitBox、机器人压测或其他研究项只按实际完成情况描述。
