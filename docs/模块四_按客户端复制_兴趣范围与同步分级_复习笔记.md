# 模块四：按客户端复制、兴趣范围与同步分级复习笔记

> 复习重点：服务器世界仍完整模拟，但不同客户端收到不同的状态视图。要能解释“范围”“状态刷新频率”“字段差分”三件事为什么不能混为一谈。

---

## 一、模块总览

```text
GameWorld：维护全部玩家的权威状态，仍以 30Hz 模拟
-> SnapshotBuilder.Capture()：读取一次世界状态为候选实体
-> 每个 ConnectedClient 的 ClientReplicator：独立筛选与安排发送
-> WorldSnapshot：players + replicatedPlayerIds
-> 客户端：刷新状态、保留或回收远端 Avatar
```

**核心目标：** 降低无关实体的带宽、序列化和客户端表现开销，同时保证近处和战斗对象仍平滑可玩。

---

## 二、一次按客户端快照如何生成

### 工作过程

`SnapshotBuilder` 从 `GameWorld` 读取所有权威玩家状态，生成不含 UDP Endpoint 的 `ReplicationCandidate` 列表。随后服务器为**每一个客户端**调用该客户端自己的：

```text
ClientReplicator.BuildSnapshot(
    recipientPlayerId,
    serverTick,
    candidates)
```

对接收者 A，复制器遍历全部候选玩家：

```text
是否 A 自己，或距离 <= 45m？
-> 否：不在复制范围

-> 是：加入 replicatedPlayerIds
      再判断高/低优先级
      决定本包是否把完整状态加入 players
```

因此同一个权威世界会生成不同客户端视图：A 可能收到 B 而收不到 C；C 也会有自己的独立发送节奏和快照序号。

### 代码定位

- `Server/Server/SnapshotBuilder.cs`：从权威世界捕获候选状态。
- `Server/Server/ClientReplicator.cs`：按接收者构建快照。
- `Server/Server/UdpGameServer.cs`：在快照节奏中为每个客户端调用复制器。

### 面试话术

> 我将世界状态读取和网络复制策略分离。`GameWorld` 只维护完整权威状态，`SnapshotBuilder` 将其转为无网络细节的候选实体；之后每个连接各自拥有 `ClientReplicator`，按照接收者的位置、战斗状态和发送历史生成独立快照。因此不是把同一份全世界快照广播给所有人，而是同一权威世界对应多个按客户端裁剪的复制视图。

---

## 三、距离与战斗状态的频率分级

### 工作过程

当前规则：

```text
自己
-> 永远高频

距离 <= 18m
-> 高频，30Hz

18m < 距离 <= 45m，且最近约 30 Tick 发生过战斗
-> 高频，30Hz

18m < 距离 <= 45m，非战斗
-> 低频，5Hz

距离 > 45m
-> 不进入复制范围
```

战斗提升优先级只在 `45m` 复制范围内有效。服务器仍以 30Hz 模拟全部玩家；降低的是“某实体发给某客户端的状态频率”，不是服务器移动、冷却或命中判定频率。

新进入范围的实体即使属于低频，也会立即发送一次完整状态。离开范围后，服务器清理该客户端对该实体的发送记录；下次重新进入范围，会再次立即发送初始完整状态。

### 面试话术

> 我将服务器模拟频率和实体复制频率分开：世界始终以 30Hz 推进，但自己、近距离和近期战斗实体高频复制，范围内远处非战斗实体降到 5Hz，45m 外不复制。新实体进入范围时立即发送完整状态，之后再按优先级限频；这样把带宽优先留给与当前玩家体验最相关的对象，而不会降低服务器规则精度。

## 四、`players` 与 `replicatedPlayerIds`：状态刷新和范围必须分开

### 工作过程

低优先级实体 B 虽然只 5Hz 更新，但外层快照仍以 30Hz 发送：

```text
Tick 100
players = [A, B]
replicatedPlayerIds = [A, B]

Tick 101
players = [A]
replicatedPlayerIds = [A, B]
```

`players` 表示“本包真正携带完整状态的实体”；`replicatedPlayerIds` 表示“当前仍应保留的复制范围”。因此客户端只有在 B 不再位于 `replicatedPlayerIds` 时，才回收其 Avatar。

```text
首次收到 B 状态
-> 创建 B 的 Avatar

B 仍在 replicatedPlayerIds 但本包没有状态
-> 保留 Avatar，继续插值或等待下次刷新

B 离开 replicatedPlayerIds
-> 回收 Avatar
```

低频实体每约 6 Tick 收到一次完整状态；模块二的自适应插值延迟负责延长它的历史播放缓冲，避免中间空包导致停住后跳变。

### 代码定位

- `ClientReplicator.BuildSnapshot()`：同时生成状态数组和范围数组。
- `UdpNetworkClient.GetReplicationScopePlayerIds()`：读取范围。
- `UdpNetworkClient.RemoveRemoteAvatarsOutsideReplicationScope()`：回收真正离开范围的 Avatar。

### 面试话术

> 我把实体是否仍在兴趣范围与本包是否刷新它的状态分开表达。低频实体在中间快照中可能不出现在 `players`，但仍存在于 `replicatedPlayerIds`；客户端因此不会误删 Avatar，只继续保留并插值。只有实体离开复制范围时才回收对象，这避免了低频同步下的对象闪烁和重复创建。

## 五、为什么当前采用全量状态而不是字段级差分

### 工作过程

当前每次决定发送某实体时，状态条目都是：

```text
isFullState = true
changeMask = All
```

即位置、朝向、血量、存活等完整字段都可独立解析。若 Tick 106 的 B 状态包丢失，Tick 112 的完整 B 状态仍可直接覆盖恢复；它不依赖 Tick 106。

字段级差分则只发变化字段，例如：

```text
基线：位置 0，血量 100
位置变为 1
-> 只发 Position
```

若这个位置差分包丢失，而服务器错误地假设客户端已经有位置 1，下一包只发血量变化，客户端会保留旧位置 0。这不是 JSON 解析失败，而是客户端缺少本应由丢失包更新的字段。

### 确认基线是什么

基线是服务器与客户端都确认一致的一份状态，例如 Snapshot #100。真正差分同步必须：

```text
服务器发送完整 Snapshot #100
-> 客户端收到并 ACK #100
-> 服务器记录：该客户端确认基线为 #100

后续差分包丢失
-> 客户端没有 ACK 新版本
-> 服务器仍以 #100 为基线计算下一份差分
-> 将相对 #100 变化的字段再次带上
```

因此，正确的差分协议能处理 UDP 丢包，但需要每客户端、每实体的确认基线、快照 ACK、`baselineId`、`snapshotId`、`changeMask`，以及定期全量关键帧恢复。

### 当前取舍

当前项目只有关键事件 ACK，没有快照 ACK；因此使用全量实体状态是合理取舍：每次状态独立、丢包恢复简单、适合少量玩家和 JSON 调试。代价是重复字段较多，实体数量上升后带宽增长更快。

### 面试话术

> 当前项目实现了实体范围过滤和频率分级，但状态条目仍使用全量状态。原因是 UDP 下“服务器已发送”不等于“客户端已收到”；差分包丢失后，如果服务器按未确认的新状态继续省略字段，客户端会长期保留旧字段。真正差分同步需要客户端确认快照基线，服务器基于最后确认基线计算变化字段，并用关键帧修复丢包或重连。当前先用全量状态换取独立解析和稳定恢复，是针对 Demo 阶段的明确取舍。

## 六、事件也遵循兴趣范围

### 工作过程

快照过滤后，事件也不能再无差别广播。服务器根据事件关联的玩家判断相关性：

```text
FireEvent：射手
HitEvent：射手和目标
Death / Respawn：发生生命周期变化的玩家
KillEvent：击杀者和受害者
MatchEnd：全局事件
```

只有相关玩家仍处于接收者复制范围，才向该客户端发送事件。范围外并不代表玩家从 `GameWorld` 消失，只是该客户端不再收到其状态与普通战斗事件。

### 面试话术

> 兴趣管理不仅筛选状态快照，也用于事件相关性路由。服务器根据开火、命中或死亡事件关联的玩家，判断该事件是否对接收客户端仍有意义；这样远距离无关客户端不会持续收到别处战斗的状态和事件，快照与事件的可见性保持一致。

## 七、当前边界、验收与升级方向

### 当前边界

- 当前兴趣范围只按二维地面距离判断，不是视锥裁剪、遮挡裁剪或完整 AOI 分区。
- 为每个客户端构建快照时仍遍历全部候选实体，实体量大时距离判断接近 `O(N²)`。
- 当前 `isFullState=true`、`changeMask=All`，没有快照确认基线和真正字段差分。
- 低频实体的自适应插值延迟已实现，但该动态延迟尚未精确反馈到开火延迟补偿。

### 验收场景

```text
10m：远端每个快照都更新，约 30Hz
30m 且非战斗：远端约每 6 Tick 更新，Avatar 不删除
30m 且近期战斗：约 1 秒内恢复高频
超过 45m：从 replicatedPlayerIds 消失，客户端回收 Avatar
重新进入 45m：立即收到完整状态并重新创建 Avatar
```

服务器遥测重点看每客户端的 `bytes`、`statePlayers`、`scopePlayers`；其中 `statePlayers < scopePlayers` 对低频实体是正常现象。

### 优化方向

```text
距离筛选
-> 空间网格 / AOI 分区，减少全量距离遍历

完整状态
-> 快照 ACK + 确认基线 + 差分字段 + 定期关键帧

地图与相机完善后
-> 视锥、遮挡与更细粒度实体优先级
```

## 八、本模块重点疑惑回顾（保留我的实际提问）

### 1. 阶段四能否概括为“近处/战斗高频，中距离低频，远处不显示”？

可以。更严谨地说：自己和 `18m` 内实体高频；`18m` 到 `45m` 的近期战斗实体也高频；同范围非战斗实体低频；超过 `45m` 不进入该客户端复制范围。服务器仍模拟范围外实体，只是不向该客户端同步，也由客户端回收其 Avatar。

### 2. 确认基线是干什么的？

确认基线是客户端明确 ACK 过、服务端确认双方一致的一份旧状态。字段差分只能相对于确认基线省略未变化字段；否则差分包丢失后，服务器不知道客户端缺了哪些字段，客户端会长期保持旧数据。

### 3. 现在不做字段级差分是好事吗？

对当前小规模 UDP + JSON Demo 是合理取舍，不是永远更好。全量实体状态会重复发送字段，但每次可独立解析，丢包后下次完整状态能恢复；差分同步更省带宽，但必须补快照 ACK、基线管理和关键帧恢复。

---

## 九、60 秒模块总结

> 项目将权威世界状态读取与复制策略分离：服务器先捕获全部候选实体，再由每个客户端独立的 `ClientReplicator` 按距离和战斗状态生成不同快照。自己、近距离和近期战斗实体高频复制，范围内远处非战斗实体低频，45m 外不复制；`replicatedPlayerIds` 表示仍在范围的实体，`players` 只表示本包刷新的状态，因此低频对象不会被误删。当前采用完整状态而非字段差分，以避免 UDP 丢包导致未确认基线上的字段长期陈旧；后续可通过空间 AOI、快照 ACK、确认基线、差分字段和关键帧继续升级。
