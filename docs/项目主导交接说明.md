# CalabiYau 项目主导交接说明

## 一、项目定位与协作目标

这是一个用于 Unity 游戏客户端/网络方向实习展示的个人项目：Unity 客户端加 .NET 8 C# UDP 独立服务器，实现服务端权威的第三人称坦克射击 Demo。

协作目标不是盲目堆叠“商业级”名词，而是让作者能理解、独立讲清并验证每项实现。作者是 Unity 初学阶段的本科生；讲解应先说明“解决什么问题、为什么选这个方案、有什么替代方案”，再开始代码修改。

## 二、已完成的网络底座

- UDP + JSON 通信；服务器固定 30Hz Tick，客户端只上报移动、瞄准和开火意图。
- 服务端权威 `GameWorld`：作为无渲染的 GameCore 式模拟核心，统一推进位置、朝向、血量、死亡和重生。
- 客户端本地预测、权威快照校正、未确认输入重放；远端快照插值、短时外推和表现层平滑追赶。
- 服务端权威射击：开火进入 Tick 队列，服务端维护玩家历史位置并进行有限延迟补偿；当前命中模型是简化的射线与圆形命中半径。
- 阶段 9 已完成服务端职责拆分：网络收发、连接会话、权威世界、快照构建、按客户端复制、可靠事件账本各自分离。
- 阶段 10 已完成命令时间线和权威校验门：输入去重、过期拒绝、输入租约、服务端推导射线和快照序列号。
- 阶段 11 已完成按客户端复制与轻量兴趣管理：距离与近期战斗状态决定复制范围和高/低频同步；当前是全量状态快照，不是真正字段差分。
- 阶段 12A 已完成开火请求序列、收据确认、有限重发和服务端去重。
- 阶段 12B/12B.1 已完成死亡、重生、击杀、结算的事件 ID、ACK、有限重传和去重；以 `lifeStateVersion` 解决死亡/重生乱序，Avatar 未创建时缓存生命周期事件；握手下发真实服务器 TickRate。
- 已有运行时调试面板与弱网验证能力：RTT、快照缓冲、预测误差、校正、快照缺口、开火收据、可靠事件重传和 ACK 延迟等。

## 三、已知边界：不能写成“已完成”

- 没有真正的基线确认、字段级差分复制、量化压缩或位打包；`changeMask` 仅为后续扩展预留。
- 当前兴趣管理是距离/战斗状态分级，不是视锥裁剪，也不是地图分区 AOI。
- 没有完整断线重连、观战回放、大厅匹配、独立战斗服调度或多线程世界分片。
- 服务端尚未具备完整地图障碍物/物理碰撞模拟；后续若继续网络优化，可先做轻量空间校验。
- 当前表现仍是 Tank 验证版本，角色模型、第三人称相机、动画状态机和完整 3C 属于长期第三章方向。

## 四、当前建议的节奏

网络项目已具备较完整的实习展示价值。不要继续无止境扩张网络功能。

近期优先事项：

1. 根据个人时间决定是否完成轻量服务端空间校验；完成后收束网络开发。
2. 复习现有模块，准备架构图、README、弱网测试记录和演示视频，同时开始投递实习。
3. 3C 作为长期学习分支：先做固定角色模型、第三人称相机、逻辑/表现分离、Local/Remote Player 分离，再逐步加入动画和武器表现。

## 五、主导对话应遵守的约束

- 修改前先阅读相关代码和文档；不靠历史猜测覆盖当前实现。
- 只做小步、可运行、可验收的改动；每个阶段给出手动验收步骤和必要测试。
- 保持现有 UDP + JSON、服务端权威、固定 Tick 架构，除非先讨论迁移收益和代价。
- 不引入复杂框架、反射、ECS 或第三方网络库来制造“高级感”。
- 严格区分“已实现、正在验证、未来规划”，尤其在简历和项目文档中。
- 解释使用某项技术的原因和替代方案；代码优先清晰、适合作者复习。
- 尊重现有用户改动，禁止随意回滚、删除 Assets 或 Git 历史。
