# 模块五：调试面板、弱网验证与测试复习笔记

> 复习重点：知道每个调试数据在测什么；能针对延迟、抖动、丢包、重复和乱序设计验收；能说明服务端单元测试与双客户端弱网测试各自覆盖什么。

---

## 一、调试面板的定位：从“画面现象”回到原因

调试面板不是展示一堆数字，而是用于回答：

```text
网络有没有慢？
快照有没有断？
预测和服务器世界是否分叉？
可靠事件是否正在重传？
低频复制是否按预期运行？
```

当前面板主要由 `UdpNetworkClient.OnGUI()` 绘制。

---

## 二、RTT：当前测的不是纯 Ping

### 工作过程

客户端发送带 `inputTick=101` 的输入；服务器在快照中回传：

```text
lastProcessedInputTick = 101
```

客户端收到该快照时：

```text
RTT 样本
= 当前收到快照时间 - 输入 101 的发送时间
```

它包含：

```text
客户端上行
+ 等待服务器 Tick 消费
+ 等待快照下发
+ 服务器下行
```

因此它更准确叫“输入端到端确认延迟”，不是纯网络 Ping。面板同时显示：

```text
smoothed RTT：平滑后的当前参考值
last RTT：最近一次原始样本
```

若二者差异明显，说明网络或服务器 Tick 等待存在波动。

### 代码定位

- `UdpNetworkClient.UpdateRttFromAcknowledgedInput()`：根据确认输入生成样本并平滑。
- `UdpNetworkClient.FormatRttText()`：面板显示平滑值与最近样本。

### 面试话术

> 调试面板中的 RTT 不是传统 Ping，而是输入从客户端发送、经服务器 Tick 消费、再由快照确认返回的端到端时间。它更接近玩家一次操作真正被服务器确认的延迟；我同时显示平滑值和最近样本，用于判断稳定延迟和抖动。

## 三、World ticks 与 Input ticks：分别看哪条时间线落后

### 工作过程

面板显示：

```text
World ticks
-> 客户端估算的当前 serverTick
-> 最近收到快照中的 serverTick

Input ticks
-> 本地已发送到第几个 inputTick
-> 服务器确认到 lastProcessedInputTick
```

例如：

```text
本地 inputTick = 150
服务器确认 = 144
```

说明有 6 条本地输入已经执行并发出、但服务器尚未确认。这是本地预测正常存在的原因，不代表 6 个包都丢失；数量持续增大才可能表示网络确认延迟升高，或服务器快照迟迟未返回。

### 面试话术

> 我将服务器世界 Tick 和客户端输入 Tick 分开显示。前者帮助判断快照与服务器时间线的距离，后者反映本地预测仍有多少输入未被服务器确认。未确认输入不是错误，而是本地预测的正常工作区；持续积压才说明确认链路出现延迟或阻塞。

---

## 四、预测误差与校正次数：判断网络慢还是两端规则分叉

### 工作过程

面板关键项：

```text
Latest prediction error
-> 当前本地预测位置与重建预测目标的距离

Smooth corrections
-> 历史累计平滑校正次数

Hard corrections
-> 历史累计硬修正次数

Corrections (5s)
-> 最近 5 秒发生的校正次数
```

判断方式：

```text
RTT 高，但预测误差小、校正少
-> 网络慢，但客户端和服务器运动规则基本一致

RTT 不高，但校正频繁、误差很大
-> 更像两端速度、Tick、碰撞或重放规则不同

持续移动时误差升高，松手后才收敛
-> 符合当前“移动中延后校正”的设计边界
```

预测误差比单看 RTT 更能判断问题来自网络，还是来自同步逻辑不一致。

### 代码定位

- `UdpNetworkClient.ReconcileLocalPrediction()`：计算误差、记录平滑/硬修正次数。
- `UdpNetworkClient.OnGUI()`：显示误差和校正计数。

### 面试话术

> 我不仅观察 RTT，还观察预测误差和校正次数。高延迟但误差小，说明预测与服务器规则仍一致；低延迟却频繁大校正，通常是两端时间步、速度或碰撞规则分叉。这样可以避免把所有画面跳变都误判成网络问题。

## 五、Snapshot delivery：丢包率是交付缺口估算

### 工作过程

快照带 `snapshotSequence`。客户端若看到：

```text
上一次最新序号 = 100
本次最新序号 = 104
```

会估算：

```text
可能少了 101、102、103
estimatedMissedSnapshotCount += 3
```

再计算：

```text
estimated loss rate
= 估计遗漏数量
 /（收到数量 + 估计遗漏数量）
```

它更准确叫“快照交付缺口估算”，不等同严格抓包意义上的物理网络丢包率。UDP 乱序也可能造成序号先跳过、旧包之后到达；旧快照通常已没有同步价值，仍会被丢弃。

因此它对“快照是否及时参与同步”有价值，但不能直接宣称为精确丢包率。

### 代码定位

- `UdpNetworkClient.RecordSnapshotStats()`：根据序号缺口估算遗漏。
- `UdpNetworkClient.FormatSnapshotDeliveryText()`：显示估算缺口率。

### 面试话术

> 我通过快照序列号间隔估算快照交付缺口，用来观察弱网下有多少状态未能及时参与客户端同步。它不是严格网络层丢包率，因为 UDP 乱序也会形成序号跳跃；但从状态同步视角看，迟到旧快照同样会被丢弃，所以该指标仍能反映快照链路的有效性。

## 六、远端缓冲、开火收据与可靠事件

### 工作过程

面板还会显示：

```text
Snapshot buffer
-> 所有远端 Avatar 当前缓存的快照数量

Remote interpolation
-> 基础插值延迟与实际动态延迟

Fire request receipts
-> 待确认开火数、重发次数、失败次数、接受/拒绝数

Reliable results
-> 最近可靠事件数、重复丢弃数、旧生命周期事件丢弃数、待缓存生命周期事件数
```

组合解释：

```text
低频实体
-> 快照缓冲与实际插值延迟变大
-> 正常现象，不一定是卡顿

开火待确认、重发持续增加
-> FireReceipt 可能丢失或服务器处理存在问题

可靠事件重发多、ACK 延迟高
-> 弱网下关键结果正在走有限可靠机制

重复事件丢弃增加
-> 发生了重传，但客户端去重正在正常工作
```

### 面试话术

> 调试面板还将远端缓冲、开火收据和可靠事件作为一组观察。低频对象缓冲和插值延迟提高通常是带宽分级的预期行为；开火重发和待确认数量反映请求收据链路；可靠事件的重传、ACK 延迟和重复丢弃则用于确认关键结果在弱网下是否正确地重试并保持至多一次应用。

## 七、弱网测试到底测什么

弱网测试不是只把延迟调到 200ms，再看角色有没有卡；它要验证每类机制在坏网络下是否按语义工作。

| 弱网条件 | 本质 | 主要验证模块 |
| --- | --- | --- |
| 延迟 | 包稳定地晚到 | 本地预测、延迟补偿、输入确认 |
| 抖动 | 每个包延迟不稳定 | 快照缓冲、自适应插值延迟 |
| 丢包 | 一部分包永远不到 | 最新快照、输入租约、有限重发 |
| 重复 | 同一包多次到达 | `fireSequence`、`eventId` 去重 |
| 乱序 | 后发包先到 | 快照新旧过滤、`lifeStateVersion` |

若弱网工具设置的是“单方向额外延迟 100ms”，双向确认延迟可能接近 200ms。测试时应以面板的输入确认延迟为准，不只相信工具配置。

---

## 八、延迟、抖动与丢包的验收

### 1. 延迟测试

可测试：

```text
0ms
100ms
200ms
```

预期：

```text
本地移动：按键仍立即响应，RTT 和未确认输入上升，预测后仍可收敛
远端玩家：显示更滞后，但继续平滑
射击：FireReceipt 更晚，FireEvent 的回溯时间增加
```

当“确认延迟 + 插值延迟”超过 350ms 时，服务器不会无限回溯。这是当前公平性上限，不是测试失败。

### 2. 抖动测试

在固定延迟基础上加入随机波动，预期：

```text
last RTT 波动，smoothed RTT 相对稳定
快照到达间隔不均匀
远端 Avatar 的有效插值延迟可能提高
远端视觉更滞后，但不应频繁停住、瞬移和前后抽搐
```

抖动下远端卡顿，应先看：

```text
Snapshot buffer
Remote interpolation
Snapshot delivery
```

抖动主要伤害远端快照播放，不一定会让本地输入立刻变差。

### 3. 丢包测试

可从：

```text
1%
5%
10%
```

预期：

```text
快照丢失
-> snapshotSequence 出现缺口
-> 下一份完整状态仍能独立恢复
-> 远端短暂保持或更滞后，但不长期错误

停止移动输入丢失
-> 服务器最多按输入租约短暂沿用旧输入
-> 租约到期后停止，不应永久向前移动

FireRequest 或 FireReceipt 丢失
-> 客户端有限重发同一 fireSequence
-> 服务器只入队一次，不应重复扣血

Death / Respawn 丢失
-> 服务器有限重发
-> 客户端 eventId 去重
-> 最终不应丢失或重复执行
```

## 九、重复、乱序与综合验收矩阵

### 重复包

```text
同一 FireRequest 重发
-> 同一 fireSequence 只进入 PendingFires 一次

同一 DeathEvent 重发
-> eventId 只应用一次，但仍 ACK

同一输入重复
-> 最新意图逻辑不应让世界倒退
```

### 乱序包

```text
旧 WorldSnapshot 晚到
-> serverTick 更旧
-> 客户端丢弃，不覆盖新状态

DeathEvent 晚于 RespawnEvent
-> lifeStateVersion 更旧
-> 客户端忽略，不把重生玩家重新判死

旧 FireRequest 晚到
-> 当前不同 fireSequence 的乱序会被拒绝
-> 属于已知有限可靠语义，不是 bug
```

### 建议矩阵

| 场景 | 设置 | 重点验收 |
| --- | --- | --- |
| 基线 | 0ms、0% 丢包 | 双客户端移动、射击、死亡重生完整运行 |
| 高延迟 | 100ms、200ms | 本地跟手、预测误差、回溯 Tick、远端平滑 |
| 抖动 | 固定延迟 + 随机波动 | 插值缓冲、动态延迟、远端不抽搐 |
| 丢包 | 1%、5%、10% | 快照恢复、输入租约、收据重发、可靠事件 |
| 重复/乱序 | 工具支持时开启 | 去重、新旧快照过滤、生命版本过滤 |
| 综合 | 延迟 + 抖动 + 少量丢包 | 无重复伤害、无永久错误、可继续游玩 |

测试记录至少保留：

```text
弱网设置
面板关键数据
看到的现象
是否符合预期
若不符合，定位到哪个模块
```

示例：

```text
200ms 确认延迟 + 5% 丢包：
本地移动仍立即响应；
远端有更高视觉延迟但未频繁闪烁；
FireRequest 出现重发，但无重复扣血；
DeathEvent ACK 延迟上升，最终仍正确重生。
```

### 面试话术

> 我通过弱网工具分别注入稳定延迟、抖动、丢包、重复和乱序，而不是只测试高 Ping。延迟主要验证本地预测与历史回溯，抖动验证远端快照缓冲和插值，丢包验证全量快照恢复、输入租约以及开火和生命周期事件的有限可靠语义，乱序验证快照 Tick 过滤和生命版本过滤。测试时结合面板的确认延迟、预测误差、快照序号缺口、重传与 ACK 数据记录结果，确保优化有可观测依据。

## 十、服务端单元测试与三层验证

### 验证分层

```text
第一层：服务端单元测试
-> 验证规则是否正确
-> 不启动 UDP、不依赖 JSON、不依赖 Unity

第二层：双客户端联调
-> 验证客户端、UDP、快照和 Avatar 是否真正接通

第三层：弱网测试
-> 注入坏网络，验证实际运行时的时序语义
```

三层不能互相替代。服务端单元测试通过，只说明 `GameWorld` 规则正确；它不能证明 Unity 一定正确创建 Avatar，也不能证明两端 JSON 协议完全一致。

### 当前服务端测试覆盖

测试入口：`Server/Server.Tests/Program.cs`。

```text
输入
- 乱序旧输入不能让世界倒退
- 输入租约到期后角色停止
- 非法轴值、NaN、未来输入被拒绝

开火
- 开火入队后，Tick 前不能扣血
- 同一 fireSequence 只能入队一次
- 重传得到同一份 FireReceipt
- 死亡玩家不能移动或开火

复制
- 自己始终发送
- 范围外玩家不进入复制范围
- 低频玩家保持 scope，但不每包刷新
- 快照保留 LifeStateVersion

可靠结果
- ACK 前按间隔重发，ACK 后不再重发
- 到达重试上限后停止
- 同一 eventId 只应用一次
- 去重窗口有限
- Death / Respawn 版本单调递增
- 等待可靠 ACK 时快照仍继续发送
```

### 为什么 `GameWorld` 能单独测试

`GameWorld` 不知道 UDP Socket、JSON、Unity GameObject 或 Rigidbody。它接收 `InputCommand`、`FireCommand`，输出权威 `PlayerState`、世界事件和收据决定，因此测试可以直接：

```text
输入命令
-> 推进 Tick
-> 断言位置

开火命令
-> Tick 前断言目标不掉血
-> 推进 Tick
-> 断言掉血和 FireResolvedEvent
```

这就是网络层与权威世界分离带来的可测试性。

### 当前测试边界

当前未自动化覆盖：

```text
真实 UDP 的发送、丢包、乱序
客户端 JSON 反序列化
Unity Avatar 创建和表现
本地预测的 Rigidbody 行为
外部弱网工具下的双端回归
```

未来可逐步增加协议序列化往返测试、本机 UDP 集成测试、Unity PlayMode 测试和固定弱网配置的回归脚本。

### 面试话术

> 我把验证拆为服务端规则单元测试、双客户端联调和弱网场景测试。`GameWorld` 不依赖 UDP、JSON 或 Unity，可以直接构造命令、推进 Tick 并断言权威状态和事件，因此稳定覆盖了输入乱序、开火去重、生命周期版本、复制范围和可靠重传等时序规则；真实协议与 Unity 表现则通过双端和弱网测试补充验证，并明确保留自动化不足的边界。

## 十一、现象到模块的定位表

| 现象 | 优先检查 |
| --- | --- |
| 本地按键不跟手 | `TankController`、预测输入、本地控制是否被关闭 |
| 本地频繁被拉回 | 预测误差、速度/Tick 一致性、移动中延后校正 |
| 远端一停一跳 | 快照频率、缓冲区、插值延迟、低频规则 |
| 远端 Avatar 闪烁 | `replicatedPlayerIds` 与 `players` 是否混用 |
| 一枪扣两次血 | `fireSequence` 去重、`PendingFires`、重传逻辑 |
| 有开火表现但没伤害 | `FireReceipt` 与 `FireEvent` 是否混淆、冷却或瞄准拒绝 |
| 死亡后又重生再死亡 | `lifeStateVersion`、可靠事件乱序过滤 |
| 状态正确但少受击火花 | `HitEvent` 可丢失，检查快照血量 |
| 可靠事件持续重发 | ACK、Endpoint、事件是否仍在复制范围 |

## 十二、重点追问

### 1. 面板中的“丢包率”是不是严格网络丢包率？

不是。它是根据 `snapshotSequence` 跳跃得到的快照交付缺口估算，乱序包也会影响它；它适合判断有多少快照没及时参与同步，不能替代底层抓包统计。

### 2. RTT 高是不是一定会让本地预测很差？

不一定。RTT 高只说明确认变慢；若客户端和服务器移动规则一致，预测误差仍可较小。应同时看预测误差和校正次数。

### 3. 为什么还要单元测试，双客户端跑通不就够了吗？

双客户端难以稳定构造重复、乱序、边界 Tick 等时序条件。单元测试能直接构造命令并断言规则；联调和弱网测试则验证协议、网络与表现层，三层共同覆盖。

## 十三、60 秒模块总结

> 我为网络调试面板保留了输入确认延迟、服务器与输入 Tick、预测误差、校正次数、快照序号缺口、远端缓冲、开火收据和可靠事件等指标，用于把画面异常定位到网络、预测、复制或时序模块。弱网测试分别注入延迟、抖动、丢包、重复和乱序，验证本地预测、远端插值、输入租约、开火去重和生命周期可靠性。除此之外，服务端将 `GameWorld` 保持为不依赖 UDP、JSON 和 Unity 的纯规则层，通过单元测试覆盖关键时序边界，再以双客户端和弱网测试补足真实协议与表现验证。
